<objective>
Make a property violation say which invariant broke, and make the three defect cases that plan 06-01
committed fail loudly and specifically instead of not being run at all.

Measured starting point, from `06-RESEARCH.md` section 3.1: `engine/tests/fuzz_invariants.rs` is a
single `#[test] fn test_fuzz_invariants()` at line 19 that evaluates ten invariants plus two safety
checks inline over 100 cases. Its messages already carry names such as `INV1 sum_conservation`, so
COV-02 is not about adding names. Three gaps are:

1. Twelve checks share one cargo test, so cargo's own output cannot say which invariant broke.
2. `INV9 collation` at lines 203-206 is a comment and nothing else — it evaluates zero assertions and
   the file says so. `INV6 adoption_equality` at lines 146-158 does not check adoption; its body is
   byte-equivalent to the `SAFETY no_negative_nfe` check at line 243. `INV3` and `INV4` are gated to
   testate cases only.
3. No invariant has a stable machine-readable id.

Every strengthening below was evaluated over all 140 committed inputs and 564 heir rows during
planning, and each produced **zero** violations. The measurements are in `06-RESEARCH.md`
section 3.2. One candidate was rejected there for producing 37 violations, and it is not proposed
here.

The second half of this plan is `engine/tests/defect_ledger.rs`, the bidirectional check over
`engine/defect-baseline.json`. It fails when a defect case violates an invariant its entry does not
declare (the defect got worse) and it fails when a declared violation is no longer observed (the
defect was fixed and the ledger must shrink). That second direction is what makes phases 7 and 14
self-verifying.
</objective>

  <action>
Rewrite `engine/tests/fuzz_invariants.rs` so that each named invariant is an independent function
and an independent `#[test]`.

**Corpus discovery.** Replace the single `const FUZZ_DIR` with
`const CORPUS_DIRS: &[&str] = &["examples/fuzz-cases", "examples/coverage-cases"];`. A shared
`fn load_corpus() -> Vec<(String, EngineInput, EngineOutput)>` reads every `.json` file from both
directories in sorted filename order, parses it, runs `run_pipeline` inside
`std::panic::catch_unwind`, and panics with the filename when either step fails. It asserts the
combined file count is at least **130**, so deleting inputs cannot quietly shrink what these tests
cover.

**The invariant table.** Declare a top-level
`const INVARIANTS: &[(&str, &str, fn(&EngineInput, &EngineOutput) -> Vec<String>)]` whose entries
are `(id, human_name, check_fn)`. Ids and names, in this order:

| id | name | what the check function returns a violation for |
|---|---|---|
| `INV01` | `sum_conservation` | sum of `net_from_estate` across rows differs from `net_distributable_estate` |
| `INV02` | `legitime_floor` | any row has `total` below zero |
| `INV03` | `ic_le_lc` | with both present and nonzero, `max(IC total)` exceeds `min(LC own-right total)`. **Remove the testate-only gate**: this was measured over all 140 inputs across every succession type with zero violations |
| `INV04` | `ic_cap` | total of all `IllegitimateChildGroup` totals exceeds the estate. **Remove the testate-only gate** |
| `INV05` | `representation_link` | a row with `represents` set whose `inherits_by` is not `Representation`, or a row with `inherits_by` `Representation` whose `represents` is unset, or a representation group whose summed `net_from_estate` is negative. Both directions measured with zero violations |
| `INV06` | `adoption_equality` | an input person with `relationship_to_decedent` `AdoptedChild` whose output row is not in `EffectiveCategory::LegitimateChildGroup`, or whose `total` differs from another own-right `LegitimateChildGroup` row in the same case when both rows have `donations_imputed` of zero and both totals are above zero. **This replaces the current body, which checks only that `net_from_estate` is non-negative and duplicates the safety check below** |
| `INV07` | `preterition_annulment` | `succession_type` is `IntestateByPreterition` and no row has a positive `total` |
| `INV08` | `disinheritance_zero` | a validly disinherited heir with no children in the family tree has a nonzero `total` |
| `INV09` | `collation_identity` | any row where `gross_entitlement` differs from `net_from_estate` plus `donations_imputed`. **This replaces the current comment-only INV9, which evaluates nothing.** Measured over 564 rows with zero violations |
| `INV10` | `scenario_consistency` | the scenario-code prefix does not match the succession type, using the existing rules at lines 216-224 unchanged, including the documented `IntestateByPreterition` allowance |
| `INV11` | `gross_ge_net` | any row where `gross_entitlement` is below `net_from_estate` |
| `INV12` | `donations_imputed_nonneg` | any row with `donations_imputed` below zero |
| `INV13` | `unique_heir_id` | a `heir_id` value appearing more than once in `per_heir_shares` |
| `INV14` | `legitime_fraction_present` | any row whose `legitime_fraction` is the empty string |
| `SAFETY01` | `single_share_cap` | any row whose `net_from_estate` exceeds the estate |
| `SAFETY02` | `no_negative_nfe` | any row whose `net_from_estate` is below zero |

Every returned violation string must begin with the invariant id, then a colon and a space, then the
offending heir id when the violation is per-row, then the expected and the observed value. Preserve
the existing message content wherever it already carries those parts.

**One `#[test]` per entry**, named `test_inv01_sum_conservation` through
`test_inv14_legitime_fraction_present`, plus `test_safety01_single_share_cap` and
`test_safety02_no_negative_nfe`. Each loads the corpus once, runs only its own check function over
every case, collects `filename` plus violation strings, and panics at the end with the full list and
a header naming the invariant id and the count of failing cases. That is sixteen tests.

**Keep `test_fuzz_invariants`**, rewritten to iterate the `INVARIANTS` table over the whole corpus
and report every violation from every invariant in one message. It is the roll-up: a case that
breaks four invariants is reported once with all four rather than in four separate test failures.
The file therefore ends with **seventeen** `#[test]` functions.

`INV06` is expected to be near-vacuous on `examples/fuzz-cases` (one `AdoptedChild` in the whole
original corpus) and to become live on the `examples/coverage-cases` files plan 06-01 generated,
which pair an `AdoptedChild` with legitimate children. If `INV06` reports a violation, that is a
real finding: stop and report BLOCKED with the case file and both totals rather than relaxing the
check.

  <action>
Create `engine/tests/defect_ledger.rs`, a new integration test binary that runs the same invariant
table over `examples/defect-cases` and compares the observed violations against
`engine/defect-baseline.json`.

Because a Rust integration test binary cannot import another test binary's items, copy the invariant
table and the check functions into this file, or extract them into
`engine/tests/common/invariants.rs` included by both with `#[path]`. Either structure is acceptable;
what must hold is that the two files evaluate the identical predicates, asserted by task 3's grep.

Parse `engine/defect-baseline.json` with `serde_json::from_str` into a
`#[derive(Deserialize)] struct DefectLedger { known_violations: Vec<DefectEntry> }` with
`DefectEntry { case: String, invariants_violated: Vec<String>, requirement: String }`. Additional
fields in the JSON are ignored by serde and need no struct member.

Three `#[test]` functions:

`test_every_defect_case_is_declared` — every `.json` file in `examples/defect-cases` has exactly one
ledger entry, and every ledger entry names a file that exists. Violations are reported as
`UNDECLARED DEFECT CASE: <file>` and `MISSING DEFECT CASE: <file>`.

`test_declared_violations_still_reproduce` — for each entry, run `run_pipeline` inside
`catch_unwind`, evaluate every invariant, and collect the ids that reported at least one violation.
Two failure directions, both required:
- an observed id that is not in `invariants_violated` is reported as
  `NEW DEFECT: <case> now violates <id>, which the ledger does not declare` — the defect got worse;
- a declared id that is no longer observed is reported as
  `STALE DEFECT DECLARATION: <case> no longer violates <id>; delete that entry from
  engine/defect-baseline.json` — the defect was fixed and the ledger must shrink.

`test_defect_cases_are_rejected_by_the_checked_entry_point` — for each case, assert that
`inheritance_engine::output_check::check_output(&output, &input.net_distributable_estate)` returns
`Err`, and that the rendered defect text contains either `sum conservation violated` or
`duplicate heir_id`. This ties the corpus-level ledger to the runtime rejection plan 05-05
introduced, so the two mechanisms cannot drift apart silently.

Every failure message must name the case file. The header of each panic must state the count of
failing cases.

Add a file-level `//!` comment stating: these three inputs reproduce defects that already have
owners — `LAW-02` in phase 7 for the collateral case, `LAW-06` in phase 14 for the two donation
cases, the latter blocked on the recorded decision `LAWYER-06` — and that the correct response to a
`STALE DEFECT DECLARATION` is to delete the ledger entry, never to re-break the engine.
