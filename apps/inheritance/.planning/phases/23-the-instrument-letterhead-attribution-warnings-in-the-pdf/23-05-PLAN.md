<objective>
Make the letterhead reachable: load the firm profile in `ActionsBar` and pass it to `downloadPDF`,
so the letterhead the app captures and stores can render in a PDF a user can actually obtain.

Purpose: this is the audit's blocker 7 and ROADMAP Phase 23 success criterion 1.
`23-RESEARCH.md` §1 measured that `ActionsBar.tsx:46` calls `downloadPDF(input, output, null)`, that
`ActionsBar` is the only production caller of `downloadPDF`, that `EstatePDF` gates the letterhead on
that third argument, and that `DEFAULT_PDF_OPTIONS.includeFirmHeader` is already `true` — so the
literal `null` is the entire reason a configured letterhead can never appear. It also measured that
`FirmProfileProvider` is mounted only at `/settings`, so `useFirmProfile()` is unreachable from the
results view and the export has to load the profile itself.

Output: one loader in `lib/firm-profile.ts`, one awaited call in `ActionsBar`, and tests that
assert the third argument is the loaded profile rather than `null`.
</objective>

<constraints>
- The profile is loaded inside the Export PDF click handler, not on every render of the results
  view. A results view that fetches a profile nobody asked for costs a round trip on every
  computation.
- `loadCurrentFirmProfile` returns `FirmProfile | null` and NEVER throws. It returns `null` when
  `supabaseConfigured` is false, when there is no signed-in user, and when the auth call rejects.
  `frontend/src/lib/supabase.ts` exports `supabase` as `null as any` when the environment variables
  are absent, so an unguarded call would throw a `TypeError` inside a click handler.
- A `null` result does NOT abandon the export. The PDF is still produced, and plan 23-04's
  attribution block prints `ATTORNEY ATTRIBUTION UNAVAILABLE` on its face, so an unbranded document
  states why it is unbranded instead of merely looking plain.
- `ActionsBar` does not call `useAuth()`. That hook subscribes to auth state on mount and would make
  every existing render of this component depend on a Supabase subscription; the loader resolves
  the user itself, at click time, through the client the rest of `lib/` already uses.
- `frontend/src/components/results/ResultsView.tsx`, `frontend/src/routes/cases/$caseId.tsx` and
  `frontend/src/App.tsx` are NOT modified. `ActionsBar`'s props are unchanged, so no consumer and no
  consumer's test moves.
- `loadFirmProfile(userId)` is reused unchanged. No second profile query is written.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  runs the scoped commands below and makes no claim about the whole suite.
</constraints>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser session → `user_profiles` | The export reads the signed-in user's own profile row |
| profile → downloaded file | Stored strings become text in a file that leaves the machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-05a | Spoofing | whose profile reaches the document | mitigate | The user id comes from `supabase.auth.getUser()`, never from a prop, a route parameter or the case row. `loadFirmProfile` filters `user_profiles` by `.eq('id', userId)` under the unchanged `user_profiles_own` policy, so a caller cannot name someone else's row. |
| T-23-05b | Denial of service | a failed profile load blocking the export | mitigate | The loader catches and returns `null`; the export proceeds and prints the absence marker. The existing `try / finally` around `setPdfLoading` is preserved, so the button is re-enabled on every path. |
| T-23-05c | Information disclosure | the profile leaving the browser | accept | The PDF is generated client-side by `@react-pdf/renderer` and handed to the browser's own download machinery. No network call carries the profile anywhere; `pdf-export.ts` opens no socket. |
| T-23-05d | Repudiation | an unbranded document looking like a branded one | mitigate | Plan 23-04's block prints `ATTORNEY ATTRIBUTION UNAVAILABLE` when the profile is `null`, and a test in this plan asserts `downloadPDF` receives `null` on the no-session path so that behaviour is reached rather than assumed. |
| T-23-05-SC | Tampering | npm installs | mitigate | This plan installs nothing; the verification block requires an empty `package.json` / lockfile diff. |
</threat_model>

`export async function loadCurrentFirmProfile(): Promise<FirmProfile | null>`

Give it a doc comment stating: that this is the loader the PDF export uses because
`FirmProfileProvider` is mounted only under `/settings` and is therefore unreachable from the
results view; that it never throws, because it runs inside a click handler and a rejection there
would abandon a download the user asked for; and that a `null` result is rendered as an explicit
marker on the document rather than as a silently unbranded page.

Body, in this order:

1. When `supabaseConfigured` is false, return `null` at once. `frontend/src/lib/supabase.ts` exports
   `supabase` as `null as any` in that case, so any property access would throw.
2. Inside a `try`, `const { data, error } = await supabase.auth.getUser();`. When `error` is
   truthy, or `data` is nullish, or `data.user` is nullish, or `data.user.id` is not a non-empty
   string, return `null`.
3. Return `await loadFirmProfile(data.user.id)`.
4. `catch` any thrown value and return `null`.

Write no second query against `user_profiles`; `loadFirmProfile` is reused exactly as it stands,
including its own fallback to `defaultFirmProfile()` when the row is missing.

Then extend `frontend/src/lib/__tests__/firm-profile.test.ts` with a `describe` block for
`loadCurrentFirmProfile`, using the same supabase mocking the file already uses for
`loadFirmProfile` and `saveFirmProfile`. Cover:

- A signed-in user: `auth.getUser` resolves `{ data: { user: { id: 'u1' } }, error: null }` and the
  profile row query resolves a row whose `firm_name` is `'Test Firm Alpha Law Offices'`; the
  function resolves a `FirmProfile` whose `firmName` is that string.
- No session: `auth.getUser` resolves `{ data: { user: null }, error: null }`; the function resolves
  `null` and the profile row query is never called.
- An auth error: `auth.getUser` resolves `{ data: null, error: { message: 'boom' } }`; the function
  resolves `null`.
- A thrown rejection: `auth.getUser` rejects; the function resolves `null` and does not reject,
  asserted with `await expect(loadCurrentFirmProfile()).resolves.toBeNull()`.
