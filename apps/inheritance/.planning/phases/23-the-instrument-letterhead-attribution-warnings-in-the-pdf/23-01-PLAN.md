<objective>
Give the firm profile a Roll of Attorneys number of its own, so the attorney attribution block
built in plan 23-04 can print five separately-sourced items rather than four.

Purpose: ROADMAP Phase 23 success criterion 2 and requirement INST-02 name five items — name, Roll
of Attorneys number, IBP number, PTR number and MCLE compliance. `23-RESEARCH.md` §2 measured the
store and it holds four: `counsel_name`, `ibp_roll_no`, `ptr_no`, `mcle_compliance_no`. There is no
`roll_of_attorneys_no` column anywhere in the tree. The existing `ibp_roll_no` is labelled
"IBP Roll No." in the settings form and in the PDF header, so re-pointing it at a different meaning
would change what an already-stored value denotes without anyone re-entering it, and printing one
stored number under two labels would state the same fact twice while claiming it is two facts.

Output: migration `016`, the widened `FirmProfile` type with both row mappers and the upsert
updated, and one more input on the settings form. This plan renders nothing into any PDF.
</objective>

<constraints>
- One new column only: `roll_of_attorneys_no TEXT`, nullable, no default, no CHECK constraint.
  Nothing else in `user_profiles` is altered, renamed, dropped or given a new meaning.
- `ibp_roll_no` keeps its existing label verbatim — `IBP Roll No.` — in
  `frontend/src/components/settings/FirmProfileForm.tsx`. This plan does not change that string.
- This is a storage decision about how many identifiers a signature block records. It is not a rule
  of succession or taxation, so `.planning/lawyer-decisions.json`, `.planning/LAWYER-AGENDA.md`,
  `.planning/BLOCKED-REQUIREMENTS.md` and everything under `specs/` are untouched.
- `frontend/supabase/seed.sql` is NOT modified by this plan. `scripts/check-seed-fixture.mjs`
  compares the seeded `input_json` byte for byte against a committed engine case and the seed's
  `user_profiles` insert names three columns only; leaving it alone keeps that gate green.
- No migration file that already exists is edited. The new file's name and number are fixed by this
  plan: `016_roll_of_attorneys.sql`, taking the next free number after the committed
  `015_shared_case_single_signature.sql`.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  runs the scoped commands below and makes no claim about the whole suite.
</constraints>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-23-01a | Elevation of privilege | `user_profiles` row-level security | accept | The existing policy `user_profiles_own` is `FOR ALL USING (auth.uid() = id) WITH CHECK (auth.uid() = id)` (migration `001_initial_schema.sql:111-112`). `ALTER TABLE ... ADD COLUMN` does not create, drop or alter a policy, so the new column inherits the same row scope as every sibling column. The migration contains no `CREATE POLICY`, no `DROP POLICY`, no `ALTER POLICY` and no `GRANT`. |
| T-23-01b | Tampering | `saveFirmProfile` upsert payload | mitigate | `saveFirmProfile` builds its payload key by key from an allow-list of `Partial<FirmProfile>` fields and never spreads caller input into the row. The new field is added as one more explicit `if (updates.rollOfAttorneysNo !== undefined)` branch, so an attacker-supplied extra key still cannot reach the `upsert`. |
| T-23-01c | Information disclosure | the new column's contents | accept | A Roll of Attorneys number is printed on every pleading a lawyer files and is published by the Supreme Court. It is not a secret, and it is scoped to the owning user by the unchanged policy above. |
| T-23-01-SC | Tampering | npm / cargo installs | mitigate | This plan installs nothing. `git diff -- frontend/package.json frontend/package-lock.json` is required to be empty by the verification block. |
</threat_model>
