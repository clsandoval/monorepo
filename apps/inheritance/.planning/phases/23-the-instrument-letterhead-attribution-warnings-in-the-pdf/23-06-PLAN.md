<objective>
Make the exported PDF print every engine warning the results screen shows, field for field, by
rendering both surfaces from the one model plan 23-02 built.

Purpose: ROADMAP Phase 23 success criterion 3 and requirement INST-03. `23-RESEARCH.md` §4 measured
the gap precisely, and it is narrower and more specific than the audit's wording: the PDF already
prints one entry per warning, so the count already matches, but it prints `[category] description`
under a heading `Warnings`, while the screen prints a heading `Manual Review Required`, a severity
word, the description and `Related heir: <name>`. Rendering the real document confirmed it —
the exported page reads `[RA_11642_RETROACTIVITY] A pre-2022 adoption decree …` with no severity
and without naming the heir `Adopted Child` the flag points at.

Output: both renderers consume `buildWarningLines`, the PDF adopts the screen's heading, the gate
that asserts the old heading is pointed at the new one, and parity is asserted field by field.
</objective>

<constraints>
- Neither renderer composes warning text of its own. Each maps `buildWarningLines(...)` to elements
  and prints the four fields it is handed. Neither reads `warning.category` directly, neither calls
  `getWarningSeverity`, and neither performs its own `shares.find`.
- The PDF's heading changes from `Warnings` to `WARNINGS_HEADING`, whose value is
  `Manual Review Required` — the words the screen already uses. `frontend/journey/pdf-structure.mjs`
  builds a derived required-section list containing the literal `'Warnings'` for the case where the
  engine emitted at least one warning; that literal becomes `'Manual Review Required'` in the same
  commit. This is a one-for-one retarget of an existing assertion at its renamed subject: the
  condition, the assertion and the failure marker `SECTION MISSING` are unchanged, and no assertion
  is removed.
- The PDF entry format is fixed by this plan and is not left to the executor. Each warning renders
  as one `<Text>` reading `[<severity>] [<category>] <description>` and, when `relatedHeirName` is
  non-null, a second `<Text>` reading `<RELATED_HEIR_LABEL> <relatedHeirName>`. The severity token
  is the model's own lowercase value, so a text gate can compare it against the model.
- The screen keeps its existing `data-testid` values `warnings-panel` and `warning-card-<index>`,
  its severity colour classes and its icons. Measured, those testids are consumed by exactly three
  files — `WarningsPanel.tsx` itself, `WarningsPanel.test.tsx` and `ResultsView.test.tsx` — and by
  no journey step record or rubric, so keeping them keeps two existing test files passing unedited.
- `output.warnings` on the seeded journey case is empty, so the screen renders the same empty
  `<div data-testid="warnings-panel" />` before and after this plan, and the `results-view`
  screenshot is pixel-unchanged by this plan. That is what keeps the journey step references
  withheld since Phase 16 from moving again.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  runs the scoped commands below and makes no claim about the whole suite.
</constraints>
