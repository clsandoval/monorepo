<objective>
Add the five remaining JRNY-02 steps to the journey registry, so signup, the email-verification
route, login, session persistence and logout each carry a passing screenshot-plus-rubric gate run
against seeded state.

Plan 11-03 authored `auth-signin`, which covers the login form. This plan adds `auth-signup`,
`auth-verify-nocode`, `auth-verify-badcode`, `auth-session-persisted` and `auth-signed-out`.

Every expectation below is a string read off the live application during research
(`11-RESEARCH.md` §4.3 and §4.5), not composed:

| URL | Landed at | Body, truncated | Console errors |
|---|---|---|---|
| `/auth?mode=signup` | `/auth?mode=signup&redirect=` | `Create Account  Create an account to get started.  Firm Name  Full Name  Email  Password  Confirm Password  Create Account  Already have an account? Sign in` | none |
| `/auth/callback` | `/auth?mode=signin&redirect=` | the sign-in card | none |
| `/auth/callback?code=not-a-real-code` | unchanged | `invalid request: both auth code and code verifier should be non-empty  Your confirmation link may have expired.  Return to sign in` | **one** |
| `/` with a seeded Alpha session | unchanged | `… alpha@example.test Sign Out Dashboard New Case RECENT CASES View all → Seeded Case Alpha draft` | none |

The `auth-verify-badcode` console error is the product behaving correctly — GoTrue answers 400 to a
code with no verifier — so that one step sets `allowConsoleErrors` true in its own record and its
rubric omits the `no_console_error` assertion. Every other step keeps both.

`11-RESEARCH.md` D-I records what this phase does **not** cover and why, measured rather than
assumed: `frontend/supabase/config.toml:209` sets `enable_confirmations = false`, so `signUp` returns
a session, `src/routes/auth.tsx:83` takes the auto-confirmed branch, and the "Check your email"
interstitial is unreachable in this stack. The happy-path confirmation exchange additionally needs a
PKCE `code_verifier` that only the initiating client holds — confirmed live by the exact error string
in the table above. That path is deferred, and this plan writes the deferral into
`frontend/journey/JOURNEY.md` so the next reader finds it rather than inferring it.

Output: five step records, five rubrics, five approved reference pairs, and one documented deferral.
</objective>

1. **A reference may be approved only after that step's rubric has passed.** Read
   `.journey-runs/<newest>/<stepId>/assertions.json` and confirm `"passed": true` and
   `"failedCount": 0` first. The rubric is the content check and the reference is the layout check;
   approving first freezes an unverified screen as the definition of correct.

2. **`maxDiffPixels` stays at the default `0` for every reference.** `REFERENCES.md` states that
   raising it to clear a red gate is prohibited, and names exactly two legitimate reasons to
   re-approve. Neither is "the gate is red".

3. **`allowConsoleErrors` is set on exactly one step, `auth-verify-badcode`.** Setting it anywhere
   else would silence a real defect. Setting it globally, or dropping the `no_console_error`
   assertion from the other four rubrics, is prohibited.

4. **No application source file is edited by this plan.** Every testid these rubrics address was added
   by plan 11-02. A rubric that cannot find its element is a finding about plan 11-02, and the correct
   output is a BLOCKED report with the real output.

5. **No rubric assertion may be deleted or loosened to make a step pass.** A `text_equals` may not
   become a `text_contains` to accommodate an unexpected string. If the screen says something other
   than what `11-RESEARCH.md` recorded, that difference is the finding.

   `git commit -a` are prohibited.
