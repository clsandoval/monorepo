<objective>
Prove COV-06 against the real local Supabase: a user in org A cannot read, write or enumerate org B's
cases, PDFs or shared links.

The requirement is one sentence and the trap inside it is the whole difficulty. Before plan 11-01, an
isolation assertion would have passed for entirely the wrong reason — every table returned HTTP 403
`42501` to every API role, so "org A sees none of org B's rows" was true because org A saw no rows at
all. `11-RESEARCH.md` §2 measured exactly that. `case_pdfs` had the same problem from the other
direction: it held zero rows, so an assertion that org A sees none of org B's PDFs held over an empty
table.

This is the failure mode PROJECT.md exists to prevent, so every assertion in this suite is written as
a **pair**: a positive control that must return rows, and the negative that must return none. A suite
where the positive control fails is a red suite, not a green one.

The measurements this plan encodes were all taken live during research, with grants applied and then
reverted:

```
A GET /rest/v1/organizations       → 200 [{"id":"a0…001","name":"Test Firm Alpha"}]
A GET /rest/v1/cases               → 200 [{"id":"a0…004","title":"Seeded Case Alpha"}]
B GET /rest/v1/cases               → 200 [{"id":"b0…004","title":"Seeded Case Beta"}]
A GET /rest/v1/cases?id=eq.b0…004  → 200 []
anon GET /rest/v1/cases            → 401 42501
anon rpc get_shared_case(alpha)    → 200, full row
anon rpc get_shared_case(beta)     → 200, []            (beta's share_enabled is false)
```

Output: one committed case table and one script that runs it, with a three-valued exit contract
matching `journey/seed-smoke.mjs`.
</objective>

<constraints>

1. **Every negative assertion is preceded by its positive control on the same table with the same
   verb.** A negative that runs without its control is prohibited, because a denial and an empty
   table are indistinguishable from the negative alone.

2. **No id is written as a literal.** Every uuid, email and token comes from
   `journey/seed.mjs:readFixtures()`. `frontend/supabase/fixtures.json` is the single source, and
   `scripts/check-seed-fixture.mjs` keeps it and `seed.sql` in agreement.

3. **The suite restores anything it writes.** The one mutating pair — a cross-tenant update and its
   same-table control — reads the original value first and writes it back afterwards, so two
   consecutive runs produce identical results. `journey/seed-smoke.mjs` already does this for
   `share_enabled`.

4. **The service-role key is read at runtime and never written to a file or printed.** It is used
   only to establish the fixture preconditions the suite asserts against, never to perform an
   isolation assertion — a service-role client bypasses RLS and would make every assertion vacuous.

5. **No migration, policy, grant or seed row is changed by this plan.** If an assertion fails, that
   is a finding about the schema and the correct output is a BLOCKED report with the real output, not
   an edit that makes the assertion pass.

6. **Do not register a gate in this plan.** Plan 11-08 performs the only permitted manifest append.

7. **Commit explicit paths only** with `bash scripts/safe-commit.sh`. `git add -A`, `git add .` and
   `git commit -a` are prohibited.

</constraints>

<interfaces>

### `frontend/journey/isolation-cases.json`

`{ "cases": [ … ] }`, each record with exactly these fields:

| Field | Type | Closed set / rule |
|---|---|---|
| `id` | string | unique, matches `^[a-z0-9-]+$` |
| `surface` | string | one of `cases`, `pdfs`, `share-links`, `org` |
| `actor` | string | one of `alpha`, `beta`, `anon` |
| `operation` | string | one of `read-own`, `read-other`, `update-own`, `update-other`, `insert-other`, `rpc-own-token`, `rpc-other-token` |
| `expect` | string | one of `rows`, `no-rows`, `denied` |

`rows` means at least one row came back with no error. `no-rows` means zero rows came back with no
error — the RLS outcome. `denied` means the request failed and the PostgREST error `code` was
`42501` — the grant outcome. Distinguishing `no-rows` from `denied` is what makes a failure say
whether RLS or a missing grant produced it.

The committed case table, fourteen records:

| `id` | `surface` | `actor` | `operation` | `expect` |
|---|---|---|---|---|
| `org-alpha-reads-own` | `org` | `alpha` | `read-own` | `rows` |
| `org-alpha-reads-beta` | `org` | `alpha` | `read-other` | `no-rows` |
| `cases-alpha-reads-own` | `cases` | `alpha` | `read-own` | `rows` |
| `cases-alpha-reads-beta` | `cases` | `alpha` | `read-other` | `no-rows` |
| `cases-beta-reads-own` | `cases` | `beta` | `read-own` | `rows` |
| `cases-anon-reads` | `cases` | `anon` | `read-own` | `denied` |
| `cases-alpha-updates-own` | `cases` | `alpha` | `update-own` | `rows` |
| `cases-alpha-updates-beta` | `cases` | `alpha` | `update-other` | `no-rows` |
| `pdfs-alpha-reads-own` | `pdfs` | `alpha` | `read-own` | `rows` |
| `pdfs-alpha-reads-beta` | `pdfs` | `alpha` | `read-other` | `no-rows` |
| `pdfs-alpha-inserts-beta` | `pdfs` | `alpha` | `insert-other` | `denied` |
| `share-anon-alpha-token` | `share-links` | `anon` | `rpc-own-token` | `rows` |
| `share-anon-beta-token` | `share-links` | `anon` | `rpc-other-token` | `no-rows` |
| `share-alpha-enumerates` | `share-links` | `alpha` | `read-other` | `no-rows` |

(Fourteen records. The table above is the whole set; `run` order is file order.)

### `frontend/journey/rls-isolation.mjs`

| Exit | Meaning | Marker printed |
|---|---|---|
| 0 | every case matched its `expect` | `ISOLATION ok cases=14 surfaces=4` |
| 1 | a case did not match | one `ISOLATION FAILED <id>: expected <expect>, got <observed>` line per failure, then `ISOLATION FAILED cases=14 failed=<k>` |
| 2 | the local stack is not running | `ISOLATION cannot-run: <reason>` |

On **both** the pass and the fail path the suite also prints `GATE-SKIPS total=14 skipped=0`, because
`scripts/check-gate-skips.mjs` reads that line out of the gate log regardless of outcome and treats a
missing line as a failure. It is not printed on the cannot-run path, where no case was evaluated.

Operation semantics, fixed here so none is invented:

| `operation` | What it does |
|---|---|
| `read-own` | select from the surface's table filtered to the actor's own fixture id; for `anon`, an unfiltered select |
| `read-other` | select filtered to the **other** tenant's fixture id; on `share-links` it selects `share_token` from `cases` filtered to the other tenant's case id |
| `update-own` | update `cases.status` on the actor's own case to its current value, returning the affected rows |
| `update-other` | the same update against the other tenant's case id |
| `insert-other` | insert a `case_pdfs` row whose `org_id` is the other tenant's org and whose `id` is `f0000000-0000-4000-8000-000000000001`; the suite deletes that id with the admin client before and after, so a partial previous run cannot make the case pass |
| `rpc-own-token` | `rpc('get_shared_case', { p_token: <alpha share_token> })` as `anon` |
| `rpc-other-token` | the same with Beta's share token, whose case has `share_enabled` false |

The suite prints a per-surface summary line before its verdict, so a red run says which of the three
surfaces COV-06 names is broken:

```
ISOLATION SURFACE org         pass=2 fail=0
ISOLATION SURFACE cases       pass=6 fail=0
ISOLATION SURFACE pdfs        pass=3 fail=0
ISOLATION SURFACE share-links pass=3 fail=0
```
