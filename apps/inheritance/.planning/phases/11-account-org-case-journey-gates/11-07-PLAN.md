<objective>
Verify JRNY-04: case intake, including the `localStorage` draft-recovery path, step by step.

`11-RESEARCH.md` §4.4 measured the seam that makes this cheap. `GuidedIntakeForm.tsx:39-44`
initialises its entire state from `localStorage['inheritance-intake-draft']`, and that state includes
`currentStep`. So every one of the seven intake steps is reachable directly by seeding a draft — no
new search param and no click-through are needed, which is exactly what JRNY-01 asks of a seeding
seam.

It also measured the trap. Seeding a **partial** draft crashes the application:

```
seed {"currentStep":2,"conflictCheck":{"outcome":"skipped"}}
 → BODY: "Something went wrong! Show Error"
 → TypeError: Cannot read properties of undefined (reading 'full_name')
```

Seeding a **complete** `IntakeFormState` with only `currentStep` varied works, with zero console
errors:

```
seed {…full initial state…, "currentStep":3}
 → BODY: "New Estate Case — Guided Intake Step 4 of 7 … Step 4: Family Composition"
```

So this plan commits eight complete draft fixtures rather than constructing drafts in code. The exact
initial object is transcribed in `11-RESEARCH.md` §8, captured from a live run of the built
application; it is copied, never re-derived.

`INTAKE_STEPS` (`src/types/intake.ts:154`) is the seven-name list in runtime order:
Conflict Check, Client Details, Decedent Info, Family Composition, Asset Summary, Settlement Track,
Review & Save. The file-header comment in `GuidedIntakeForm.tsx` puts Settlement Track fourth; the
runtime order above is what the application renders and is what the rubrics assert.

`/cases/new` requires a signed-in user with an organization — `beforeLoad` redirects to `/auth`
without one, and the component renders `Set up your firm first` for a user with no org — so every
step here uses the seeded Alpha session.

Output: eight complete draft fixtures, eight step records, eight rubrics and eight approved reference
pairs.
</objective>

### The rubrics

Each of `intake-step-0` through `intake-step-6` asserts the stepper position and the step name,
using the two strings the application renders and that research read off the live page —
`Step <n+1> of 7` and `Step <n+1>: <name>`:

| Rubric | `Step … of 7` | Step name |
|---|---|---|
| `intake-step-0` | `Step 1 of 7` | `Conflict Check` |
| `intake-step-1` | `Step 2 of 7` | `Client Details` |
| `intake-step-2` | `Step 3 of 7` | `Decedent Info` |
| `intake-step-3` | `Step 4 of 7` | `Family Composition` |
| `intake-step-4` | `Step 5 of 7` | `Asset Summary` |
| `intake-step-5` | `Step 6 of 7` | `Settlement Track` |
| `intake-step-6` | `Step 7 of 7` | `Review & Save` |

Each of the seven rubrics has exactly these five assertions, with `<n+1>` and `<name>` substituted:

```json
{
  "rubricId": "intake-step-<n>",
  "assertions": [
    { "id": "form",         "kind": "element_visible", "selector": "[data-testid=\"guided-intake-form\"]" },
    { "id": "position",     "kind": "text_contains",   "selector": "[data-testid=\"guided-intake-form\"]", "expect": "Step <n+1> of 7" },
    { "id": "step-name",    "kind": "text_contains",   "selector": "[data-testid=\"guided-intake-form\"]", "expect": "Step <n+1>: <name>" },
    { "id": "no-crash",     "kind": "text_absent",     "selector": "body", "expect": "Something went wrong!" },
    { "id": "clean-console","kind": "no_console_error" }
  ]
}
```

The `no-crash` assertion is present on every intake rubric on purpose: the measured failure mode for
this screen is the error boundary, and a rubric that only checked the stepper would pass on a page
that had already crashed if the crash text happened to contain the stepper string.

`intake-draft-recovered.json` is the eighth rubric and asserts content rather than position:

```json
{
  "rubricId": "intake-draft-recovered",
  "assertions": [
    { "id": "form",          "kind": "element_visible",  "selector": "[data-testid=\"guided-intake-form\"]" },
    { "id": "position",      "kind": "text_contains",    "selector": "[data-testid=\"guided-intake-form\"]", "expect": "Step 2 of 7" },
    { "id": "recovered-name","kind": "attribute_equals",  "selector": "#client-full-name", "attr": "value", "expect": "Recovered Client" },
    { "id": "clear-draft",   "kind": "text_contains",    "selector": "[data-testid=\"guided-intake-form\"]", "expect": "Clear Draft" },
    { "id": "no-crash",      "kind": "text_absent",      "selector": "body", "expect": "Something went wrong!" },
    { "id": "clean-console", "kind": "no_console_error" }
  ]
}
```

Two selector facts this rubric depends on, each of which task 1 verifies against the source before
the rubric is written: `guided-intake-form` is the testid on `GuidedIntakeForm`'s outer container,
and `client-full-name` is the id of the client full-name input in `ClientDetailsStep.tsx`. When
either differs in the source, the plan's rule is to use the value in the source and record the
substitution in the plan summary — the source is the fact, this table is the transcription.
