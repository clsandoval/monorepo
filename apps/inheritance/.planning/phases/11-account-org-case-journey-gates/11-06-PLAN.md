<objective>
Verify JRNY-03: org creation and invite acceptance, each with a passing screenshot-plus-rubric gate
run against seeded state.

Both journeys mutate the database, which is what makes them different from every step in plan 11-05.
Creating an organization inserts an `organizations` row and an `organization_members` row; accepting
an invitation inserts a membership and flips the invitation's `status` to `accepted`. A second run
would then see a user who already has an org and an invitation that is no longer pending, and both
screens would render something else. So each mutating step declares a **reset** that returns the
fixture to its seeded state before the step runs, and the reset is named in the step record rather
than hidden inside the runner.

The org-less user this needs does not exist in the pre-Phase-11 fixture — both seeded users already
administer an organization. Plan 11-01 added a third, `orphan@example.test`
(`c0000000-0000-4000-8000-000000000002`), with no `organizations` row and no `organization_members`
row, plus a `pending` invitation to Alpha's org
(`c0000000-0000-4000-8000-000000000003`, token `c0000000-0000-4000-8000-000000000004`).
`11-RESEARCH.md` §9 records why: `/onboarding` redirects away for a user who already has an
organization, so a user without one is the only way to reach its first screen.

Two measured facts shape the step list. `/onboarding` visited anonymously redirects to
`/auth?mode=signin&redirect=` — so every onboarding step needs the seeded Orphan session. And
`/invite/<a token the database refuses>` landed on `/settings/team` before plan 11-02 corrected it,
which is the defect `org-invite-rejected` exists to hold in place.

Alpha's `seat_limit` is 5 against 1 existing member, and `accept_invitation` matches on
`token`, `status = 'pending'`, the caller's own `email`, and `expires_at > NOW()`, so the acceptance
succeeds and the refusal is a genuine refusal rather than a seat-limit artefact.

Output: two named resets, five step records, five rubrics and five approved reference pairs.
</objective>

### Two named resets, added to `RESETS` in `frontend/journey/resets.mjs`

| Name | Body |
|---|---|
| `orphan-no-org` | with the admin client, delete every `organization_members` row whose `user_id` is `fixtures.orphan.user_id`, then delete every `organizations` row whose `id` is not `fixtures.orgs.alpha.org_id` and not `fixtures.orgs.beta.org_id` |
| `orphan-invitation-pending` | runs `orphan-no-org` first, then updates the `organization_invitations` row whose `id` is `fixtures.orphan.invitation_id`, setting `status` to `pending` and `accepted_at` to `null` and `expires_at` to `now() + 7 days` |

`orphan-no-org` deletes organizations by exclusion rather than by id because the onboarding step
creates one whose id the runner did not choose. Restricting the delete to organizations that are not
one of the two seeded ones keeps it from touching a developer's own rows while still converging.
