<objective>
Turn the WASM boundary's failure mode from an opaque thrown string into a typed, inspectable error.

Purpose: `engine/src/wasm.rs` is 12 lines and every failure path returns
`JsValue::from_str(&format!(...))` of an ad-hoc sentence. On the JavaScript side,
`frontend/src/wasm/bridge.ts` does `JSON.stringify` → `compute_json` → `JSON.parse` with no
try/catch and no type, so a `serde` rejection arrives at the calling route component as a bare
string with no way to tell an unparseable input apart from a corrupt output. `ROADMAP` Phase 5
criterion 4 requires a structured validation error observed in a frontend test.

The engine's `serde` deserializer stays the single validator. No Zod pre-flight is added in front of
it: `EngineInputSchema` already exists and is used by `computeMock`, and running two validators over
the same payload is the duplicate-rule pattern ROADMAP Phase 9 exists to delete.

Checked before writing this plan: no committed frontend test asserts on the *text* of an engine
error. `wasm-live.test.ts:209` uses `rejects.toThrow()` with no matcher and
`conformance.test.ts:468` and `:493` use `toThrow()` with no matcher, so changing the payload shape
cannot break them.

`frontend/src/wasm/bridge.ts` is also edited by ROADMAP Phase 9, which deletes `predictScenario()`
and `computeMock()` from it. This plan touches only `computeWasm`, `compute`, and the new exported
error class, so that deletion stays clean.

Output: a JSON error payload from `compute_json`, an `EngineError` class thrown by `computeWasm`, and
a new frontend test file that observes all three kinds.
</objective>

  <action>
Rewrite the three error paths in `engine/src/wasm.rs` so each rejects with a JSON document rather
than a sentence. Keep the signature `pub fn compute_json(input: &str) -> Result<String, JsValue>` and
keep `JsValue::from_str` as the rejection mechanism.

Add a private helper `fn engine_error(kind: &str, message: &str, detail: &str) -> JsValue` that
builds the payload with `serde_json::json!` and returns `JsValue::from_str(&payload.to_string())`.
The payload shape is exactly:

```
{"error":{"kind":"<kind>","message":"<message>","detail":"<detail>"}}
```

Three call sites, with these exact `kind` and `message` values:

| Failure | `kind` | `message` | `detail` |
|---|---|---|---|
| `serde_json::from_str` rejects the input | `invalid_input` | `The engine input could not be parsed.` | the `serde` error rendered with `to_string()` |
| `run_pipeline_checked` returns `Err(defects)` | `output_check` | `The computed distribution failed the engine output check.` | the defects rendered with their `Display` impl and joined by `"; "` |
| `serde_json::to_string` rejects the output | `serialize` | `The engine output could not be serialised.` | the `serde` error rendered with `to_string()` |

`message` is fixed text a user can read; `detail` is the engine's own diagnostic and may be any
length. Both are always present, and `kind` is always one of exactly those three strings, so the
JavaScript side can switch on it without string matching.

Plan 05-05 already switched this file to `run_pipeline_checked` and used the prefix
`Engine output check failed: `. That prefix is replaced by the structured payload; read
`05-05-SUMMARY.md` for the exact defect `Display` text so the joined detail stays faithful.

`serde_json` is already a dependency of the crate and `json!` is available through it; add
`use serde_json::json;` if the macro is not already in scope. Add no crate.

Then rebuild the WebAssembly artifact with `bash engine/build-wasm.sh` so the frontend exercises the
new payload. That script verifies existence, a 100 KB size floor and the WebAssembly magic number, so
its exit code is real proof the binary landed.

  <files>frontend/src/wasm/bridge.ts, frontend/src/wasm/__tests__/wasm-errors.test.ts</files>
  <read_first>frontend/src/wasm/bridge.ts, engine/src/wasm.rs, frontend/src/wasm/__tests__/wasm-live.test.ts, frontend/src/wasm/__tests__/conformance.test.ts</read_first>
  <action>
**In `frontend/src/wasm/bridge.ts`,** add one exported error class and wrap the boundary call.

`export type EngineErrorKind = "invalid_input" | "output_check" | "serialize" | "unknown";`

`export class EngineError extends Error` with a constructor taking `kind: EngineErrorKind`,
`message: string` and `detail: string`, calling `super(message)`, setting `this.name = "EngineError"`
and assigning `this.kind` and `this.detail` as public readonly fields. Include
`Object.setPrototypeOf(this, EngineError.prototype);` so `instanceof` works after the TypeScript
down-level emit, which is required because `frontend/tsconfig.json` compiles a class extending a
built-in.

Add `export function parseEngineError(thrown: unknown): EngineError`. It converts the value
`compute_json` rejected with:

1. Derive a candidate string: the value itself when `typeof thrown === "string"`, otherwise
   `thrown instanceof Error ? thrown.message : String(thrown)`.
2. Attempt `JSON.parse` on it inside a `try`. When the parse succeeds and the result has an `error`
   object with a string `kind` that is one of the three engine kinds, return
   `new EngineError(kind, error.message, error.detail)`.
3. In every other case return `new EngineError("unknown", "The engine failed.", candidate)`. The
   `unknown` kind exists so a WASM trap or a future payload change still produces an `EngineError`
   rather than an unhandled value.

Rewrite `computeWasm` to:

```
await ensureWasmInitialized();
let resultJson: string;
try { resultJson = compute_json(JSON.stringify(input)); }
catch (thrown) { throw parseEngineError(thrown); }
return JSON.parse(resultJson) as EngineOutput;
```

Leave `compute` as the one-line delegation to `computeWasm` it already is. Change nothing else in the
file — constraint 6 lists the functions Phase 9 will delete and this plan must not disturb.
