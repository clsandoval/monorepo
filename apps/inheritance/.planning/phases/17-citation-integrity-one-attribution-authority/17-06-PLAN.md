<threat_model>
This plan edits the file that decides which checks run. `gates.manifest.json` is marked
OWNER-OWNED in its own `$comment`, and the single worst outcome available here is a manifest edit
that quietly reduces enforcement — a command string swapped for a lenient one, a `blocking` flipped,
a gate dropped while the lock is edited to match.

Three structural defences make that detectable rather than trusted. `check-gate-manifest.mjs` compares
the manifest against the lock on every run and raises `GATE REMOVED`, `GATE COMMAND CHANGED` and
`GATE WEAKENED` as separate markers, and it is itself G5 at order 1 — the first thing the suite runs.
The script has no flag that rewrites either file. And Task 4's verification diffs the manifest against
its previous revision and asserts that the only changes are the appended G14 object and incremented
`order` integers, so a change to any other field is caught by the plan itself rather than only by the
gate.

The second hazard is a documentation edit that overstates what shipped. This phase does not produce a
green suite, and a `RESUME.md` reading `ALL GATES PASSED (33/33)` is a template claim about what a
green run prints, not an assertion that this branch produced one. Task 3 requires the adjacent prose
to say plainly that the suite exits 1 at G3 on two owner decisions, so the number and the truth sit
next to each other.
</threat_model>
