<objective>
Close three requirements at once against a single captured document: PDF-01 (every required section
present in the extracted text), PDF-02 (every peso figure matches engine output exactly), and PDF-03
(article citations and a per-heir narrative for every heir).

They share a gate because they share a capture. Splitting them would mean three application builds and
three browser sessions to inspect three views of the same bytes, and `13-RESEARCH.md` §10 records why
a gate that reuses another gate's artefact is worse: it acquires an order dependency and a silent
failure mode when the producing gate is skipped.

The money comparison follows the discipline `journey/money-parity.mjs` established and that
`.planning/STATE.md` records for Phase 12: the expected value is computed, never stored. The run resets
the Alpha case, asks the compiled engine directly, makes the product compute and export in a real
browser, then compares what the document actually says. Nothing here reads a committed expected
figure, and `scripts/check-seed-fixture.mjs` already rejects a seeded engine result with
`SEED WRITES OUTPUT`.

`13-RESEARCH.md` §3 measured why the section list cannot be a committed list of eight names:
`WarningsSection` returns `null` when the engine emits no warning, and the seeded case emits none,
while `NarrativesSection` returns `null` when there are no narratives, and the seeded case has four.
The list is therefore derived from the engine output of the same run.

Output: one dependency-free check with four named verdict families.
</objective>

<constraints>

1. **No expected peso figure is committed anywhere.** Not in this script, not in a JSON file, not in a
   comment. Every expected amount is produced by `computeEngineOutput` during the run.

2. **All money comparison is `BigInt`.** `Money.centavos` is `number | string` on the TypeScript side
   precisely because a large estate exceeds `Number.MAX_SAFE_INTEGER`. `Number()` appears nowhere in a
   comparison path.

3. **The gate formats no money and parses instead.** It converts the PDF's printed token back to
   centavos, exactly as `journey/money-parity.mjs` does for the screen. Writing a second formatter
   would create the duplicate money implementation EXT-02 forbids and would make the gate agree with
   itself rather than with the product.

4. **No tolerance, rounding allowance or epsilon exists anywhere in the script.** The engine converts
   to centavos exactly once, in `step10_finalize.rs`, with largest-remainder distribution. A gate that
   allowed a centavo of slack would hide exactly the defect it exists to find.

5. **The comparison runs in both directions.** Every engine amount must appear in the document, and
   every amount the document prints must be one the engine produced. A one-directional check passes a
   PDF that invented an extra line.

6. **Citations are asserted present and matching the engine's own `legal_basis` entries — never
   correct.** Whether `Art. 996` is the right article for this family is a point of Philippine law and
   is not decided here, by this gate or by anything in this plan.

7. **The exit contract is the project's three-valued one.** A stopped stack, a failed build, a missing
   browser, a missing PDF tool or a capture that produced no PDF is exit `2` with the
   `PDF STRUCTURE CANNOT RUN: ` prefix.

8. **`GATE-SKIPS total=<n> skipped=<n>` is printed on stdout on both the pass and the fail path.**

9. **No application source file, no test, no rubric, no step record and no seed file is edited.** Plan
   `13-01` fixed the currency token and plan `13-03` added the export hook.

10. **Commit explicit paths only** with `bash scripts/safe-commit.sh -m "<message>" <path> ...`.
    `git add -A`, `git add .` and `git commit -a` are prohibited.

</constraints>

<interfaces>

### `frontend/journey/pdf-structure.mjs`

Run from `frontend/`. No arguments. Calls `captureExportedPdf()` from `./pdf-capture.mjs` once, then
`extractPdfText(pdfBuffer)` from `./pdf.mjs`, and normalises the extracted text by replacing every run
of whitespace with a single space before any containment test.

#### The derived required-section list

Built from `expected`, the engine output returned by the capture:

| Section marker string | Required when |
|---|---|
| `Estate of <input.decedent.name>` | always |
| `Date of Death: <input.decedent.date_of_death>` | always |
| `Report Generated: 2026-06-15` | always — the fixed clock plan `13-03` installs |
| `Succession Type:` | always |
| `Net Distributable Estate:` | always |
| `Distribution of Shares` | always |
| `Heir` `Relationship` `Mode` `Net Share` | always — the four table column headings |
| `Per-Heir Breakdown` | always |
| `Gross Entitlement:` | always |
| `Net From Estate:` | always |
| `Computation Log` | always |
| `Final Scenario: <expected.computation_log.final_scenario>` | always |
| `Disclaimer` | always |
| `informational purposes` | always |
| `Heir Narratives` | when `expected.narratives.length > 0` |
| `Warnings` | when `expected.warnings.length > 0` |

The two conditional rows are what `13-RESEARCH.md` section 3 measured: the seeded case has four
narratives and zero warnings, so the Warnings heading is legitimately absent and asserting it would be
a false failure.

`FirmHeaderSection` is deliberately **not** on the list. `ActionsBar.tsx:49` calls
`downloadPDF(input, output, null)`, so no PDF a user can obtain carries a firm header. Asserting one
would assert a section the product never renders.

#### `parsePdfPesoText(text) -> BigInt`

The inverse of `formatPesoPdf` from `src/components/pdf/pdf-text.ts`, which plan `13-01` created:
`PHP ` followed by thousands-separated pesos and, only when the centavo remainder is non-zero, `.` and
exactly two digits.

- Strip the leading `PHP ` and every `,`.
- When a `.` remains, its fractional part must be exactly two digits; otherwise throw
  `PESO UNPARSEABLE: <the original text>`.
- Return `BigInt(pesoPart) * 100n + BigInt(centPart)` with `centPart` defaulting to `00`.
- Any leftover non-digit character throws the same error.

#### The four verdict families

| Marker | Fails when |
|---|---|
| `SECTION MISSING` | a required-section string from the derived list is absent from the normalised text; the message names the string |
| `PDF AMOUNT UNEXPECTED` | a `PHP <amount>` token found in the document parses to a centavo value that is in neither expected set below, or does not parse at all |
| `PDF AMOUNT MISSING` | an amount the engine produced does not appear in the document |
| `HEIR EVIDENCE MISSING` | for a heir the engine awarded a positive `net_from_estate`, the document lacks the heir's name, lacks every one of that heir's `legal_basis` entries, or lacks a narrative for that heir |

#### The two expected amount sets

Both are built from `expected` and `input` during the run:

1. **The structured set.** For every entry in `expected.per_heir_shares`, the centavo values of
   `from_legitime`, `from_free_portion`, `from_intestate`, `gross_entitlement`, `donations_imputed`
   and `net_from_estate`, dropping zeros because `PerHeirBreakdownSection` suppresses a zero
   component. Plus `input.net_distributable_estate.centavos`.
2. **The narrative set.** Every amount appearing inside `expected.narratives[].text`, found by matching
   the peso sign followed by digits, commas and an optional two-digit fraction, and converted with the
   same parsing rule. The engine writes those strings, so this set is engine-derived too — plan
   `13-01`'s `toPdfSafeText` is what turns them into `PHP ` tokens on the page.

`PDF AMOUNT MISSING` is checked against the structured set only, because a narrative amount is prose
the engine may phrase in whole pesos while the table prints centavos, and requiring both directions on
prose would assert the engine's wording rather than its arithmetic.

`PDF AMOUNT UNEXPECTED` is checked against the union of both sets. That direction is what catches a
figure the PDF invented.

#### `HEIR EVIDENCE MISSING`, precisely

For each `share` in `expected.per_heir_shares` whose `net_from_estate` centavos exceed zero:

- the normalised text contains `share.heir_name`
- for at least one entry `b` of `share.legal_basis`, the normalised text contains `b`
- the normalised text contains the corresponding `expected.narratives` entry's `heir_name`, and the
  substring `Heir Narratives` occurs at an earlier index than that heir's last occurrence, so a
  narrative section that rendered no bodies fails

Each failure names the heir id and which of the three pieces of evidence was absent.

Output:

- one line per failure: `<marker> — <detail naming the string, the heir or both integers>`
- always, on stdout: `GATE-SKIPS total=4 skipped=0`
- pass path: `PDF STRUCTURE PASS sections=<n> amounts=<n> heirs=<n>` and exit `0`
- fail path: `PDF STRUCTURE FAIL checks=4 failed=<k>` and exit `1`

### The three observed failures

| Marker | Injection, against a scratch edit restored afterwards |
|---|---|
| `SECTION MISSING` | in `frontend/src/components/pdf/EstatePDF.tsx`, remove the `<DisclaimerSection />` element; rebuild; run |
| `PDF AMOUNT UNEXPECTED` | in `frontend/src/components/pdf/DistributionTableSection.tsx`, render `formatPesoPdf(BigInt(share.net_from_estate.centavos) + 1n)` in the amount cell; rebuild; run |
| `HEIR EVIDENCE MISSING` | in `frontend/src/components/pdf/PerHeirBreakdownSection.tsx`, render only the first entry of `share.legal_basis` and drop the heir name line; rebuild; run |

The second injection is the load-bearing one: a one-centavo change must turn the run red, and it also
demonstrates `PDF AMOUNT MISSING` firing for the original value. Each injection is restored with
`git checkout --` and the check re-run green before the plan commits.
