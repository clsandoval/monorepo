<objective>
EXT-06 asks for a documented procedure for adding a **new** legal rule: article, vector,
implementation, gate.

`.planning/LEGAL-CORRECTION-WORKFLOW.md` already documents the neighbouring procedure — correcting an
**existing** rule after a lawyer says an output is wrong — in five fixed steps. Its own closing
paragraph reserves this one:

> `EXT-06` in Phase 15 covers adding a **brand-new** legal rule — article → vector → implementation →
> gate. This document covers **correcting an existing one**. They are different procedures and should
> not be conflated.

So the separation is a decision the repository already recorded. This plan writes the second
document, `.planning/NEW-LEGAL-RULE.md`, in the same five-step shape, plugged into the traceability
machinery Phase 14 built: the `// LEGAL-VECTOR: Art. NNN` marker, `engine/legal-rules.json`, the
shrink-only `engine/legal-traceability.lock`, and gate **G28**.

The load-bearing design decision: a document nobody runs decays. The check this plan adds does not
merely confirm the five headings exist — it re-resolves the document's **worked example** against the
tree on every gate run. The example names one real article, one real test file and one real test
function; if that function is renamed, moved, or loses its marker, the procedure goes red and says
so. That is the same anchoring discipline Phase 4 adopted for lawyer decisions after measuring that
later phases rewrite the exact files a registry points at.
</objective>
