<objective>
Make the ₱5,000,000 the engine already applied readable by a typed consumer.

`21-RESEARCH.md` §1.4 measured the root cause of the audit's Item-35A finding, and it is a type rather
than a display bug. `computeSpecialDeductions` returns `SpecialDeductionsResultExtended`, which carries
`standardDeduction` and `ra4917`. `EstateTaxFullOutput.specialDeductions` is declared as the narrower
`SpecialDeductionsResult`, which carries neither. A real engine run proves both keys survive at runtime
by object shorthand:

```
SPECIAL_DEDUCTIONS_OBJECT {"item37a_family_home":0,"item37b_funeral_expenses":0,
                           "item37c_judicial_admin_expenses":0,"item37d_medical_expenses":0,
                           "total":500000000,"standardDeduction":500000000,"ra4917":0}
HAS_standardDeduction_KEY true
HAS_ra4917_KEY true
```

so `specialDeductions.total` is `500000000` centavos while the four named fields sum to `0`. Any display
reading only the named fields must show a shortfall of exactly ₱5,000,000, and that is what
`Form1801View` does today.

This plan widens the declared type and repairs the one construction site the compiler will name. It is
deliberately the whole of wave 1: nothing else in this phase can be written correctly until a typed
consumer can read the standard deduction.
</objective>

<constraints>
- No arithmetic changes. `specialDeductions.total` already includes both values (`special-deductions.ts:168`),
  `netEstate` already subtracts that total (`pipeline.ts:485`), and no tax figure may move. The engine
  regression control for this plan is that every existing estate-tax test passes byte-identically.
- The two fields are declared as required `number`, never `number | undefined` and never optional. The
  compiler naming an unconverted construction site is the point of the change, not an obstacle to it.
- `SpecialDeductionsResultExtended` in `special-deductions.ts` is not deleted and not renamed. It stays
  as the return type of `computeSpecialDeductions`; after this plan it is structurally identical to
  `SpecialDeductionsResult`, and that redundancy is recorded in the type comment rather than resolved,
  because deleting an exported symbol has importers this plan has not enumerated.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan runs
  the scoped commands below and makes no claim about the whole suite.
</constraints>

<threat_model>
A pure type widening plus one object literal gaining two zero-valued keys. No input, no network call, no
storage access, no authorisation decision, no user-supplied string.

The single hazard is **a silent semantic change to persisted data**. `cases.tax_output_json` holds
`EstateTaxFullOutput` rows written before this plan. Those rows already contain both keys, because the
real path has always written them by shorthand — proven by the probe above, which is a real run of the
shipped code. So a re-read of an old row still satisfies the widened type. The one shape that does not
is a row written by `makeErrorOutput`, whose literal omits them; task 2 fixes the producer, and a
historical error row read back would surface as `undefined` at a property access rather than as a wrong
number. Task 3 asserts the error path emits both keys as `0` so no new row can have that shape.

Severity: low. Recorded because "widening a type is safe" is exactly the assumption under which a
persisted-shape mismatch ships.
</threat_model>
