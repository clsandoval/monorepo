<objective>
Build the one Form 1801 line array that the screen, the PDF and the CSV all render.

`21-RESEARCH.md` §6 records the architectural decision and why it is not three renderers reading the
output object: three independent mappings are three chances to reproduce the Item-35A defect, and only
one gate hoping to catch all of them. With one line model the three surfaces cannot disagree about
which rows exist or what they are called, and the gate is left verifying rendering fidelity — a much
smaller property.

The module lives inside the engine package because the authority strings are engine data. Putting them
in `components/` would make a display layer the attribution authority, which is exactly what Phase 17
removed and gate `G14` now enforces.

It also carries the reconciliation invariant, which is roadmap criterion 1 made executable: the
ordinary rows must sum to `ordinaryDeductions.total` per column, and the special rows to
`specialDeductions.total`. Today the second fails by exactly `500000000` centavos.
</objective>

<constraints>
- Every authority literal is copied from `21-RESEARCH.md` §4.1, which transcribed each one from a
  heading already committed in `specs/estate-tax-engine-spec.md` at the line number recorded there.
  Two lines — funeral and judicial/administrative — have no NIRC section anywhere in the repository and
  carry a spec reference instead. That is the answer for those two lines, not a gap to be filled.
- No arithmetic. Every amount is read from `EstateTaxFullOutput`; the module performs no multiplication,
  no rate application and no subtraction other than the reconciliation differences it reports.
- The module does not mutate `EstateTaxFullOutput` and does not append to `output.warnings`. It returns
  its warnings alongside its lines, so `computeEstateTax` behaviour is byte-identical and no existing
  test changes.
- Engine field names are not renamed. `21-RESEARCH.md` §1.5 records that eight of them disagree with the
  spec's line letters; this module is the translation boundary and the renaming is out of scope.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan runs
  the scoped commands below and makes no claim about the whole suite.
</constraints>

<threat_model>
A pure function over an in-memory object. No input, no network call, no storage access, no
authorisation decision.

The hazard that matters is **a line silently disappearing**. Every consumer of this module renders what
it returns and nothing else, so a row dropped here is a row missing from the screen, the PDF and the CSV
at once — the Item-37A failure, industrialised. The defence is structural rather than behavioural: the
module exports a frozen array of every line id it can ever produce, and task 4 asserts the built array's
id set equals that constant exactly. A dropped row then fails a set comparison rather than passing an
"every row I built is correct" check vacuously.

The second hazard is **an authority string becoming a legal claim**. Every literal is a transcription of
a committed spec heading; a line whose authority is not in the §4.1 table is a line the plan did not
anticipate, and the correct response is BLOCKED, never an invented section.

Severity: low technically, high in consequence — this array is the content of a document a lawyer signs.
</threat_model>
