<objective>
Put the two exits on the screen, so a lawyer can reach them.

`21-04` and `21-05` built the writers. Until a control exists in the product, the audit's finding stands
unchanged — the grep for `react-pdf` across `src/components/tax/` still returns zero, and `21-07` has no
button to click. This plan is what turns two library functions into an exit.

It is deliberately its own wave. The gate in `21-07` obtains both artifacts the way a user obtains them,
by clicking the product's own control in a real browser, because a harness that renders the document for
itself proves the harness can call `@react-pdf/renderer` — not that the lazy import, the blob and the
download work. That is the decision `journey/pdf-capture.mjs` already records for the succession report.
</objective>

<constraints>
- The bar renders inside the Form 1801 tab of `TaxResultsPanel`, above the table, so both controls sit
  with the document they export.
- Both dates come from the route. `dateOfDeath` is `factSet.dateOfDeath`, which Phase 18 made the single
  keyed spine and gate `G34` protects; `generatedOn` is computed once in the route and passed down.
  Neither export module reads a clock.
- Failure is surfaced, never swallowed. A rejected export shows a `sonner` error toast, the pattern
  `$caseId.tax.tsx` already uses for `handleCompute`, and the button returns to its enabled state.
- The PDF button is disabled while its generation is in flight, because the lazy import is cold and takes
  seconds; the CSV button is not, because building a string is synchronous.
- No line, label, amount or authority is constructed here. This plan adds controls only.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan runs
  the scoped commands below and makes no claim about the whole suite.
</constraints>

<threat_model>
Two buttons that build a blob from data already in memory and hand it to the browser's download
machinery. No network call, no storage write, no authorisation decision.

The hazard is **an export of the wrong case**. `TaxResultsPanel` receives `output` as a prop and the
route holds one case at a time, so the risk is not cross-tenant; it is temporal. A user who edits the
wizard, does not recompute, and presses Export would receive a document built from the previous
computation. The defence is that both controls read the same `output` object the table renders, so the
document always matches what is on screen — and the screen is what the user is looking at when they press
the button. No separate compute is triggered.

The second hazard is **an unhandled promise rejection leaving the button permanently disabled**. The
in-flight flag is cleared in a `finally`, and task 3 asserts the button is enabled again after a rejected
generation.

Severity: low.
</threat_model>
