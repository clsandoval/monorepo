<objective>
Measure progress against the frozen manifest, so a narrowed scope shows up as reduced coverage rather than as a green run.

Purpose: LOOP-04 asks that progress be measured against the frozen gate manifest. The failure it guards against is subtle and is the one most likely to survive every other check in this phase: a run that legitimately passes everything it executed, while quietly executing less than the manifest requires. Exit code 0 with `ALL GATES PASSED` is exactly what that looks like from the outside. The only defense is to compute coverage from two independent sources — the manifest as the expectation, the run record as the observation — and to fail when the observation is a strict subset of the expectation on an otherwise-passing run.

The rule, decided in 02-RESEARCH.md section 4 so no executor has to decide it: fail with `SCOPE NARROWED` when the run's `outcome` is `pass` and any blocking manifest gate has status `not-run`. Do not fail on a halted or failed run, where later gates are legitimately unreached. Do not fail on ungated requirements, because 85 of the 93 v1 requirements are legitimately ungated today and will be until their phases land; failing there would make the loop unable to move at all.

Output: `scripts/gate-coverage.mjs`, three run-record fixtures, the closeout wired into the runner, and section 3 of `GATES.md`.
</objective>

  <action>
Create `scripts/gate-coverage.mjs`, a Node ESM script importing only `node:fs` and `node:path`. Resolve input paths relative to the script's own location so it works from any working directory.

Three flags, and no others:
- `--run <path>` — read the run record from `<path>` instead of `.gate-runs/latest.json`.
- `--manifest <path>` — read the manifest from `<path>` instead of `gates.manifest.json`. Diagnostic and fixture use only.
- `--json` — additionally print the computed coverage object as JSON on the last line, so a later phase can consume it without re-parsing the table. Phase 3 owns the published results format under GATE-08; this flag is the minimal hook, not that format.

**Report 1 — gate execution coverage.** Join the manifest's gates, in `order`, against the run record's `gates` array by `id`. Print a table with columns: id, order, blocking, name, status, exit code. A manifest gate absent from the record entirely has status `MISSING FROM RECORD`, which is treated identically to `not-run`. End the table with a line of the exact shape `GATE COVERAGE <executed>/<total>`, where `executed` counts gates whose status is `pass`, `fail` or `cannot-run` — that is, gates that were reached — and `total` is the manifest gate count.

Also detect and report `UNKNOWN GATE IN RECORD`: a gate id present in the run record but absent from the manifest. That means the runner executed something the frozen manifest does not describe, which is drift in the opposite direction and must be visible.

**Report 2 — requirement coverage.** Build the requirement id set from `.planning/REQUIREMENTS.md` by matching `\b[A-Z][A-Z0-9]*-[0-9]{2}\b`. For each id, list the manifest gates whose `requirements` array contains it, or `UNGATED` when none do. Print a compact list of the gated ids with their gate, then a single count line of the exact shape `REQUIREMENT COVERAGE <gated>/<total> gated`. Do not print all 93 rows; print the gated ones and the count, since the ungated list is the roadmap's remaining work rather than a defect.

**Enforcement**, in this exact order:

1. When the run record's `outcome` is `pass` and any **blocking** manifest gate has status `not-run` or `MISSING FROM RECORD`, print a line containing `SCOPE NARROWED` naming each such gate, and exit 1.
2. When any `UNKNOWN GATE IN RECORD` was detected, print it and exit 1.
3. When the run record is missing or unparseable, print a line containing `RUN RECORD UNREADABLE` and exit 1.
4. Otherwise exit 0, including when the run's `outcome` is `fail` or `cannot-run`. A halted run reached fewer gates by design; reporting that as a narrowing would punish the halt behavior that plan 02-04 exists to create.

Print the tables in every case, including the failing ones. The report is the product; the exit code is a consequence of it.

Success output ends with a line containing the literal string `COVERAGE OK`.

The script must never write to the manifest, the lock, or the run record.
  </action>
