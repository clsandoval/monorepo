<objective>
Make a stalled loop announce itself, so a month of unattended grinding cannot silently become a month of repeating the same failure.

Purpose: LOOP-06 requires that a stalled or repeatedly-failing loop surface without the owner having to poll for it. PROJECT.md is explicit that a month of slow autonomous implementation is acceptable but a stalled loop is not, and the owner's attention is scarce and non-recurring. The realistic failure is not a crash — it is a loop that keeps running, keeps producing output, and keeps hitting the same wall.

The mechanism, decided in 02-RESEARCH.md section 7 so no executor has to decide it: every gate run appends one line to a bounded committed history, and a committed one-screen status file is regenerated from that history with a state banner. No push channel is invented, because none is configured in this repo and inventing one would be an ungrounded decision. The signal is the committed file plus the CI check that already fails on any nonzero runner exit.

The stall rule is fixed, not discovered: three consecutive non-pass runs sharing one failure signature, or five consecutive non-pass runs regardless of signature.

The recorder runs from an EXIT trap, so it fires on the success path, the gate-failure path and the halt path alike. A recorder that only ran on success would record nothing about the situation it exists to detect.

Output: `scripts/loop-status.mjs`, `LOOP-STATUS.md`, `loop-history.jsonl`, three history fixtures, the trap wired into the runner, and closing sections of `GATES.md` and `README.md`.
</objective>

  <action>
Create `scripts/loop-status.mjs`, a Node ESM script importing only `node:fs` and `node:path`. Resolve paths relative to the script's own location.

Two subcommands, and no others.

**`record --run <path>`** — read a run record written by `scripts/ci-gates.sh`, then:

1. Append one line to `loop-history.jsonl` with exactly these keys: `ts` from the record's `ended_at`, `outcome`, `failure_signature`, `gates_run` counting gates whose status is `pass`, `fail` or `cannot-run`, `gates_total`, and `only` from the record.
2. Truncate the file to its most recent 200 lines, so churn is one line per run and the file stays bounded.
3. Recompute the state and rewrite `LOOP-STATUS.md`.
4. Print a line containing `LOOP STATUS <STATE>`.

Accept `--history <path>` and `--status <path>` overrides so fixtures can drive it without touching the real files.

**`check`** — recompute the state from `loop-history.jsonl` without writing anything. Print `LOOP STATUS <STATE>`. Exit 1 when the state is `STALLED`, otherwise exit 0. Accept the same `--history` override.

**State computation**, from the history's most recent entries, evaluated in this order:

1. `STALLED` — the most recent 3 entries all have `outcome` other than `pass` **and** share an identical `failure_signature`; or the most recent 5 entries all have `outcome` other than `pass` regardless of signature. Fewer entries than the window means the rule does not apply.
2. `BLOCKED` — the most recent entry has `outcome` `cannot-run`.
3. `RED` — the most recent entry has `outcome` `fail`.
4. `GREEN` — the most recent entry has `outcome` `pass`.
5. `UNKNOWN` — the history is empty.

Note the ordering consequence, which is intended: one passing run after a failing streak yields `GREEN`, because rule 1 requires the most recent entries to be non-pass. Recovery is immediate and does not require the streak to age out.

**`LOOP-STATUS.md` content**, generated and never hand-edited. State that in a comment at the top of the file. It contains, in this order:

1. A first heading line holding the state token verbatim. When the state is `STALLED` or `BLOCKED`, the same line also carries the literal string `NEEDS OWNER ATTENTION`.
2. A one-line summary: last run timestamp, outcome, and failure signature.
3. A per-gate table from the run record: id, name, status, exit code.
4. The consecutive non-pass streak length and the signature it is repeating, when the streak is nonzero.
5. A short "what to do" block keyed to the state: `GREEN` needs nothing; `RED` names the failing gate and points at `GATES.md`; `BLOCKED` points at the BLOCKED report template in `.planning/PLAN-STANDARD.md` section 3; `STALLED` states that the loop has repeated the same failure and that a human decision is now required.
6. A footer naming the history file, its current line count, and the 200-line cap.

Never write to `gates.manifest.json`, `gates.manifest.lock`, or any run record. `record` writes only `loop-history.jsonl` and `LOOP-STATUS.md`.
  </action>
