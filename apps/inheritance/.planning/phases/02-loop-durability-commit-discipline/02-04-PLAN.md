<objective>
Make the runner read the frozen manifest, and make "the gate could not run" a different answer from "the gate failed".

Purpose: LOOP-02 requires that a plan whose gates cannot run halts and reports rather than proceeding or redefining success. Today `scripts/ci-gates.sh` exits 1 both when `cargo test` fails and when `cargo` is missing. Those are opposite situations — one is information about the product, the other about the environment — and conflating them is exactly how a month-long loop quietly redefines success. LOOP-03 additionally needs the manifest to be more than a document: a gate that can be deleted from the runner while the manifest still lists it is not frozen at all.

Both are solved by the same restructure, decided in 02-RESEARCH.md sections 2 and 3. The runner stops hardcoding four gates and instead iterates `gates.manifest.json` in `order`, honoring each gate's `precondition`. Exit 0 means every gate ran and passed, exit 1 means a gate ran and failed, exit 2 means a gate could not run at all. Every path writes a run record that plans 02-05 and 02-06 consume.

This plan also performs the phase's own legitimate manifest growth: the three checks built in wave 1 are appended to the manifest and the lock as gates G5, G6 and G7, and reordered to run before the five-minute Rust, WASM and Vitest gates, so a tampered manifest is caught in seconds rather than after a full run.

Output: a manifest-driven `scripts/ci-gates.sh`, seven locked gates, `.gate-runs/latest.json`, an updated `.gitignore`, and sections of `GATES.md` and `README.md`.
</objective>

<task type="auto">
  <name>Task 2: Make the runner read the manifest and adopt the three-valued exit contract</name>
  <files>scripts/ci-gates.sh</files>
  <read_first>scripts/ci-gates.sh, gates.manifest.json, .planning/PLAN-STANDARD.md, .planning/phases/02-loop-durability-commit-discipline/02-RESEARCH.md</read_first>
  <action>
Rewrite `scripts/ci-gates.sh`. Keep its existing header comment block and extend it; the file stays the single command CI runs, so what CI runs and what a developer runs remain the same bytes.

**Manifest loading.** Resolve `APP_DIR` as today. Read `gates.manifest.json` with `node -e` and emit one tab-separated line per gate, sorted by `order`, with fields `id`, `command`, `precondition`, `blocking`. Iterate those lines. When the manifest is missing or does not parse, print `GATE CANNOT RUN: manifest` and `HALT: gates.manifest.json is missing or unparseable` and exit 2.

**Preflight.** Keep `require_tool` for `cargo`, `rustup`, `wasm-pack`, `node`, `npm`, and keep the `frontend/node_modules` check. Change every preflight failure to print `GATE CANNOT RUN: preflight`, then `HALT: <reason>`, then exit **2** instead of 1. A missing toolchain is not a product failure and must never be reported as one.

**Per-gate execution.** For each gate in `order`:

1. Print a banner naming the gate: id, ordinal position, total count, and name.
2. Evaluate the `precondition` with `bash -c` from `APP_DIR`. When it exits nonzero, record the gate as `cannot-run`, print `GATE CANNOT RUN: <id>` and `HALT: precondition failed — <precondition>`, and exit 2 immediately.
3. Run the gate: `set +e`, then `( cd "$APP_DIR" && bash -c "<command>" )`, then `rc=$?`, then `set -e`. Constraint 6 governs this: the code is captured and branched on explicitly, never swallowed.
4. When `rc` is 127, record `cannot-run`, print `GATE CANNOT RUN: <id>` and `HALT: command not found — <command>`, and exit 2. A command that does not exist did not run.
5. When `rc` is any other nonzero value, record `fail`, print `GATE FAILED: <id> (exit <rc>)`, and exit 1.
6. When `rc` is 0, record `pass` and continue.

**`--only <id>`.** Replace the numeric `--only <1-4>` with `--only <gate-id>`, validated against the ids present in the manifest. An unknown id prints an error listing the valid ids and exits 1. On success the final line is `GATE <id> PASSED (ran with --only <id>; this is NOT a full gate run)`, preserving the Phase 1 rule that a partial run never prints a whole-run success message. There remains no option that omits a gate from a full run.

**Final line.** On a complete successful run print `ALL GATES PASSED (<n>/<n>)` where `<n>` is the manifest gate count, so the number tracks the manifest rather than a hardcoded 4.

**Exit contract**, stated in the header comment as a table: 0 all gates ran and passed; 1 a gate ran and failed; 2 a gate could not run. Also state in the header that exit 2 is a halt: the operator reports BLOCKED per `.planning/PLAN-STANDARD.md` section 3 and does not edit a gate to make the halt go away.

Do not add a `--manifest` flag. The runner must always read the real manifest, so no invocation can point it at a weaker gate set.
  </action>

**Part A — the run record.** Add a bash `trap ... EXIT` to `scripts/ci-gates.sh` that writes `.gate-runs/latest.json` on every exit path: success, gate failure, and halt alike. A recorder that only runs on success records nothing about the situation it exists to detect.

Accumulate per-gate results in shell variables as the run proceeds, then serialize with `node -e` reading them from the environment, so no hand-rolled JSON escaping is needed. Create the `.gate-runs` directory when absent.

Record shape, exactly these keys:

- `schema` — the integer `1`.
- `started_at`, `ended_at` — ISO 8601 timestamps.
- `outcome` — one of `pass`, `fail`, `cannot-run`.
- `failure_signature` — the empty string when `outcome` is `pass`; `<gate_id>:<exit_code>` when `fail`; `CANNOT_RUN:<gate_id>` when a gate could not run; `PREFLIGHT:<reason>` when preflight halted.
- `manifest_version` — the manifest's `version`.
- `gates_total` — the manifest gate count.
- `only` — the `--only` id when the run was partial, otherwise the empty string.
- `gates` — an array in manifest `order`, one object per manifest gate with keys `id`, `status`, `exit_code`, `started_at`, `ended_at`. `status` is one of `pass`, `fail`, `cannot-run`, `not-run`. Gates after the aborting gate are `not-run` with `exit_code` `null`. Every manifest gate appears, including ones that never started — that absence-as-data is what plan 02-05 turns into a coverage report.

**Part B — gitignore.** Create `.gitignore` at the app root containing `.gate-runs/` with a one-line comment explaining that per-run records are pure churn in a repo with a concurrent auto-committer. Do not modify `frontend/.gitignore`.

**Part C — fail-closed injection hooks.** Add four environment variables used only to exercise the exit contract. Each can turn a green run red and none can turn a red run green. The script must carry that sentence as a comment next to their handling, and must print `INJECTED FAILURE ACTIVE: <var>=<value>` when any is set.

- `GATES_INJECT_MISSING_TOOL=<tool>` — preflight treats that tool as absent.
- `GATES_INJECT_PRECONDITION_FAIL=<gate id>` — that gate's precondition is treated as failed.
- `GATES_INJECT_GATE_FAIL=<gate id>` — that gate's command is replaced with `exit 3`.
- `GATES_INJECT_NOT_FOUND=<gate id>` — that gate's command is replaced with `definitely-not-a-real-binary-xyz`.

**Part D — prove the contract.** Run each of the four injections plus a clean run, and record the exit code, the printed marker, and the resulting `failure_signature` from `.gate-runs/latest.json`. Expected:

| Invocation | Exit | Marker | `failure_signature` |
|---|---:|---|---|
| `bash scripts/ci-gates.sh` | 0 | `ALL GATES PASSED (7/7)` | `""` |
| `GATES_INJECT_MISSING_TOOL=cargo bash scripts/ci-gates.sh` | 2 | `GATE CANNOT RUN: preflight` | `PREFLIGHT:cargo` |
| `GATES_INJECT_PRECONDITION_FAIL=G6 bash scripts/ci-gates.sh` | 2 | `GATE CANNOT RUN: G6` | `CANNOT_RUN:G6` |
| `GATES_INJECT_NOT_FOUND=G6 bash scripts/ci-gates.sh` | 2 | `GATE CANNOT RUN: G6` | `CANNOT_RUN:G6` |
| `GATES_INJECT_GATE_FAIL=G6 bash scripts/ci-gates.sh` | 1 | `GATE FAILED: G6 (exit 3)` | `G6:3` |

The last two rows are the discrimination this plan exists to create: the same gate, one case exiting 2 because the command did not run and one case exiting 1 because it ran and failed.

After each injected run, confirm `.gate-runs/latest.json` exists and parses, proving the trap fired on the halt and failure paths as well as on success.
