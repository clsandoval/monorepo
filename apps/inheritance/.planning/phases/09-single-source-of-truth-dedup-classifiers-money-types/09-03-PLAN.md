<objective>
Make a peso unassignable to a centavo, and prove it with an instrument that fails when the property
is absent.

`frontend/src/types/index.ts:496-503` declares `pesosToCentavos(pesos: number): number` and
`centavosToPesos(centavos: number | string): number`. Both units are bare `number`, so nothing stops
a caller passing one where the other belongs — and `09-RESEARCH.md` §4.4 shows the two wizards store
money in *different* units, pesos in one and centavos in the other.

This plan introduces the two flavoured unit types, moves the converters onto them, routes the
succession wizard's only money control through them, and commits a negative type test that `tsc`
already runs as gate `G4`.

The technique was run end to end against this repository's own TypeScript 5.9.3 before being written
here; `09-RESEARCH.md` §4.2 records both the passing and the failing direction. Nothing below is a
guess about how the compiler behaves.

Output: one new type module, one new proof file, and the succession-wizard boundary typed.
</objective>

The exact technique, verified in this repo (`09-RESEARCH.md` §4.2):

```ts
type Flavor<T, F extends string> = T & { readonly __unit?: F };
```

The brand property is **optional**. That is the whole trick: numeric literals and plain `number`
remain assignable to both units, while `Pesos` and `Centavos` remain mutually unassignable because
`__unit?: "pesos"` and `__unit?: "centavos"` conflict.

Measured constraint from `frontend/tsconfig.json:25-32`: `include` is `["src"]` and `exclude` lists
`src/**/__tests__/**`, `src/**/*.test.ts(x)` and `src/**/*.spec.ts(x)`. A proof file named
`*.test.ts` or placed under `__tests__/` would never be compiled.
