<objective>
Make a journey failure inspectable after the fact.

JRNY-12: *"Every gate failure emits the screenshot, the diff, and the failing assertion as durable
artifacts."* The reason this is a requirement rather than a nicety is the executor model this project
targets. `PROJECT.md` fixes it: implementation is delegated to a deliberately cheap model running
unattended for a month. When a journey gate goes red at 3am, nobody is watching the terminal. If the
only record is scrollback, the failure is unreadable by the time anyone looks, and the loop's options
collapse to "re-run and hope" — which over a month becomes "ignore".

This plan writes those artifacts, and it writes them where the monorepo's concurrent auto-committer
cannot swallow them. That last point is concrete rather than theoretical: STATE.md records three
unrelated `fitness log` commits landing during unrelated sessions, and LOOP-05 exists specifically
because of it. A directory of PNGs that lands in a commit is churn at best and a leaked artifact at
worst, so `.journey-runs/` is gitignored, mirroring the reasoning the root `.gitignore` already gives
for `.gate-runs/`.

Output: one writer module, a gitignore entry, and a probe that induces a real failure and then finds
five files on disk.
</objective>

<constraints>

1. **Artifacts are never committed.** `frontend/.journey-runs/` is added to `frontend/.gitignore`.
   This mirrors the root `.gitignore`'s treatment of `.gate-runs/`, whose comment already states the
   reasoning: per-run detail, regenerated on every exit path, and a concurrent auto-committer runs on
   this monorepo.

2. **Write artifacts on failure, and write the screenshot on success too.** The screenshot is what
   `approve.mjs` reads when a reference is legitimately re-approved, and plan 10-03's `approve.mjs`
   sources from `<newest run>/<stepId>/actual.png`. A writer that only fired on failure would make
   approving a *passing* step impossible.

3. **Do not write into `frontend/journey/references/`.** Plan 10-03 constraint 3 reserves that path
   for `approve.mjs`. A writer that could touch it would let a gate rewrite its own expectation.

4. **Do not edit `browser.mjs`, `rubric.mjs`, `diff.mjs` or `approve.mjs`.** They belong to plans
   10-01, 10-02 and 10-03 and are read-only here.

5. **Do not register any gate.** Plan 10-06 owns the single permitted manifest append.

6. **Commit explicit paths only,** via `bash scripts/safe-commit.sh`. `git add -A`, `git add .` and
   `git commit -a` are prohibited.

</constraints>

<interfaces>

**Artifact layout**, fixed here because plan 10-03's `approve.mjs` already reads it and plan 10-06's
gate already reports it:

```
frontend/.journey-runs/<runStamp>/<stepId>/actual.png        always written
frontend/.journey-runs/<runStamp>/<stepId>/reference.png     written when a reference existed
frontend/.journey-runs/<runStamp>/<stepId>/diff.png          written when a pixel comparison ran
frontend/.journey-runs/<runStamp>/<stepId>/assertions.json   always written — the full RubricResult
frontend/.journey-runs/<runStamp>/<stepId>/FAILURE.txt       written only when the step failed
```

`<runStamp>` is `new Date().toISOString().replace(/[:.]/g, '-')`. Sorting these names descending
yields newest-first, which is exactly what `approve.mjs` relies on.

**Exports of `frontend/journey/artifacts.mjs`:**

| Export | Signature | Contract |
|---|---|---|
| `ARTIFACT_ROOT` | `string` | The absolute path of `frontend/.journey-runs` |
| `newRunStamp` | `() => string` | The timestamp form above |
| `writeStepArtifacts` | `({ runStamp, stepId, actualPng, referencePng, rubricResult, diffResult }) => string` | Creates the step directory, writes the files above, returns the directory path |

`FAILURE.txt` is plain text and must contain, in this order:

1. A first line listing the markers that fired, space-separated, drawn from plan 10-03's
   `DIFF_MARKERS` vocabulary — for example `RUBRIC FAILURE DIFF FAILURE`.
2. A `Step: <stepId>` line and a `Run: <runStamp>` line.
3. For a rubric failure, one line per failing assertion in the form
   `FAILED <id> kind=<kind> expected=<expected> actual=<actual>`.
4. For a diff failure, one line in the form
   `DIFF diffPixels=<n> maxDiffPixels=<n>`.
5. A closing line naming the absolute path of the step directory, so a reader can find the images
   without reconstructing the path.

A step is failed when `rubricResult.passed === false` or `diffResult.status === 'fail'`. When both are
false, both marker sets appear on line 1 — the distinction plan 10-03 built must survive into the
artifact.

</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| gate process → filesystem | The harness writes PNGs and text into the working tree; anything it writes into a tracked path can be picked up by the monorepo's concurrent auto-committer |
| failure record → future reader | The artifact is the only durable evidence of a 3am failure; an incomplete record silently narrows what a later session can diagnose |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-04 | Tampering | `frontend/.journey-runs/` | mitigate | The directory is gitignored, verified in Task 3 with `git check-ignore -v`, so a failing run's images cannot be absorbed into an unrelated commit |
| T-10-04b | Repudiation | `FAILURE.txt` | mitigate | The marker line preserves which mechanism failed, and per-assertion lines record `expected` and `actual`, so the record is diagnostic rather than a bare "failed" |
| T-10-04c | Information Disclosure | captured screenshots | accept | Journey screenshots depict seeded fixture state from `frontend/supabase/fixtures.json`, already committed to this repository. The gitignore also keeps them off any branch, so they stay local to the machine that ran the gate |
| T-10-04d | Denial of Service | unbounded artifact growth | mitigate | Task 2 caps retention at the 20 newest run directories, pruning older ones, so a month-long unattended loop cannot fill the disk with PNGs |
</threat_model>
