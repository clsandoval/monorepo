<objective>
Plan `16-02` removed the three screens and left the tree with compiler errors confined to four
files. This plan closes them: it deletes `frontend/src/lib/conflict-check.ts` outright, strips the
seven identifiers the cut orphaned from `frontend/src/types/intake.ts`, and repairs the readers in
`frontend/src/lib/intake.ts`, `frontend/src/components/intake/IntakeReviewStep.tsx` and
`frontend/src/types/index.ts`.

CUT-01 names "`frontend/src/lib/conflict-check.ts` plus the intake types those cuts orphaned". The
orphan set is not left to the executor to work out — research enumerated it and it is transcribed
in `## Reference A` below. Seven identifiers go, and `ConflictOutcome` goes with the module that
defines it, which is why `types/intake.ts:8` currently imports from `@/lib/conflict-check`.

Two decisions this plan makes so the executor does not have to:

**`IntakeData.settlement_track` is removed, not defaulted.** `IntakeData` is the shape written to
the `cases.intake_data` JSONB column, and that column has no Postgres-level shape constraint. A
field kept alive with a hardcoded literal after the screen that set it is gone would write a value
no user chose into a legal case record. Removing the field is the honest option; Task 4 enumerates
every reader first so the removal is proven safe rather than assumed safe.

**`createInitialIntakeState` drops the three state members rather than keeping empty ones.**
`GuidedIntakeForm` parses `localStorage['inheritance-intake-draft']` straight into
`IntakeFormState` with no validation, and the journey step file's own comment records that a shape
mismatch crashes the app into its error boundary. Task 5 therefore adds nothing clever — it changes
the storage key so an old seven-key draft is never parsed into the new four-key shape.
</objective>

<threat_model>
This plan removes a code path that wrote client identity data — name, TIN, government ID, address,
contact details — into `cases.intake_data`. The direction of travel is a reduction in stored
personal data, which is the desired outcome.

The concrete hazard is the **JSONB shape drift** the objective names: `cases.intake_data` has no
Postgres CHECK constraint, so rows written before this phase still carry `settlement_track` and
`relationship_to_decedent` keys that the type no longer declares. Any code that reads those rows
back and assumes the new shape will see extra keys, which TypeScript will not catch because the
value arrives as JSON. Task 4 enumerates the readers precisely so this is checked rather than
hoped; if a reader destructures the removed field, that is a BLOCKED report, not a silent edit.

The second hazard is the stale `localStorage` draft. An old seven-key draft parsed into the new
four-key `IntakeFormState` reaches `state.decedentInfo.full_name` on a member that is present, but
`isStepComplete` and the progress indicator would index a step list that shrank. Task 5's key change
makes an old draft simply not load, which is a visible loss of one in-progress draft and is strictly
better than an error-boundary crash on a case a lawyer was part-way through.
</threat_model>
