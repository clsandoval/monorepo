<objective>
Plans `16-02` and `16-03` deleted the three intake screens and their supporting module and types.
Three test files still call the deleted code and are the last thing keeping the frontend suite from
compiling. This plan retires exactly the tests whose subject no longer exists, and then runs
headlong into a wall that the phase brief did not anticipate and that this plan exists to report
honestly.

The wall, measured during research:

- `frontend/test-baseline.json` carries `min_total_tests: 2119`, and
  `frontend/scripts/check-test-baseline.mjs:186` fails with `TEST COUNT DROPPED` the moment the
  measured total falls below it.
- `src/lib/__tests__/conflict-check.test.ts` holds **11** tests, every one of which tests
  `lib/conflict-check.ts`. That module is gone, so all 11 go with it. That alone takes the total to
  at most 2108, which is below 2119.

So the frontend gate turns red, and the only thing that would turn it green again is lowering
`min_total_tests`. The baseline file does carry a `floor_lowered` record, and commit `4ccf06270`
used it once — under explicit owner authorisation, with a written reason. **This phase may not use
it.** The phase constraints prohibit lowering a baseline floor and prohibit editing
`test-baseline.json` to turn a red run green, with no authorisation path an agent can invoke.

That is not a defect in this plan. It is the system working: a floor exists precisely so that tests
cannot quietly evaporate, and it cannot distinguish "the subject was deleted under owner
authorisation" from "someone dropped a suite" — only a human can. This plan makes the cut, runs the
gate, and hands the owner one small, precise decision with the real numbers attached.
</objective>

<constraints>
- `frontend/test-baseline.json` is not edited. Not its `min_total_tests`, not its `total_tests`, not
  its `known_failures` array, not its `floor_lowered` record. The same prohibition covers
  `gate-skips.lock`, `assertion-baseline.json`, `gates.manifest.json` and `gates.manifest.lock`.
- A test is deleted only when the function, module or component it calls no longer exists. A test
  that exercises surviving behaviour stays, even when it sits in a file most of which is going.
- No assertion in a surviving test is loosened, no expected value is widened, and no test is given
  a skip, pending or todo marker. Reducing a suite's strictness to clear a red run is prohibited by
  the phase constraints and by `CLAUDE.md`.
- The three test files are edited by removing whole `describe` and `it` blocks whose subject is
  gone. `src/lib/__tests__/conflict-check.test.ts` is deleted in full with `git rm`, because its
  subject module is gone in full.
- The plan ends with a BLOCKED report written to the phase directory and committed. The report
  pastes real command output; a paraphrase is not a BLOCKED report, per
  `.planning/PLAN-STANDARD.md` section 3.
- Execution does not continue past Task 4 into any attempt to make the gate green. Plans `16-05` and
  `16-06` are separately scheduled and do not depend on the gate being green.
</constraints>

<threat_model>
The security-relevant risk here is **losing a test that guards a real boundary while claiming it was
orphaned**. Among the tests going are ones covering `lib/conflict-check.ts`, which queried Supabase
for name and TIN matches across cases — a cross-case read. If any of those 11 tests happened to
assert an org-scoping property rather than a matching-algorithm property, deleting it would remove
coverage of a tenant-isolation behaviour that still exists elsewhere.

Task 1 mitigates this concretely: before anything is deleted, every test in the file is listed with
its subject, and any test asserting an org-scoping or RLS property is named. Tenant isolation is
independently gated by G18 (`journey/rls-isolation.mjs`, fourteen cases over four surfaces with
paired positive controls), so the property does not go ungated — but the plan records the overlap
rather than assuming it.

The second risk is the inverse of the first: deleting *more* than the orphans, and hiding a
regression inside a legitimate deletion. That is exactly what the floor exists to catch, and it is
why this plan does not touch it.
</threat_model>
