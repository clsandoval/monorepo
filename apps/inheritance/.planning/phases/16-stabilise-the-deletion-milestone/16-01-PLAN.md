<objective>
CUT-02 asks that `frontend/src/test-setup.ts` supply the missing jsdom globals and that the
resulting failure-count drop be **measured before and after, not estimated**. Research measured the
before state and found the premise has already moved: the ResizeObserver polyfill and the
`scrollIntoView` and `hasPointerCapture` shims have been in `test-setup.ts` since commit
`181ae68c5`, `git diff HEAD -- src/test-setup.ts` is empty, and `cd frontend && npm run test:gate`
exits **0** at 2119 tests with 31 ledgered failures and zero skips. There is no population of ~1,465
environment failures in this tree.

So the work CUT-02 actually still contains is not "add polyfills" — it is "prove the polyfills are
sufficient". This plan does that by classifying **all 31** ledgered failures against a mechanical
rule and recording the result. If a failure turns out to be a missing DOM global, that shim is
genuinely absent and gets added here. If none is, that is the finding, and writing a duplicate
polyfill would be motion rather than work.

The plan also captures the phase's starting measurements — the frontend gate numbers, the typecheck,
and the exact per-step journey result — into one committed record, `16-BASELINE.md`. Every later
plan in this phase compares against that file rather than against a remembered number. This matters
because plans `16-02` through `16-04` deliberately move the test count, and "measured before and
after" is only meaningful if the before was written down first.

This plan changes no application source and approves no reference.
</objective>

<constraints>
- This plan writes exactly one file: the phase-directory record named in `files_modified`. It edits
  nothing under `frontend/src/`, `engine/`, `specs/` or the gate manifest.
- The one exception is conditional and is fully specified in Task 3: if and only if the
  classification rule identifies a failure caused by an absent DOM or BOM global, that single
  guarded shim is added to `frontend/src/test-setup.ts` following the existing `if (!existing)`
  pattern already in that file, and `frontend/src/test-setup.ts` is added to the commit. The
  classification rule leaves the executor no discretion — it is a string match, stated literally in
  Task 3.
- No number is written into the record that was not pasted from a command run during this plan.
  Copying a number out of `LOOP-STATUS.md`, `gate-results.json` or a prior phase summary is
  prohibited, because reconciling those files with reality is exactly what this phase exists to do.
- The local Supabase stack must be up before Task 4. Confirm with `npx supabase status` from
  `frontend/`. If it is down, run `supabase start` from `frontend/`. If it cannot be brought up,
  stop and report BLOCKED — a journey result measured against a dead database is worse than no
  measurement.
- No journey reference is approved in this plan. `node journey/approve.mjs` is not invoked.
- No test, assertion, gate or baseline floor is weakened, and nothing is appended to
  `gate-skips.lock`, `assertion-baseline.json` or `test-baseline.json`.
</constraints>

<threat_model>
The risk this plan carries is not a security boundary — it writes a markdown record and, at most,
one guarded test-environment shim. The realistic failure is **a false measurement becoming the
phase's reference point**: if a number is copied from a stale document rather than run, every later
comparison in the phase inherits the error and the phase reports a drop or a gain that never
happened. The constraint that every figure must be pasted from a command run in this plan is the
mitigation, and Task 5's verification re-runs the two cheapest measurements to confirm the record
matches a fresh run.

The second risk is a shim added under Task 3 masking a real product defect — a component that calls
a DOM API the browser also lacks would be papered over. The `if (!existing)` guard does not address
that, so Task 3's rule is narrow on purpose: it fires only on globals jsdom is known not to
implement, and the classification of every failure is written into the record where a reader can
disagree with it.
</threat_model>

A failure is an **environment failure** when its message matches either the literal substring
`is not a function` or the literal substring `is not defined`, **and** the identifier immediately

browser but is absent under jsdom. Every other failure is **product debt**.

message, and the verdict `environment` or `product-debt`.

`frontend/src/test-setup.ts` inside the existing `if (typeof window !== 'undefined')` block for
element-prototype members, or at module top level for a constructor, following the exact
`if (!existing)` guard pattern the file already uses for `ResizeObserver`. Add a one-line comment
naming the failing test that motivated it. Then re-run the gate and record the new counts.

If all 31 classify as `product-debt`, write no code. Record the finding that the jsdom globals
CUT-02 names are sufficient, and that the failure-count drop CUT-02 asks to be measured was
realised by commit `181ae68c5` rather than by this phase.
</action>
