<objective>
CUT-03 requires that every failing journey reference be either passing or **explicitly reported for
human review**, and that any re-approval be confined to the deleted sidebar navigation region and
recorded with `--by deletion-milestone-nav-change`. Note the shape of that requirement: reporting a
step for human review is a *satisfying* outcome, not a failure. CUT-03 does not ask for 28 green
steps; it asks that no step be in an undecided state.

Measured in plan `16-01`, the run is `JOURNEY FAIL steps=28 failed=24`, and the 24 split across two
markers that mean different things:

| Marker | Count | Steps |
|---|---|---|
| `DIFF FAILURE` | 22 | `auth-session-persisted`; `intake-step-0` … `intake-step-6`; `intake-draft-recovered`; `tax-tab-0` … `tax-tab-7`; the five `wizard-*` steps |
| `REFERENCE SIZE MISMATCH` | 2 | `results-view`, `results-family-tree` |

The four passing steps are all unauthenticated — `auth-signin`, `auth-signup`, `auth-verify-nocode`,
`auth-verify-badcode` — which is real evidence for the sidebar story, since an anonymous page has no
sidebar to shift. It is evidence, not a licence: each diff still gets opened.

Three groups, three dispositions, all decided here so the executor decides nothing:

**Group 1 — the 14 authenticated non-intake `DIFF FAILURE` steps.** `auth-session-persisted`, the
eight `tax-tab-*` and the five `wizard-*`. Their surfaces were not edited by this phase, so a diff
confined to the sidebar is the expected finding. Each is inspected individually and approved only on
that finding.

**Group 2 — the 8 intake steps.** `intake-step-0` … `intake-step-6` and `intake-draft-recovered`.
These are **not approvable and this plan does not approve them.** Their rubrics assert `Step 1 of 7`
and `Step 6: Settlement Track` as DOM text, and plan `16-03` moved the draft storage key, so they
fail on rubric and on seeding before any pixel is compared. Their diffs necessarily touch wizard
content, which the journey rule forbids approving. They are also not retired, because the guided
intake still exists — only three of its seven screens went, and deleting a step for a surviving
surface would be weakening a gate. They are repaired as far as an agent legitimately can (Task 4
updates the fixtures and rubrics to the post-cut truth) and then reported for human review, because
producing a first reference for a rebuilt screen is a visual judgement.

**Group 3 — the 2 `REFERENCE SIZE MISMATCH` steps.** `results-view` and `results-family-tree`. The
harness computed no pixel diff at all, because the captured page is a different height from the
reference. A height change is not self-evidently nav-attributable, so these get their own inspection
and are not folded into Group 1.

`autonomous: false` on this plan is deliberate. Task 3 requires a human to look at images.
</objective>

<constraints>
- `node journey/approve.mjs <stepId> --by deletion-milestone-nav-change` is the only way a reference
  is written, and it runs only after the diff for that step has been opened and inspected. The
  script refuses to promote anything but an image a real run produced, and no gate may call it.
- Approval is permitted **only** when every differing pixel lies in the left-hand sidebar navigation
  region. A diff touching a wizard field, a money figure, a table row or a citation is left failing
  and written into the disposition record. There is no partial approval and no tolerance increase:
  `--max-diff-pixels` is left at its default of 0 for every approval.
- The eight intake steps are not approved by this plan under any circumstance, and not deleted from
  the registry either.
- No step record is removed for a surface that still exists. The only registry deletions permitted
  here are the five orphan tolerance sidecars named in Task 5, which have no PNG and no owning step.
- `gates.manifest.json`, `gates.manifest.lock`, `gate-skips.lock`, `assertion-baseline.json` and
  `frontend/test-baseline.json` are not edited.
- The local Supabase stack must be up. Confirm with `npx supabase status` from `frontend/`, and
  start it with `supabase start` when it is down. A journey run against a dead database measures the
  environment, not the product.
- `node scripts/check-journey-registry.mjs` must exit 0 at the end of the plan. It fails when a step
  lacks a rubric or an approved reference, and when a reference exists with no owning step.
</constraints>

<threat_model>
The threat this plan is written against is not external. It is **an agent making a human's approval
decision for them.** `journey/approve.mjs` carries its rationale in its own header: no gate may call
it, because a gate that could approve its own reference would go green by rewriting its own
expectation and the change would never appear in front of a person. Twenty-four references is
exactly the volume at which bulk-approving becomes tempting, and commit `4ccf06270` explicitly
declined to do it on the owner's behalf for that reason.

The concrete failure mode: a money figure or a citation changed by one of the deletion commits sits
inside a screenshot that also shifted because the nav went. Approved in bulk, that becomes the new
expected image, and every future run certifies the wrong number forever. The per-step inspection in
Task 3, the refusal to approve Group 2 at all, and the separate handling of Group 3's size mismatch
are the three mitigations, and none of them is automatable.

A second, smaller risk: the journey fixtures in Task 4 seed `localStorage` with a state blob. The
step file's own comment records that a partial draft crashes the app into its error boundary, so a
half-updated fixture produces a red step that looks like a product defect. Task 4 requires each
fixture to be a complete post-cut state and verifies it by running the step.
</threat_model>
