<objective>
CUT-01 requires that the guided intake contain no conflict-check step, no client-details step and no
settlement-track step. This plan performs that cut inside the wizard container and deletes the three
step components, and it does nothing else — the orphaned library module, the orphaned types and the
orphaned tests are plans `16-03` and `16-04`.

The split exists because of how the previous attempt failed. The owner's record is explicit: a
careless regex sweep mangled `GuidedIntakeForm.tsx` and the whole attempt was reverted. The
structural reason it was easy to mangle is that the file encodes the step order **three times** —
in the `INTAKE_STEPS` tuple, in a `switch (currentStep)` over cases `0` through `6`, and in a
progress-indicator map over the same tuple — and a substring edit hits one copy without the others.

The measured layout, from `16-RESEARCH.md` section 3:

| Old index | Step name | Component | Fate |
|---|---|---|---|
| 0 | Conflict Check | `ConflictCheckStep` | cut |
| 1 | Client Details | `ClientDetailsStep` | cut |
| 2 | Decedent Info | `DecedentInfoStep` | survives, becomes 0 |
| 3 | Family Composition | `FamilyCompositionStep` | survives, becomes 1 |
| 4 | Asset Summary | `AssetSummaryStep` | survives, becomes 2 |
| 5 | Settlement Track | `SettlementTrackStep` | cut |
| 6 | Review & Save | `IntakeReviewStep` | survives, becomes 3 |

`INTAKE_STEP_COUNT` is derived as `INTAKE_STEPS.length`, so it follows the tuple from 7 to 4 without
a separate edit.

The removal order is **5, then 1, then 0** — highest index first. Each removal then renumbers only
the cases that follow it, so the executor never holds two numbering schemes at once. Taking index 0
first would shift all six remaining cases immediately, which is the shape of edit that produced the
reverted mess.
</objective>

<constraints>
- Edits are made with targeted replacements of named blocks. A regex sweep, a stream edit, or any
  find-and-replace across the whole of `GuidedIntakeForm.tsx` is prohibited by this plan.
- `cd frontend && npx tsc -b --force` must exit 0 after **each** of Tasks 2, 3, 4 and 5 before the
  next task begins. `frontend/tsconfig.json` sets `noUnusedLocals` and `noUnusedParameters`, so a
  stale import or an orphaned callback is a build failure — that is the tripwire this plan relies
  on. A non-zero typecheck stops the plan at that task and is reported BLOCKED with the pasted
  compiler output.
- The three deleted `.tsx` files are removed with `git rm`. `bash scripts/safe-commit.sh` refuses a
  non-empty index, so `git reset` is run before the commit in Task 6 and safe-commit stages the
  paths itself.
- The four surviving step components are not edited by this plan. Their props, their state shape and
  their rendered output stay exactly as they are; only the case labels that dispatch to them change.
- `frontend/src/lib/intake.ts`, `frontend/src/lib/conflict-check.ts`,
  `frontend/src/components/intake/IntakeReviewStep.tsx` and every test file are **out of scope
  here** and are handled by plans `16-03` and `16-04`. Between this plan and those, the tree will
  not typecheck as a whole in one specific way that Task 5 names and bounds.
- No test, assertion, gate or baseline floor is weakened, and nothing is appended to
  `gate-skips.lock`, `assertion-baseline.json` or `test-baseline.json`.
</constraints>

<threat_model>
The wizard is behind authentication and the three removed screens collected client identity data —
full name, date of birth, government ID type and number, TIN, address, email and phone in
`ClientDetailsStepState`, and a name and TIN in `ConflictCheckStepState`. Removing them **reduces**
the personal data the application collects, which is a privacy improvement, not a regression.

The one real hazard is a **partial cut that leaves collected data flowing to a place nothing reads**
— for example a surviving write of `clientDetails` into `cases.intake_data` after the screen that
populated it is gone, which would persist an empty or stale object into a JSONB column with no shape
constraint. That write lives in `lib/intake.ts` and is deliberately closed by plan `16-03`; Task 5
here records the exact compiler errors that prove it is still open so the hand-off cannot be
forgotten.

A second hazard is a draft in a user's `localStorage` under `inheritance-intake-draft` holding the
old seven-key shape. The wizard parses that key straight into `IntakeFormState` with no validation,
and the step file's own comment records that a shape mismatch crashes the app into its error
boundary. Task 5 records this as a finding for plan `16-03`, which owns the state shape.
</threat_model>
