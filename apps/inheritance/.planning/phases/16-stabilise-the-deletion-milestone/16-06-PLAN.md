<objective>
CUT-04 asks that `bash scripts/ci-gates.sh` exit 0 with nothing weakened, skipped or ledgered to get
there. This plan runs the suite, records exactly what happened, and reports the two things standing
between the tree and a green run — neither of which an agent may clear.

**Blocker A, measured in research.** Commit `4ccf06270` deleted
`frontend/journey/share-exposure.mjs` and `frontend/journey/seo-smoke.mjs` — the gates covering the
share route and the SEO landing pages, both surfaces the deletion milestone removed — but left G20
and G21 registered and **blocking** at orders 15 and 16:

```
15 G20  BLK cd frontend && node journey/share-exposure.mjs
16 G21  BLK cd frontend && node journey/seo-smoke.mjs
```

G20's precondition `test -f frontend/supabase/fixtures.json` is satisfied, so the runner executes
both rather than skipping them, and both fail with a module-not-found error. `ci-gates.sh` states in
its own header that there is deliberately no option for omitting a gate and no flag for pointing it
at a different manifest — by design, so that a long unattended loop cannot quietly redefine success.

Retiring a gate is owner action under `CLAUDE.md` invariant 2 and is enforced by G5. **So CUT-04 is
unreachable by any permitted action in this phase**, and the correct output is a precise report, not
a manifest edit.

**Blocker B** is plan `16-04`'s test-count floor, already reported in `16-FLOOR-BLOCKED.md` and
restated here so the owner sees both decisions on one page.

There is also unmeasured ground. The last full run halted at G17 having reached 13 of 32 gates, so
**G19, G22 through G25 and G30 through G33 have not executed since the deletion commits**. G19
(money parity), G24 (PDF visual) and G25 (print layout) all drive the post-deletion application and
may carry their own fallout. This plan measures them by running the suite instead of assuming, and
reports whatever it finds — including good news.
</objective>

<constraints>
- `gates.manifest.json` and `gates.manifest.lock` are not edited. No gate is removed, no `command`
  string is changed, no `blocking` flag is flipped, no `precondition` is altered.
- `frontend/test-baseline.json`, `gate-skips.lock` and `assertion-baseline.json` are not edited.
- No stub, placeholder or re-implementation of `share-exposure.mjs` or `seo-smoke.mjs` is written.
  Writing a script that exits 0 to satisfy a gate whose subject was deleted is the purest form of
  making a red run green by weakening a check, and it is prohibited. Restoring the deleted scripts
  is equally out of scope, because the surfaces they test are gone.
- `gate-results.json`, `LOOP-STATUS.md` and `loop-history.jsonl` are regenerated by
  `node scripts/loop-status.mjs record` and by the runner's own trap. They are never hand-edited;
  hand-editing a generated results file is falsifying the record of a run.
- The plan reports the real exit code of `ci-gates.sh`. It does not describe a run it did not
  perform, and it does not summarise output that should be pasted.
- The local Supabase stack must be up before the run, because gates G17, G18 and G19 all need it.
  Confirm with `npx supabase status` from `frontend/`.
</constraints>

<threat_model>
The failure this plan guards against is **a false green**. Every mechanism that could produce one is
within arm's reach of the executor at this point in the phase: two gates whose scripts are missing
could be silenced by deleting two manifest entries; a stub script exiting 0 would satisfy both in
under a minute; a hand-edited `gate-results.json` would make the published record claim a run that
never happened.

Each of those is individually cheap and each is catastrophic here, because the entire value of this
repository's 32-gate apparatus rests on a passing gate set genuinely implying a working app. A gate
retired to clear a red run is worse than the red run, and a hand-written results file is worse
again, because it survives into the record a future reader trusts.

The mitigations are all negative-space assertions and they are verified rather than promised: Task 4
diffs the manifest, the lock and the three baseline files and requires an empty diff; Task 2
requires the two failing gates to be shown failing with their real output; and the generated files
are only ever written by the project's own recorder.
</threat_model>
