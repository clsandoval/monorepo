<objective>
Phase 19's claims all have the form "work now reaches the database that previously did not". None of
them can be stated without a measured starting state, and four later plans are verified by re-running
one of these measurements and watching a specific number move. This plan takes those measurements
once, before any source file is edited, and records them in `19-BASELINE.md`.

Six quantities are established. Each is either driven to a target by a later plan or deliberately
held fixed:

1. **Call sites that feed `useAutoSave`** — how many places under `frontend/src/` call
   `setAutoSaveInput`, and how many of those are outside the case-load effect. Plan `19-04` drives
   the second number above zero.
2. **Saves performed by merely opening a case** — the observable behaviour of the current
   reference-equality guard when the page loads and nothing is typed. Plan `19-02` drives this to
   zero.
3. **Saves performed by an edit** — the observable behaviour when the same object is mutated in
   place and re-passed. Plan `19-02` drives this above zero.
4. **Saves performed by an unmount inside the debounce window** — zero today, and the committed test
   that asserts it. Plan `19-02` drives it to one.
5. **The frontend test count and the floor** — `min_total_tests` against the number the suite
   actually runs. Plan `19-06` re-reads this to determine whether the phase's added tests cleared
   `G3` without any baseline being touched.
6. **The gate set's shape at the insertion point** — the ids and orders around `G19`, so `19-06` can
   prove that `order` was the only field that moved on any pre-existing gate.

This plan writes no reusable module and no script. Each measurement is one command short enough to
live in a `<verify>` block verbatim.
</objective>

<constraints>
- Measurement only. This plan does not edit `engine/`, `frontend/src/`, `frontend/journey/`,
  `scripts/`, any test, `gates.manifest.json`, `gates.manifest.lock`, `gate-skips.lock`,
  `assertion-baseline.json` or `frontend/test-baseline.json`.
- Every command runs from `/home/clsandoval/cs/monorepo/apps/inheritance` or from its `frontend`
  subdirectory, exactly as written in each `<verify>` block.
- Any temporary probe file created under `frontend/src/hooks/__tests__/` during a measurement is
  deleted in the same `<verify>` block that creates it, and
  `git status --porcelain -- apps/inheritance/frontend` must show no new untracked file attributable
  to this plan when it finishes.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  does not run the whole suite and makes no claim about it.
- The measured numbers are recorded exactly as printed, including a number that contradicts
  `19-RESEARCH.md`. A contradiction is a finding to record in `19-BASELINE.md`, not a result to
  reconcile.
</constraints>

<threat_model>
This plan reads committed TypeScript, committed JSON and the committed Vitest suite, and writes one
Markdown file under `.planning/`. It opens no socket, contacts no database and reads no credential.
The temporary probe in Task 3 is a Vitest file that mocks `@/lib/cases`, so it performs no network
call even in principle.

The one real hazard is **a measurement that reports success because it measured nothing**: a `grep`
matching zero files prints `0`, and `0` is also the target value for two of the six quantities. Every
`grep` in this plan is therefore paired with a positive control on the same pattern set — a count
that must be non-zero for the measurement to mean anything — and an acceptance criterion that fails
the plan when the control is zero.

Severity: low. Nothing here is reachable from the running application, and the worst outcome is a
baseline that must be re-measured.
</threat_model>
