<objective>
`19-05` wrote `frontend/journey/persistence.mjs` and observed it red on three injected regressions and
green on the fixed application. This plan makes it a gate, documents it, and closes the phase with a
re-measurement rather than a summary.

Three things happen here, in this order, and the order matters.

**First, re-measure what the phase held fixed.** `cargo test` is the null control: this phase edits no
Rust, so its count must not move. If it moved, that is a finding to report before anything is
registered, not after.

**Second, register `G35` at order 17.** The gate needs Docker, a running Supabase stack, a built
application and a browser — the same environment as `G18`, `G17` and `G19` and a heavier one than
every gate before them. Placing it immediately after `G19` preserves the manifest's existing cost
ordering and shifts `G20` through `G9` down by one. `order` must be provably the only field that
moves on any pre-existing gate.

**Third, re-read the test-count floor and report the truth about it.** `19-01` measured `2109` tests
against a floor of `2119`, a gap of exactly ten, and
`frontend/scripts/check-test-baseline.mjs:186` compares with a strict less-than — so a run count above
the floor passes. This phase adds test cases across four files. Whether that cleared `G3` is a
measurement this plan takes and records. It is not a claim this phase makes in advance, and no
baseline is edited either way.

The phase does **not** claim `bash scripts/ci-gates.sh` exits 0. `G20` and `G21` are registered
blocking gates whose scripts are gone, and retiring a gate is owner action.
</objective>

  file is edited by this plan.
- `frontend/test-baseline.json`, `assertion-baseline.json` and `gate-skips.lock` are not edited. If
  the observed test count is still below the floor, that is reported with the pasted
  `TEST COUNT DROPPED` line.
- Every prose statement of the gate count in the repository moves together with the manifest, so no
  document contradicts the file it describes.
</constraints>

<threat_model>
This plan edits the file that decides what the build checks. The hazards are all about the gate set
quietly getting weaker while appearing to grow.

1. **A field other than `order` moving on a pre-existing gate.** A command string edited during a bulk
   renumber would silently retarget or disable an existing check while `G5` still passed, because `G5`
   compares against the lock rather than against the previous manifest. Mitigated by a field-by-field
   comparison against `git show HEAD:apps/inheritance/gates.manifest.json` whose acceptance criterion
   is `NON_ORDER_CHANGES 0`.
2. **Registering a gate that has never been seen failing.** Mitigated by ordering: `19-05` observed
   three red runs and their reverts before this plan runs, and Task 2's `read_first` names the
   `19-05` summary that records them.
3. **Making the suite look green by moving a floor.** The single most tempting action available in
   this phase is editing `min_total_tests`. It is prohibited by name in this plan's truths, in its
   constraints and in its acceptance criteria, and a `git diff` on the baseline file is one of the
   final verification commands.

Severity: high in consequence, low in likelihood, and every path is checked by a command rather than
by care.
</threat_model>
