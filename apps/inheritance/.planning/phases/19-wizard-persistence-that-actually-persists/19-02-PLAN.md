<objective>
`useAutoSave` cannot save. Two independent defects in one 52-line file produce that, and this plan
fixes both without touching any caller.

**Defect 1 — the guard compares references.** `useAutoSave.ts:40` reads
`if (prevInputRef.current === input) return;`. A form library that mutates an object in place, or any
caller that re-passes the same object after changing a nested field, is invisible to it. Its
replacement compares a deterministic serialization of the value.

**Defect 2 — the cleanup discards work.** `useAutoSave.ts:46-48` clears the pending timer on every
effect re-run and on unmount, so up to 1.5 seconds of typing dies when the lawyer navigates away.
Its replacement flushes on unmount and carries the pending save's target with it, so a case switch
saves against the case that was being edited rather than against the one just opened.

The plan also removes a third, quieter behaviour `19-01` measured: opening a case and typing nothing
currently performs one save whose payload equals what was just read. After this plan the first value
a hook observes is **adopted**, not treated as a change, so opening a case writes nothing and the
save indicator stays silent until the lawyer actually edits.

A pure serializer is extracted to its own module so it can be tested directly rather than through the
hook, and so the money rule it enforces lives somewhere a reader can find it.
</objective>

<threat_model>
This plan edits a hook that writes to the `cases` table through `updateCaseInput`, so the realistic
hazards are about **writing the wrong thing** rather than about disclosure.

1. **Saving against the wrong case.** A pending debounce that fires after `caseId` changed would
   overwrite case B's `input_json` with case A's family tree — silent cross-case corruption inside
   one tenant, invisible to RLS because both rows belong to the same user. Mitigated structurally:
   the pending record carries its own `caseId`, so a flush can only ever write to the case whose edit
   scheduled it. A test asserts this by changing `caseId` mid-debounce and checking the mock's first
   argument.
2. **Flushing something that was never scheduled.** An unmount that saved unconditionally would write
   on every page open, including opens the lawyer abandoned. Mitigated by flushing only when a
   pending record exists, and by making the first observed value an adoption. A test mounts and
   immediately unmounts and asserts zero calls.
3. **A serializer that silently truncates.** A cyclic or pathologically deep object would either hang
   or throw inside a React effect. `EngineInput` is JSON-derived and acyclic, and the serializer
   raises a named error above 32 levels rather than recursing without bound.

No credential, no network endpoint and no authorisation decision is touched. Severity: medium, fully
covered by the tests below.
</threat_model>

State held in refs:

- `timerRef` — the `setTimeout` handle or `null`.
- `pendingRef` — either `null`, or a record carrying **both** the `caseId` and the `EngineInput` that
  the scheduled save must write. The pending save carries its own target so a flush can never write
  to a different case than the one whose edit scheduled it.
- `prevSerializedRef` — the last serialized value observed for the current `caseId`, or `null`
  meaning "nothing observed yet".
- `mountedRef` — `true` until the unmount cleanup runs.

Behaviour, expressed as four effects and one callback declared in this order:

1. `doSave(target)` — a `useCallback` with an empty dependency array taking the pending record. It
   sets status `saving`, awaits `updateCaseInput(target.caseId, target.input)`, sets `saved` on
   success and `error` on rejection, each guarded by `mountedRef.current`.
2. A **case-boundary effect** depending on `[caseId, doSave]`. When the `caseId` it last saw differs
   from the current one, it clears any timer, flushes any pending record through `doSave` — which
   writes to the **previous** case, because the record carries its own target — and then sets
   `prevSerializedRef.current` to `null` so the new case's first value is adopted rather than saved.
3. A **debounce effect** depending on `[caseId, input, doSave]`. It returns immediately when `caseId`
   is `null`. Otherwise it computes `stableStringify(input)`; when `prevSerializedRef.current` is
   `null` it stores the value and returns **without scheduling anything**; when the stored value is
   equal it returns; otherwise it stores the new value, clears any existing timer, writes
   `{ caseId, input }` into `pendingRef` and schedules a `setTimeout` for `DEBOUNCE_MS` that clears
   `timerRef`, takes the pending record, nulls `pendingRef` and calls `doSave` with it. **This effect
   returns no cleanup function.**
4. An **unmount effect** with dependency array `[doSave]`, whose only body is a cleanup that sets
   `mountedRef.current` to `false`, clears any timer, and — when `pendingRef` holds a record — nulls
   it and calls `doSave` with it.

The exported `save` is a `useCallback` over `[caseId, input, doSave]` that clears any timer, takes
the pending record when one exists and otherwise builds `{ caseId, input }` when `caseId` is
non-null, nulls `pendingRef`, and calls `doSave` with whichever record it obtained. When `caseId` is
`null` and no record is pending it does nothing.

the first value observed for a case is adopted rather than saved so that opening a case writes
nothing.
