<objective>
Make the same clause obtainable as DOCX (DEED-02), adding no dependency.

Purpose: ROADMAP criterion 2 says "the same clause is obtainable as DOCX." This plan makes
that word *same* literally checkable by rendering `word/document.xml` from the string
`buildDeedClauseText` already returned, one `<w:p>` per line. There is then no second
composition that could carry a different peso figure, and the gate in plan 22-07 asserts the
round trip.

Output: `frontend/src/lib/deed/docx.ts` returning a `Uint8Array` OPC package with exactly
three parts, plus its test file.
</objective>

<constraints>
- No npm dependency. The module imports only `./zip`, `./clause-text` and a type from
  `./schedule-lines`.
- Exactly three parts, in this order: `[Content_Types].xml`, `_rels/.rels`,
  `word/document.xml`. No styles part, no theme, no fontTable, no settings, no
  `docProps`. A deed clause is pasted into the firm's own template, so shipping a style sheet
  would be shipping design taste this product has no basis for.
- The body is `buildDeedClauseText(schedule).split('\n')`, one paragraph per element, in
  order, with nothing added, dropped, trimmed or reordered.
- XML text-node escaping replaces `&` first, then `<`, then `>`. Nothing else is replaced;
  `"` and `'` need no escaping inside a text node and escaping them would alter a name a
  lawyer typed.
- `xml:space="preserve"` on every `<w:t>`, so leading indentation on continuation lines
  survives the round trip.
- Byte-determinism: no wall clock anywhere. `new Date()`, `Date.now()` and
  `performance.now()` must not appear.
- The module produces bytes and never writes a file, never touches `document`, never touches
  `window` and never touches the network. The download path lives in plan 22-05.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own.
</constraints>

<threat_model>
A pure byte producer over a string already built in the browser. No network, no filesystem,
no authorisation decision.

**T-22-04 — XML injection through free text.** A decedent or heir name is user-typed and
lands inside an XML text node. A name containing `</w:t></w:r></w:p>` would close the element
early and let the rest of the name become markup. Severity: high for document integrity — a
corrupt part makes Word show a repair prompt, and a cleverly-closed one could inject
paragraphs that read as engine output. Mitigation: `escapeXmlText` is applied to **every**
string that reaches a text node, with `&` replaced first so an escape sequence is never
double-escaped; a test asserts that a name containing `</w:t>`, `&`, `<` and `>` round-trips
to the identical characters and that the produced part contains no unescaped `<w:t>` beyond
the expected count.

**T-22-04b — path traversal through a part name.** Ruled out by construction and by the layer
below: the three part names are module-level constants in `DOCX_PART_NAMES` and no
caller-supplied string ever becomes an entry name, and `buildStoredZip` (plan 22-01)
independently rejects an absolute, backslash-bearing or `..`-bearing name.

**T-22-04c — a zip bomb or unbounded allocation.** Not applicable: entries are stored, so the
archive is the size of its content plus fixed headers, and the content is a clause whose
length is linear in the heir count.

No other threat at or above the configured blocking severity applies to this plan.
</threat_model>

  <action>
Create `frontend/src/lib/deed/docx.ts`.

Open it with a module doc comment stating: a `.docx` is an OPC package, OPC permits stored
entries, and so this exporter needs no dependency; the body is the clause text and not a
second rendering of the schedule, which is what makes ROADMAP criterion 2's word *same*
checkable; and there are three parts and no style sheet, deliberately.

Imports: `import { buildStoredZip } from './zip';`,
`import { buildDeedClauseText } from './clause-text';`, and
`import type { DeedSchedule } from './schedule-lines';`. No other import.

Export `export const DOCX_MIME_TYPE = 'application/vnd.openxmlformats-officedocument.wordprocessingml.document';`

Export `export const DOCX_PART_NAMES = ['[Content_Types].xml', '_rels/.rels', 'word/document.xml'] as const;`

Export `export function escapeXmlText(value: string): string` replacing, in this order,
`&` with `&amp;`, then `<` with `&lt;`, then `>` with `&gt;`. Use
`String.prototype.split(...).join(...)` or a global regex; do not use a single chained
`replace` with a lookahead. Add a comment stating that `&` must be first so an emitted
`&amp;` is not re-escaped, and that quotes are deliberately untouched because a text node
does not require them and altering a typed name is itself a defect.

Declare three module-level template constants holding the part bodies. `XML_DECL` is
`<?xml version="1.0" encoding="UTF-8" standalone="yes"?>` followed by a single `\n`.

`CONTENT_TYPES_XML` is `XML_DECL` followed by, on one line:

```
<Types xmlns="http://schemas.openxmlformats.org/package/2006/content-types"><Default Extension="rels" ContentType="application/vnd.openxmlformats-package.relationships+xml"/><Default Extension="xml" ContentType="application/xml"/><Override PartName="/word/document.xml" ContentType="application/vnd.openxmlformats-officedocument.wordprocessingml.document.main+xml"/></Types>
```

`RELS_XML` is `XML_DECL` followed by, on one line:

```
<Relationships xmlns="http://schemas.openxmlformats.org/package/2006/relationships"><Relationship Id="rId1" Type="http://schemas.openxmlformats.org/officeDocument/2006/relationships/officeDocument" Target="word/document.xml"/></Relationships>
```

Export `export function buildDeedClauseDocx(schedule: DeedSchedule): Uint8Array`:

1. `const text = buildDeedClauseText(schedule);`
2. `const paragraphs = text.split('\n').map(toParagraph).join('');` where `toParagraph` returns
   `<w:p/>` for the empty string and otherwise
   `` `<w:p><w:r><w:t xml:space="preserve">${escapeXmlText(line)}</w:t></w:r></w:p>` ``.
3. `documentXml` is `XML_DECL` followed by, on one line:

```
<w:document xmlns:w="http://schemas.openxmlformats.org/wordprocessingml/2006/main"><w:body>{paragraphs}<w:sectPr/></w:body></w:document>
```

4. Encode each of the three bodies with `new TextEncoder().encode(...)` and call
   `buildStoredZip` with the three entries in `DOCX_PART_NAMES` order, returning its result.

Also export `export function extractDocxParagraphs(documentXml: string): string[]` — the
inverse used by the tests and by the gate: match every `<w:p/>` or
`<w:p>...</w:p>` in order, map a self-closing `<w:p/>` to the empty string, otherwise take
the content of the single `<w:t ...>...</w:t>` inside it and reverse the escaping by
replacing `&lt;` with `<`, then `&gt;` with `>`, then `&amp;` with `&` — the reverse order of
`escapeXmlText`, stated in a comment. A paragraph containing no `<w:t` maps to the empty
string. Exporting the inverse next to the writer keeps the two definitions adjacent so a
change to one makes the other's test fail immediately.

Write a local reader at the top of the file, `readStoredZip(bytes: Uint8Array): Map<string,
string>`, which parses the archive the way the gate will: locate the End of Central Directory
by scanning backwards for the signature `0x06054b50`, read the central-directory offset and
entry count from it, walk each 46-byte central header reading the name and the local-header
offset, then for each entry read the local header at that offset, skip
`30 + nameLen + extraLen` bytes and slice `compressedSize` bytes, decoding with
`new TextDecoder().decode(...)`. Throw with a distinct message on any signature mismatch.
This reader is local to the test file on purpose: a shared reader imported by both the test
and the writer would let a single mistake satisfy both sides.

Build the `DeedSchedule` inputs by calling the real `buildDeedSchedule`, exactly as
`clause-text.test.ts` does.

Write these tests.

Part set:
- `readStoredZip(buildDeedClauseDocx(schedule))` has exactly 3 keys.
- the keys, in the archive's own order, are `[Content_Types].xml`, `_rels/.rels`,
  `word/document.xml`.
- `[Content_Types].xml` contains the override for `/word/document.xml`.
- `_rels/.rels` contains `Target="word/document.xml"` and `Id="rId1"`.
- every part begins with `<?xml version="1.0" encoding="UTF-8" standalone="yes"?>`.

Round trip — the check that makes criterion 2 true:
- `extractDocxParagraphs(parts.get('word/document.xml')!).join('\n')` equals
  `buildDeedClauseText(schedule)` exactly, for a schedule with two stated lines, one refused
  line and one document-level refusal.
- the paragraph count equals `buildDeedClauseText(schedule).split('\n').length`.
- an empty clause line becomes `<w:p/>` and comes back as the empty string.

Escaping:
- `escapeXmlText('a & b')` is `a &amp; b`; `escapeXmlText('<x>')` is `&lt;x&gt;`;
  `escapeXmlText('&lt;')` is `&amp;lt;` — proving `&` is replaced first.
- a decedent named `` Ampersand & <Angle> </w:t></w:r></w:p> Injection `` round-trips through
  `buildDeedClauseDocx` and `extractDocxParagraphs` to the identical characters.
- for that same decedent, `parts.get('word/document.xml')` contains exactly as many
  occurrences of the substring `<w:t xml:space="preserve">` as there are non-empty clause
  lines, proving the injected close tag created no extra element.

Determinism:
- two calls with the same schedule produce byte-identical arrays.

Peso integrity:
- for a schedule whose first stated line displays `PHP 1,234,567.89`, that exact string
  appears in the recovered `word/document.xml` text and appears exactly as many times as it
  appears in `buildDeedClauseText(schedule)`.

Refusal integrity:
- the paragraph corresponding to a refused heir contains no `PHP ` token.
