<objective>
Build the one line model every deed renderer reads, and nothing else.

Purpose: Phase 21 shipped one Form 1801 line model with three renderers, and its ROADMAP row
records the reason — "three renderers cannot disagree about which rows exist." This plan is
the same move for the deed clause. `22-RESEARCH.md` §1 measured that
`EngineOutput.per_heir_shares[i]` already carries `heir_name`, `heir_category`,
`net_from_estate` and `legal_basis: string[]`, and that `ManualFlag.related_heir_id` is
nullable in exactly the way DEED-04 needs: a flag naming a heir refuses that heir's line, a
flag naming none refuses the whole schedule.

Output: `frontend/src/lib/deed/schedule-lines.ts`, the only site in the codebase that
constructs a deed line, formats a deed peso amount or assembles a deed article list, plus its
test file. This plan renders nothing — no text, no XML, no React.
</objective>

<constraints>
- The engine is the single attribution authority (CLAUDE.md invariant 5, gate G14). Article
  strings are copied from `share.legal_basis` by reference-free array copy and are never
  parsed, reordered, deduplicated, prefixed, suffixed or looked up. The module source must
  contain no match for the pattern `Art.` followed by a digit.
- The money field this module states is `net_from_estate`, matching what
  `journey/money-parity.mjs` asserts on the results screen for the `heir-net-*` cells. A deed
  stating a different field than the screen the lawyer just read would be a second,
  silently-disagreeing figure.
- All money arithmetic is `BigInt`. `Money.centavos` is typed `number | string` precisely so
  an estate may exceed `Number.MAX_SAFE_INTEGER`; `Number()`, `parseInt` and `parseFloat`
  must not appear in this module.
- Heir order is the engine's own `per_heir_shares` order, unchanged. Sorting a schedule of
  shares would imply an order of preference the engine did not state.
- No wall clock. `new Date()`, `Date.now()` and `performance.now()` must not appear. The date
  the schedule carries is `input.decedent.date_of_death`.
- Every character of every refusal string is either a module-level constant declared in this
  file or a verbatim engine string interpolated unchanged. No refusal is composed from what a
  flag means.
- No point of Philippine law is decided here, and none is needed: all four refusal rules test
  the shape of the engine output.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own.
</constraints>

<threat_model>
A pure function over an engine output already held in the browser. No network, no filesystem,
no authorisation decision, no persisted write.

**T-22-02 — a heir name is attacker-influenced text that reaches two output surfaces.**
`Person.name` is free text a user typed and is stored in `cases.input_json`. It reaches the
clause text (plain, inert) and the DOCX (`word/document.xml`, an XML text node). Severity:
medium if unescaped. Mitigation is placed at the boundary that owns each encoding: this module
stores the name **raw and unmodified**, plan 22-04 escapes `&`, `<` and `>` when it writes the
XML text node, and plan 22-05 renders through React, which escapes by construction. Escaping
here instead would double-escape the plain-text surface and corrupt a legitimate name
containing an ampersand.

**T-22-02b — a wrong figure presented as a right one.** The real hazard of this module is not
injection, it is arithmetic. A centavo value silently coerced through a JS double loses
precision above `Number.MAX_SAFE_INTEGER`, and the result is a peso figure on a legal
instrument. Mitigation: BigInt end to end, a grep-checkable prohibition on `Number(`,
`parseInt` and `parseFloat` in this file, and a test asserting an estate above
`Number.MAX_SAFE_INTEGER` centavos formats exactly.

**T-22-02c — a negative share formatted as a positive one.** A negative `net_from_estate`
would render as a peso amount if the formatter were sign-blind. Mitigation: `formatDeedPesos`
throws on a negative input and `buildDeedSchedule` refuses such a line under rule R0 rather
than calling the formatter.

No other threat at or above the configured blocking severity applies to this plan.
</threat_model>

Export these types.

```ts
export type DeedLineKind = 'stated' | 'refused';

export interface DeedScheduleLine {
  heirId: string;
  heirName: string;
  categoryLabel: string;
  kind: DeedLineKind;
  amountCentavos: string | null;
  displayAmount: string | null;
  articles: string[];
  refusalReasons: string[];
}

export interface DeedSchedule {
  decedentName: string;
  dateOfDeath: string;
  netEstateCentavos: string;
  netEstateDisplay: string;
  lines: DeedScheduleLine[];
  documentRefusals: string[];
  statedCount: number;
  refusedCount: number;
  statedSumCentavos: string;
  statedSumDisplay: string;
}
```

`amountCentavos`, `netEstateCentavos` and `statedSumCentavos` are decimal strings, never
numbers, so a value above `Number.MAX_SAFE_INTEGER` survives the type.

Export `export function formatDeedPesos(centavos: bigint | number | string): string`:
coerce with `BigInt(centavos)`; throw `new Error('DEED NEGATIVE AMOUNT: ' + c.toString())`
when the value is below `0n`; otherwise return
`'PHP ' + (c / 100n).toLocaleString('en-US') + '.' + (c % 100n).toString().padStart(2, '0')`.
The two centavo digits are ALWAYS printed. Add a comment stating that this deliberately
differs from `formatPeso` in `src/types/index.ts`, which drops `.00`, because a deed states
centavos explicitly or states nothing.

Export `export function buildDeedSchedule(input: EngineInput, output: EngineOutput): DeedSchedule`.

Its algorithm, in order:

1. `documentRefusals` = for every `f` in `output.warnings` with `f.related_heir_id === null`,
   the string `` `${f.category}: ${f.description}` ``, in the engine's own array order.
2. For each `share` of `output.per_heir_shares`, in the engine's own order, build one line:
   - `heirId` = `share.heir_id`; `heirName` = `share.heir_name` raw and unmodified.
   - `categoryLabel` = `EFFECTIVE_CATEGORY_LABELS[share.heir_category]`, falling back to
     `share.heir_category` when the map has no entry for it, so an engine that adds a
     category is visible rather than blank.
   - `articles` = `[...share.legal_basis]` — a copy, unmodified in content and order.
   - `const c = BigInt(share.net_from_estate.centavos)`.
   - Collect `refusalReasons` by applying all four rules and keeping every one that fires:
     - **R0** `c < 0n` pushes `REFUSAL_NEGATIVE_AMOUNT`.
     - **R1** `share.legal_basis.length === 0` pushes `REFUSAL_NO_ARTICLE`.
     - **R2** for every `f` in `output.warnings` with `f.related_heir_id === share.heir_id`,
       push `` `${REFUSAL_FLAGGED_PREFIX}${f.category}: ${f.description}` ``, in array order.
     - **R3** is document-level and is handled in step 1; it does not refuse a line.
   - When `refusalReasons.length > 0`: `kind` is `'refused'`, `amountCentavos` is `null`,
     `displayAmount` is `null`. `formatDeedPesos` is not called for a refused line.
   - Otherwise: `kind` is `'stated'`, `amountCentavos` is `c.toString()`, `displayAmount` is
     `formatDeedPesos(c)`.
3. `statedCount` and `refusedCount` are the two partition sizes and must sum to
   `output.per_heir_shares.length`.
4. `statedSumCentavos` is the BigInt sum of `amountCentavos` over stated lines only, as a
   decimal string; `statedSumDisplay` is `formatDeedPesos` of that sum.
5. `netEstateCentavos` = `BigInt(input.net_distributable_estate.centavos).toString()`, and
   `netEstateDisplay` = `formatDeedPesos` of it. When that value is negative, catch the throw
   and set `netEstateDisplay` to the constant `REFUSAL_NEGATIVE_AMOUNT` instead of a peso
   string — a negative estate is never printed as an amount.
6. `decedentName` = `input.decedent.name` raw; `dateOfDeath` = `input.decedent.date_of_death`
   raw.
