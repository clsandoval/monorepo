<objective>
Wire `penalties.ts` into the estate-tax pipeline, so the engine stops publishing a total it cannot
support.

Today the pipeline ends with four lines that are all false for a late estate:

```
surcharges: 0,
interest: 0,
compromise_penalty: 0,
total_amount_due: taxComputation.estateTaxDue, // No surcharges
```

and repeats them in `makeErrorOutput`. A zero is a claim that nothing is owed. Setting the total equal
to the base tax is a claim that the return is complete. Neither claim is true for the years-late
estates the roadmap describes, and `20-RESEARCH.md` §1 measured that the false total is **persisted to
`cases.tax_output_json`** — which is what Phase 21's export will print unless this plan lands first.

After this plan the engine returns a `penalties` object built by `assessPenalties`, projects its three
lines onto the flat backward-compatible fields as `number | null`, sets `total_amount_due` to `null`
whenever any line is declined, and pushes a manual-review warning naming both sections into the
existing `warnings` array. The flat trio becomes a projection of one object rather than four
independent literals — one implementation, per `CLAUDE.md` invariant 5.

The type change from `number` to `number | null` is the load-bearing part. `frontend/tsconfig.json` is
`strict`, so `tsc -b` enumerates every reader that has to confront the absence instead of silently
treating it as zero.
</objective>

<constraints>
- This plan resolves nothing. Every line stays `status: 'declined'` with `centavos: null`. The reason
  is recorded in `20-RESEARCH.md` §0 and in `LAWYER-10`, `LAWYER-11` and `LAWYER-12`.
- `tax_due`, `item44_net_estate_tax_due`, `item40_gross_estate`, `item44_total_deductions`,
  `item34c_gross_estate`, `item35_debts_and_charges`, `item39_spouse_net_share` and `schedules` are not
  touched. This plan changes four fields and adds one.
- `assessPenalties` is called with `input.decedent.dateOfDeath`, `input.filing.filingDate` and
  `taxComputation.estateTaxDue`, in that order. No other base is used.
- `makeErrorOutput` builds its assessment from `assessPenalties('', '', 0)`, so an error output
  refuses in exactly the same shape a real one does rather than reintroducing zeros through the back
  door.
- No `as any`, no `as unknown as`, and no widening of a nullable field back to `number` anywhere. A
  type error is fixed with a null check.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  runs the scoped commands below and makes no claim about the whole suite.
</constraints>

<threat_model>
The pipeline is a pure function over a wizard state; this plan adds one call and changes four output
fields. No new I/O, no new dependency, no authorisation surface.

The hazard with real consequences is **a persisted shape change against JSONB with no database-level
constraint**. `cases.tax_output_json` has no shape check, so rows written before this plan hold
`surcharges: 0` and `total_amount_due: <number>`, and rows written after hold `null`. Any reader that
does arithmetic on a value read back from that column would produce `NaN` on a new row. The measured
mitigation is that **no such reader exists**: `20-RESEARCH.md` §1 pasted the full consumer list, and it
is one interface declaration in `tax-bridge.ts` plus four test fixtures. This plan widens that
declaration in the same commit, so the compiler covers any reader added later.

The second hazard is the familiar one: a future agent replaces `null` with `0` because a display needed
a number. Gate `G36`, built in `20-06`, exists to catch precisely that, and its first injected
regression is restoring the line this plan deletes.

Severity: low, with the caveat that the persisted-shape note belongs in the commit body so Phase 21
reads it before writing an exporter.
</threat_model>
