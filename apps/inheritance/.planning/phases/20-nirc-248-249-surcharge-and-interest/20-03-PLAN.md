<objective>
Give the filing date a source, and take the wall clock out of the engine.

`20-RESEARCH.md` §2 measured an un-audited defect: `frontend/src/lib/estate-tax-engine/pipeline.ts:308`
already sets `FilingInfo.filingDate` from `new Date().toISOString().slice(0, 10)`, the field is read by
nothing, and the spec's first claim about this engine is that it is *fully deterministic*. So the
roadmap's "filing date" is not new plumbing — it is an existing field fed by the calendar. This plan
replaces the calendar with a value the lawyer enters:

1. `EstateTaxWizardState.filing` gains `assumedFilingDate`, an ISO `YYYY-MM-DD` string defaulting to
   the empty string.
2. The Zod schema for `FilingData` gains the matching field.
3. The Filing tab renders a date input for it, with a source note stating why it is blank.
4. `pipeline.ts:308` reads the entered value and the `new Date()` call is deleted.
5. Every object literal the new required field breaks is fixed at the site the compiler names.

Nothing in this plan computes a penalty or a deadline. It moves one string from the calendar to the
lawyer, which is the half of roadmap criterion 1 that reads *"computed from the date of death and the
filing date"*.
</objective>

<constraints>
- The new field is **required**, not optional. An optional filing date would let every existing call
  site keep compiling while silently producing an undetermined lateness, which is the silent path this
  phase removes. The compiler enumerating every site is the point.
- The default is `''`. No plan in this phase writes `new Date()`, `Date.now()`, `today` or any
  equivalent into `frontend/src/`.
- The field name is `assumedFilingDate` and the input's testid is `assumed-filing-date`. Both are
  fixed; neither is chosen during execution.
- The edit to `pipeline.ts` in this plan is confined to the `FilingInfo` construction at line 308. The
  output-assembly block at lines 582–619 and `makeErrorOutput` are `20-04`'s, not this plan's.
- Existing test literals are **extended** with the new field. No test is deleted, skipped or given a
  weaker assertion, and no `.skip`, `.todo` or `.only` marker is introduced anywhere.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  runs the scoped commands below and makes no claim about the whole suite.
</constraints>

<threat_model>
The changed surface is a form field, a Zod field, a type field and one line of an input mapper. No
authorisation boundary, no query, no storage key and no network call is touched. The field is persisted
inside the existing `cases.tax_input_json` JSONB blob, which is already RLS-scoped by
`frontend/supabase/migrations/010_rls_org_scope.sql`; no new column and no new policy is involved.

Two real hazards.

**Injection into the engine through a date string.** The value reaches
`statutoryFilingDeadline` and `filingLateness`, which per `20-01` reject anything that does not match
the ISO shape and never call `eval`, a constructor or a template query. An HTML `type="date"` input
constrains the value further at the browser. A pasted arbitrary string therefore yields
`kind: 'undetermined'` rather than a parse of attacker-controlled text.

**A silent default.** If the field defaulted to today, every computation of the same fact set would
produce a different lateness tomorrow, and a lawyer re-running last month's case would see a different
figure with no visible cause. That is silent wrongness in the strict sense this project ranks worst,
so the default is the empty string and Task 6 greps to prove no wall-clock read survives anywhere under
`frontend/src/lib/estate-tax-engine/`.

Severity: low.
</threat_model>
