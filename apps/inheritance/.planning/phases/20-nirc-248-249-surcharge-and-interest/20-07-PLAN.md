<objective>
Make the Phase 20 refusal permanent, and close the phase with measurements rather than claims.

Four things happen here. `G36` becomes a registered blocking gate, so the refusal cannot be quietly
replaced by an invented rate. The three penalty requirements that genuinely wait on a lawyer are
recorded in `.planning/BLOCKED-REQUIREMENTS.md`, so gate `G26` — which is deliberately red on *good*
news — starts watching for the answer and forces the work the day it arrives. The documents that state
the gate count are moved from 35 to 36 so `G33` stays true. And the phase's null controls, its honest
status, and the place the whole suite halts are all measured and written down.

The `BLOCKED-REQUIREMENTS.md` registration is the part with the longest half-life. `G26`'s own header
says it best: it fails *"when an answer has arrived and the requirement is still open. That last case
is a deliberate red on good news: the answer arriving is exactly the moment the work must start, and a
silent pass would let a month-long unattended loop walk straight past it."* Without this task, the
lawyer could answer `LAWYER-10` and nothing in the repository would notice.
</objective>

<threat_model>
This plan edits planning documents, two markdown documents, one gate script and the gate manifest. It
runs no server and touches no application code.

The hazard is **a manifest edit that silently weakens the gate set**. Three defences, all mechanical.
`gates.manifest.lock` is append-only and `scripts/check-gate-manifest.mjs` (`G5`) fails on a removed
entry, a changed command string or a blocking gate turned non-blocking. Task 1 additionally computes,
before and after, the `{id, command, blocking, requirements}` tuple of every pre-existing gate and
asserts that the count of gates whose non-order fields changed is zero — the same proof Phase 19
recorded for `G35`. And Task 2 runs `G5` itself.

The second hazard is **closing a requirement the lawyer has not answered**, which would make the whole
refusal cosmetic. `G26` enforces it directly once Task 5 lands, and Task 6's acceptance criteria assert
the three checkboxes are still unticked.

Severity: low, and every failure mode is caught by a gate that already exists.
</threat_model>
