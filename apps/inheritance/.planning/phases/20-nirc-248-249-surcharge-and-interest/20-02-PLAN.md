<objective>
Record the three questions Phase 20 refuses to answer, in the two files gate `G10` holds against each
other, so that the engine's refusal is anchored to a named question with a lawyer's signature pending
rather than to a comment nobody will read.

`.planning/NEW-LEGAL-RULE.md` Step 1 prescribes exactly this output when a rule is not stated in a
spec: a `BLOCKED` report, a new `LAWYER-<NN>` entry using the agenda's own eight-heading structure at
the next free id, and a matching object in `.planning/lawyer-decisions.json` using the fourteen-key
schema. `20-RESEARCH.md` §0 pastes the two spec sentences that place surcharges, interest and
compromise penalties out of scope, which is what puts this phase on that path.

Three entries, because three distinct things are being declined and each needs its own anchor:

| Id | Question | Blocks |
|---|---|---|
| `LAWYER-10` | Q10 — the NIRC Sec. 248 surcharge on a late estate-tax return | `PEN-01` |
| `LAWYER-11` | Q11 — the NIRC Sec. 249 interest on late-paid estate tax | `PEN-02` |
| `LAWYER-12` | Q12 — whether a compromise penalty may be computed by an engine at all | `PEN-03` |

Each asks for the four inputs the engine would need in order to compute the line — the rate, the base
it applies to, the date accrual starts, the date accrual stops — or for confirmation that the line
should stay refused. That framing is deliberate and is what makes this plan safe to execute: it asks
the lawyer a question about the engine's scope, and it takes no position on what either section says.
</objective>

<constraints>
- This plan edits three files and creates none. It touches no source file, no test, no gate manifest
  and no baseline.
- Every field value for all three registry objects and every heading for all three agenda entries is
  fixed below. None is composed during execution.
- No numeric rate, percentage, period or peso amount appears anywhere in either file for any of the
  three entries. A sentence containing a rate is the prohibited act, whether it appears in code or in

  in the registry. The agenda's own definition of that value is quoted in each entry and then
  qualified: the engine used to produce a number by omission and no longer does.
- `.planning/LEGAL-CORRECTION-WORKFLOW.md` and `.planning/BLOCKED-REQUIREMENTS.md` are not edited by
  this plan.
- `bash scripts/ci-gates.sh` exits 1 on this branch for reasons this phase does not own. This plan
  runs `node scripts/check-lawyer-agenda.mjs` and makes no claim about the whole suite.
</constraints>

<threat_model>
This plan writes two planning documents and adds three strings to a gate script. It runs no server,
opens no socket and touches nothing reachable from the application.

The hazard is **a recorded question that is really a recorded answer**. An entry that names a rate and
then asks for confirmation has decided the point and disguised the decision as a question, and every
later agent will implement the number it finds in the question. The defence is mechanical rather than
stylistic: no digit-bearing rate and no lettered subsection may appear in either file for these three
entries, and Task 5 greps for exactly that.

The second hazard is **G10 passing for the wrong reason**. Its anchor check requires the pattern to
occur exactly once in the anchor file, and requires that file to carry a matching `LAWYER-DECISION:`
comment, so an anchor pointing at a pattern that appears twice, or at a file with no marker, fails.
That is why this plan is in wave 2: `20-01` must already have created `penalties.ts` with its three
marker lines.

Severity: low for the machine, high for the record. This file is the only place a future agent learns
that the number it is about to write has not been authorised.
</threat_model>
