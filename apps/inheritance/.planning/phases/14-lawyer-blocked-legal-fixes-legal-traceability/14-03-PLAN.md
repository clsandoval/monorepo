<objective>
LAW-06, LAW-07 and LAW-12 cannot be implemented. Each is hard-blocked on a recorded decision that
the lawyer has not answered — the lawyer is sitting the bar examination — and
`.planning/PLAN-STANDARD.md` section 3 prohibits an agent from adopting a reading in the meantime.

The deliverable is therefore not an implementation. It is a committed, machine-checked record that
says, for each of the three requirements, exactly which question it waits on, in the lawyer's own
requested wording, what already exists in the tree, and what turns the answer into a fix. Plus a gate
that keeps that record honest in both directions: it fails when the record drifts from
`.planning/lawyer-decisions.json`, and it fails when an answer has arrived while the requirement is
still open, so a returning owner cannot miss that the work is now unblocked.

The mapping is fixed by `.planning/REQUIREMENTS.md` and by the `LAWYER_BLOCKED` table already
hardcoded in `scripts/check-plan-closed-world.mjs`:

| Requirement | Blocking decision | Question |
|---|---|---|
| LAW-06 | LAWYER-06 | Q6 — donation-excess entitlement, estate pesos or a claim against the donee |
| LAW-07 | LAWYER-04 | Q4 — the reach of *Aquino v. Aquino* into the collateral line |
| LAW-12 | LAWYER-08 | Q8 — RA 11642 Sec. 41 retroactivity to pre-2022 decrees |

This plan transcribes that mapping. It does not create it and does not vary it.
</objective>

<constraints>
- `.planning/LAWYER-AGENDA.md` and `.planning/lawyer-decisions.json` are read-only in this plan. No
  `**Status:**` is advanced, no `- [ ]` Answer box becomes `- [x]`, no `answered_by`, `answered_on`
  or `answer` field is filled. Gate G10 already fails when those two files disagree, and this plan
  must leave `node scripts/check-lawyer-agenda.mjs` exiting 0 exactly as it does today.
- No file under `engine/src/`, `frontend/src/` or `specs/` is edited. Nothing about the three
  blocked readings is implemented, stubbed, defaulted, or flagged behind a config switch.
- Every question text written into `.planning/BLOCKED-REQUIREMENTS.md` is copied verbatim from the
  `### What I need from you` section of the matching entry in `.planning/LAWYER-AGENDA.md`.
  Paraphrasing is prohibited, because a paraphrase of a legal question is already an interpretation.
- `scripts/check-blocked-requirements.mjs` is dependency-free Node ESM using `node:` builtins only.
  It writes no file and has no `--fix`, `--update`, `--accept`, `--regenerate` or waiver flag. Its
  three flags — `--ledger`, `--decisions`, `--requirements` — are read-only path overrides that exist
  so the committed fixtures can drive each failure path.
- The script prints exactly one `GATE-SKIPS total=3 skipped=0` line on every exit path.
- Gate registration is not part of this plan. Plan `14-06` registers this script as gate G26.
- Every commit stages explicit paths through `bash scripts/safe-commit.sh`.
- No point of Philippine law is decided. Guessing is prohibited, adopting whichever reading looks
  defensible is prohibited, and silently taking the option that makes a check green is prohibited.
</constraints>

`STATUS DRIFT` — an entry's `**Registry status:**` value differs from that decision's `status` in
`.planning/lawyer-decisions.json`.

its blocking decision is still `awaiting-answer`.
`ANSWER ARRIVED` — a blocking decision's status is no longer `awaiting-answer` while its requirement
is still unchecked in `.planning/REQUIREMENTS.md`. The message names the decision, the requirement,
and instructs the reader to run the five steps of `.planning/LEGAL-CORRECTION-WORKFLOW.md`. This is a
deliberate red on good news: the answer arriving is exactly the moment the work must start, and a
silent pass would let a month-long unattended loop walk past it.
`BLOCKED LEDGER UNREADABLE` — any of the three inputs is missing or unparseable; exits 1 immediately.

and `GATE-SKIPS total=3 skipped=0` and exits 0. Otherwise it prints the violation list, the same
`GATE-SKIPS` line, and exits 1. There is no other exit code.
