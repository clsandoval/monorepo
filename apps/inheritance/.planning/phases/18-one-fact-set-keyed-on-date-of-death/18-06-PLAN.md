<threat_model>
The highest-consequence mistake available here is **an edit to an existing gate disguised as a
reorder**. A changed command string or a `blocking: true` flipped to `false` inside the same diff that
legitimately renumbers twenty-four gates is exactly the change a reviewer skims past. The defence is
mechanical: Task 2 diffs every pre-existing gate object field-by-field against
`git show HEAD:gates.manifest.json` and asserts the count of non-`order` differences is `0`, and G5
(`node scripts/check-gate-manifest.mjs`) independently refuses any command or blocking change against
the lock.

The second hazard is **registering a gate that cannot run in CI**. The check needs `npx tsx`, which
resolves from `frontend/node_modules` installed by `bash scripts/setup-env.sh`, and the compiled WASM
artifact, which G2 produces two orders earlier. Task 1 asserts both by running the gate through
`scripts/ci-gates.sh`'s own runner rather than by hand, so the precondition and the `cwd` are
exercised as the runner will exercise them.

The third is **documentation drifting from the manifest**, which is the failure G33's
`ORIENTATION GATE COUNT` check exists to catch. Three prose statements carry the count and all three
move in this plan's single commit.

This plan reads and writes repository files only. It opens no socket, contacts no database and touches
no credential.
</threat_model>
