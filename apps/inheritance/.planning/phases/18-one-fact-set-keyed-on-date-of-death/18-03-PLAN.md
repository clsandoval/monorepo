<objective>
FACT-01 says a lawyer enters the date of death exactly once per case, and that neither path offers a
second independently-editable field for it. Plan `18-01` Task 1 measured the one place that violates
this: `frontend/src/components/tax/tabs/DecedentTab.tsx:92-93`, an `<Input type="date">` whose
`onChange` writes `EstateTaxWizardState.decedent.dateOfDeath` — a different field of a different
object, persisted to a different JSONB column than the succession spine.

This plan removes the writer and keeps the reader. The control stays on screen, keeps its
`data-testid="decedent-dod"`, keeps rendering the value, and gains `readOnly` plus a line naming
where the value comes from. Removing the control outright was rejected for two reasons: the date of
death is the single most consequential field on a Form 1801 and a lawyer proof-reading the return
needs to see it, and its `data-testid` is asserted by a committed test and by a committed journey
rubric — deleting it would turn a coverage question into a deletion.

The value it renders is `state.decedent.dateOfDeath`, unchanged from today. Plan `18-04` makes that
field a copy of the succession spine at load time through `applyFactSet`, so after both plans the
rendered value **is** the shared value and there is exactly one writer for it in the whole
application.

This plan does not touch `EstateTaxWizard.tsx`. Its `decedentName` prop and its
`<OrdinaryDeductionsTab dateOfDeath={state.decedent.dateOfDeath}>` wiring are already correct readers
of the wizard state and need no change; plan `18-04` changes what the route feeds them.
</objective>

<constraints>
- `data-testid="decedent-dod"` is preserved verbatim. The committed assertion at
  `frontend/src/components/tax/__tests__/EstateTaxWizard.test.tsx:221` reads that testid and expects
  the value `2024-03-15`; that test is **not** edited by this plan and must stay green as written.
- The input keeps `type="date"`, keeps `id="decedent-dod"`, and keeps rendering
  `value={data.dateOfDeath}`. Only its mutability changes.
- `disabled` is not used. A `disabled` input is excluded from form submission and reads as broken to a
  screen reader; `readOnly` plus `aria-readonly="true"` is the pair that says "this value is shown,
  not edited".
- `DecedentTabProps` is unchanged: `{ data: DecedentDetails; onChange: (data: DecedentDetails) => void }`.
  The `onChange` prop and the local `update` helper stay, because the tab's other eleven fields still
  write through them.
- `isTabValid` in `frontend/src/types/estate-tax.ts` is not edited. It requires

  satisfied by the shared value; when the succession spine is empty the route refuses to compute, so
  an invalid tab 0 and a refusal agree with each other.
- This plan does not edit `frontend/src/routes/`, `frontend/src/components/tax/EstateTaxWizard.tsx`,
  `frontend/src/types/estate-tax.ts`, `frontend/src/lib/`, any gate manifest, any baseline or any

- `node frontend/journey/approve.mjs` is not run for any step by this plan, under any circumstance.
- `bash scripts/ci-gates.sh` exits 1 at G3 on this branch for a reason this phase does not own. This
  plan does not run the whole suite and makes no claim about it.
</constraints>

<threat_model>
The hazard is **a field that looks read-only and is not**, or the inverse: a field a lawyer believes
they corrected while the value silently reverts on the next load. Both produce a Form 1801 keyed on a
date the lawyer did not intend.

Two defences are built in. First, the control loses its `onChange` entirely rather than gaining a
guard inside one — there is no code path left through which a keystroke can reach
`EstateTaxWizardState.decedent.dateOfDeath` from this tab, which Task 2 asserts by typing into the
control and observing that the `onChange` spy was not called. Second, the tab renders a visible line
naming the succession wizard's Decedent step as the place to change it, so the lawyer is told where
the field moved rather than left to discover that typing does nothing.

A third, quieter hazard is a screen-reader user meeting an input that ignores them with no
announcement. `readOnly` plus `aria-readonly="true"` is asserted by Task 2 as attributes on the
element, not merely as a visual treatment.

This plan reads and writes no data, contacts no network and handles no credential.
</threat_model>
