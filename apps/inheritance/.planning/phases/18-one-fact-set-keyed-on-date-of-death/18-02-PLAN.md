<objective>
The seam this phase closes is that two JSONB columns hold two independently-editable dates of death
with no comparison between them. Closing it needs one place that answers three questions and is the
only place that answers them:

1. **What is this case's fact set?** — read from the succession spine, `cases.input_json`.
2. **Do the two stored copies agree?** — compared, with both values carried in the answer.
3. **How does the tax wizard state adopt the shared value?** — one function, applied at load.

This plan writes that place: `frontend/src/lib/fact-set.ts`, plus its unit tests. It is deliberately
the whole of the phase's decision logic, so that plans `18-03`, `18-04` and `18-05` are wiring rather
than reasoning, and so that the gate runner in `18-05` — which sits outside `frontend/tsconfig.json`'s
`include` and is therefore not typechecked by G4 — carries no rule of its own.

`prePopulateFromEngineInput` in `frontend/src/types/estate-tax.ts` is **not** the home for this. Plan
`18-01` Task 1 measured that it has zero production callers, it returns a whole `DecedentDetails`
block that would overwrite the address, citizenship and property-regime fields a lawyer has already
filled in on the tax tab, and it cannot express a refusal. It is left exactly as it is and is not
called by this phase.
</objective>

<constraints>
- The module is `frontend/src/lib/fact-set.ts`. It is pure: no Supabase call, no `fetch`, no
  `localStorage`, no React import, no `console`, and no `process.exit`.
- The spine is `cases.input_json.decedent.date_of_death`. Nothing in this module reads the
  `cases.date_of_death` column, because that column is a projection written by `lib/cases.ts:25,54`
  and a projection is not an authority.
- Every string read out of a JSONB blob is `.trim()`ed exactly once, at read time, and compared as a
  trimmed string. There is no date parsing, no `Date` construction and no timezone handling anywhere
  in this module: both values are ISO-8601 `YYYY-MM-DD` strings that sort and compare
  lexicographically, which is the same treatment `engine/src/flags.rs:65` and
  `frontend/src/types/estate-tax.ts:358` already give them.
- The module never mutates its arguments. `applyFactSet` returns a new object and leaves the input
  state untouched, because the caller holds it in React state.
- `as any` and `as unknown as` are prohibited. Reading an unknown-shaped JSONB blob goes through one
  local helper that narrows with `typeof` checks and a single
  `as Record<string, unknown>` cast, which is a structural narrowing and not a money-unit widening.
- This plan does not edit `frontend/src/routes/`, `frontend/src/components/`,
  `frontend/src/types/estate-tax.ts`, `frontend/src/lib/cases.ts`, any gate manifest or any baseline.
- `bash scripts/ci-gates.sh` exits 1 at G3 on this branch for a reason this phase does not own. This
  plan does not run the whole suite and makes no claim about it.
</constraints>

<threat_model>
The module decides whether a computation proceeds, which makes **a verdict that wrongly returns `ok`**
the whole hazard: it would let a Form 1801 be produced from a date the succession schedule does not
share, which is the exact silent wrongness this product exists to prevent.

Three shapes of that failure are guarded explicitly:

- **Whitespace disagreement read as agreement, or agreement read as disagreement.** Both sides are
  trimmed once at read time, and Task 2 asserts `' 2020-01-01 '` against `'2020-01-01'` returns `ok`.
- **A missing blob read as an empty string and then as agreement.** A null `input_json` yields
  `missing-date`, never `ok`; Task 2 asserts it.
- **A malformed blob throwing at read time**, which a caller would surface as a generic error rather
  than as a refusal. The reader returns `''` for every non-string it meets and never throws; Task 2
  asserts it against a `tax_input_json` of `{}`, of `{ decedent: null }` and of `{ decedent: { dateOfDeath: 5 } }`.

The module handles no credential and reaches no network. Its inputs are rows the caller already
fetched under RLS, so it widens no access.
</threat_model>

<action>
Create `frontend/src/lib/fact-set.ts` exporting exactly these seven bindings, with these signatures
and these rules.

`export interface CaseFactSet { decedentName: string; dateOfDeath: string; }` — the fact set that
crosses the engine boundary. Both fields are trimmed strings; `''` means absent.

`export type FactSetVerdict =` a discriminated union on `kind` with exactly three members:
`{ kind: 'ok'; factSet: CaseFactSet }`,
`{ kind: 'missing-date'; message: string }`,
`{ kind: 'disagreement'; succession: string; tax: string; message: string }`.

`export const FACT_SET_MISSING_DATE_MESSAGE` — the literal string
`Date of death has not been entered for this case. Enter it once on the Decedent step of the succession wizard; the estate-tax return reads it from there.`

`export function factSetConflictMessage(succession: string, tax: string): string` — returns
`` `This case holds two different dates of death. The succession fact set says ${succession} and the stored estate-tax fact set says ${tax}. The estate tax will not be computed until they are the same. Correct the date on the Decedent step of the succession wizard.` `` The two values are interpolated so a refusal always prints both, which is what FACT-04 requires.

`export function factSetFromCaseRow(row: CaseRow): CaseFactSet` — returns
`{ decedentName: <trimmed input_json.decedent.name>, dateOfDeath: <trimmed input_json.decedent.date_of_death> }`,
each `''` when the path is absent or the value is not a string.

`export function storedTaxDateOfDeath(row: CaseRow): string` — returns the trimmed
`tax_input_json.decedent.dateOfDeath`, or `''` when the path is absent or the value is not a string.

`export function assertOneFactSet(row: CaseRow): FactSetVerdict` — four rules, evaluated in this
order and no other:
1. succession date is `''` → `{ kind: 'missing-date', message: FACT_SET_MISSING_DATE_MESSAGE }`.
2. stored tax date is `''` → `{ kind: 'ok', factSet }`. Absence is not disagreement.
3. stored tax date differs from the succession date → `{ kind: 'disagreement', succession, tax, message: factSetConflictMessage(succession, tax) }`.
4. otherwise → `{ kind: 'ok', factSet }`.

`export function applyFactSet(state: EstateTaxWizardState, factSet: CaseFactSet): EstateTaxWizardState`
— returns `{ ...state, decedent: { ...state.decedent, dateOfDeath: factSet.dateOfDeath } }`. It
writes **only** `dateOfDeath`. It does not write `name`, `address`, `citizenship`, `maritalStatus` or
`propertyRegime`: those are BIR-form fields a lawyer fills on the tax tab, and overwriting them at
every load would discard entered work. The decedent's name reaches the tax path as
`CaseFactSet.decedentName` for display, which is what the route already did with a separate state
variable.

Add one private helper `readTrimmedString(value: unknown, ...keys: string[]): string` that walks the
key path with `typeof value === 'object' && value !== null` guards, casts once to
`Record<string, unknown>` to index, and returns `''` for any non-string terminal. It never throws.

Import `CaseRow` from `@/types` and `EstateTaxWizardState` from `@/types/estate-tax`, both with
`import type`.

Open the file with a header comment in the register the other `frontend/src/lib/*.ts` modules use,
stating in its own words: that this module is the single implementation of the one-fact-set rule; that
the spine is `cases.input_json.decedent.date_of_death` and the `cases.date_of_death` column is a
projection of it; that a disagreement is refused and never reconciled by overwriting; and that the
gate enforcing the rule after this phase is `frontend/scripts/check-one-fact-set.ts`.
</action>
