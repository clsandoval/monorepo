<objective>
Plans `18-02` through `18-04` made the two engines share one date of death. Nothing so far stops the
next change from quietly reintroducing a second one — a new tax-side control, a route that computes
without consulting the verdict, or a refactor that drops the comparison. This plan writes the check
that fails when any of those happens, and observes it going red on an injected regression before it is
registered as blocking.

Five assertions, each with its own literal marker so a failure names the rule that broke:

| Marker | What it proves | Requirement |
|---|---|---|
| `SECOND DATE FIELD` | No control anywhere under `frontend/src` writes `EstateTaxWizardState.decedent.dateOfDeath` | FACT-01 |
| `FACT SET NOT SHARED` | The estate-tax route consults the fact set and does not read the projected `decedent_name` column | FACT-02 |
| `DISAGREEMENT NOT REFUSED` | The real rule, run over committed fixture rows, refuses a disagreement and prints both dates | FACT-04 |
| `DATE NOT KEYED TO TAX` | The real tax engine's regime, medical deduction and tax due all move across the TRAIN boundary | FACT-03 |
| `ENGINE INPUT DATE MISMATCH` | The date the tax path reads is byte-identical to the date the compiled succession engine is handed, and the engine really computed | FACT-02, FACT-03 |

Plus two error markers, both refusing to pass:

- `CORPUS EMPTY` — zero fixture rows examined, exit 1.
- `FACT SET CHECK CANNOT RUN:` — the WASM artifact or a fixture is missing or unparseable, exit 2,
  which is the project's distinct "a gate could not run" code from `.planning/PLAN-STANDARD.md` §3.

**Why the succession engine's invariance is not asserted.** `18-BASELINE.md` records that the
succession engine's output does not move with the date of death, over the whole committed corpus.
Asserting that invariance would freeze today's behaviour as a permanent expectation and would turn
this gate red the day question `LAWYER-08` is answered and RA 11642 retroactivity is implemented — a
gate whose correct fix is "weaken me" is a gate that gets weakened. The gate therefore asserts the
date **arrives** at the engine, never that it **changes** the answer.
</objective>

<threat_model>
The single most dangerous outcome available to this design is **a gate that passes because it measured
nothing**. A fixtures directory that silently matched no file, or a WASM load that silently returned
nothing, would print no violations and exit 0 forever, and the phase would ship a check that certifies
its own absence. Three defences: a run examining zero fixture rows exits 1 with `CORPUS EMPTY`; a
missing `.wasm` exits 2 rather than skipping the engine assertion; and the `ENGINE INPUT DATE MISMATCH`
assertion requires a **positive** `per_heir_shares` length, so an engine that returned an empty object
fails rather than passes.

The second hazard is **a gate that can be made green by editing it**. The mitigation is structural:
the script holds no list of tolerated disagreements and no baseline file, so there is no entry to add
when it becomes inconvenient. The correct response to a red run is a BLOCKED report with the pasted
output.

The third is **a source scan that matches its own pattern**. The `SECOND DATE FIELD` scan looks for
`dateOfDeath: e.target.value` under `frontend/src`, and the runner lives under `frontend/scripts`,
outside the scanned root — but the pattern string appears in the runner's own report text, so the
scan takes its root from the `--src` override defaulting to `frontend/src` and never scans
`frontend/scripts`. Task 1's acceptance criteria assert that running the gate against the real tree
reports zero matches while `grep` over `frontend/scripts` finds the literal, proving the scan root is
correctly bounded.

The script reads committed files and a committed WASM binary. It opens no socket, contacts no
database, spawns no subprocess and reads no credential.
</threat_model>
