<objective>
`frontend/src/routes/cases/$caseId.tax.tsx:56` is the whole of the boundary today: it copies
`row.decedent_name` into a `useState` string and copies `row.tax_input_json` straight into wizard
state. Nothing else crosses, and the two stored dates of death are never compared.

This plan makes the route read the case's one fact set, apply its date of death to the tax wizard
state, and refuse to compute when the two stored copies disagree or when there is no date at all —
printing both values on screen rather than producing a return keyed on a date the succession schedule
does not share.

Three rules the date drives are satisfied by this one wiring, and no rule site is edited to achieve
it:

| Rule | Site | How it reads the shared value after this plan |
|---|---|---|
| TRAIN versus pre-TRAIN | `estate-tax-engine/regime-detection.ts` `detectRegime` | `pipeline.ts:131` maps `ws.decedent.dateOfDeath` into `DecedentInfo.dateOfDeath`, and `applyFactSet` makes `ws.decedent.dateOfDeath` the spine's value |
| The TRAIN-repealed medical deduction | `estate-tax-engine/special-deductions.ts` `computeMedicalDeduction` | gated on `deductionRules`, which `detectRegime` derives from the same date |
| RA 11642 retroactivity | `engine/src/flags.rs` `detect_spec_flags` | reads the `EngineInput` the succession wizard already owns, whose `decedent.date_of_death` **is** the spine |

The third row is why this plan edits no engine file. `18-BASELINE.md` records the measurement:
`detect_spec_flags` keys the `RA_11642_RETROACTIVITY` flag on the adoption **decree date**, the
succession engine reads `decedent.date_of_death` at no production site, and the corpus double-compute
found zero outputs that move with the date. Whether the date of death ought to gate that rule is
question `LAWYER-08`, status `awaiting-answer`. This plan routes the shared date into the engine's
input and leaves the rule exactly where the lawyer left it.

The Ordinary Deductions tab is already wired to the same value —
`EstateTaxWizard.tsx:221` passes `dateOfDeath={state.decedent.dateOfDeath}` to
`OrdinaryDeductionsTab`, which calls `getDeductionRules` — so the funeral and judicial-admin fields
appear and vanish with the shared date without any change to either component.
</objective>

<constraints>
- The route imports `factSetFromCaseRow`, `assertOneFactSet`, `applyFactSet` and the
  `CaseFactSet` / `FactSetVerdict` types from `@/lib/fact-set`. It restates no rule: no date
  comparison, no message string and no trimming appears in the route file.
- `applyFactSet` is called **only** when the verdict is `ok`. On a `disagreement` or a `missing-date`
  the loaded state is left exactly as stored, so the banner and the tab show the same values the
  database holds.
- The route never writes `tax_input_json` as part of resolving a disagreement. `updateCaseTaxInput`
  keeps its existing call sites in `handleChange`, `handleApply` and `handleRevert` and gains no new
  one.
- `handleCompute`, `handleApply` and `handleRevert` each return early without computing when the
  verdict is not `ok`. `onCompute` is passed to `EstateTaxWizard` as `undefined` in that case, which
  hides the Compute button because `FilingAmnestyTab.tsx:311` renders it behind `{onCompute && ...}`.
  That is an existing conditional and is not edited.
- `frontend/src/components/tax/EstateTaxWizard.tsx` is **not** edited. Its `decedentName: string` prop
  stays; the route now feeds it `factSet.decedentName` instead of `row.decedent_name`, so the
  committed test `displays the decedent name in header` stays green unedited.
- This plan does not edit `frontend/src/lib/estate-tax-engine/`, `frontend/src/lib/tax-bridge.ts`,
  `frontend/src/lib/cases.ts`, `engine/`, any gate manifest, any baseline or any journey artifact.
- `node frontend/journey/approve.mjs` is not run for any step by this plan, under any circumstance.
- `bash scripts/ci-gates.sh` exits 1 at G3 on this branch for a reason this phase does not own. This
  plan does not run the whole suite and makes no claim about it.
</constraints>

<threat_model>
The hazard with the largest blast radius is **a refusal that fails open**: a verdict computed but not
consulted on one of the three compute entry points, leaving a path by which a disagreeing case still
produces a Form 1801. `handleApply` and `handleRevert` are the easy ones to miss, because both call
`runCompute` indirectly after mutating state. Task 1 gates all three at their own top rather than
gating `runCompute` alone, and the acceptance criteria count the guards rather than describing them.

The second hazard is **a refusal that hides the evidence**. Overwriting the stored tax date with the
succession date would make every case agree forever and would silently discard the date a lawyer
actually typed into the old field. The route therefore has no write path on the refusal branch at
all, which the acceptance criteria assert by counting `updateCaseTaxInput` call sites before and
after.

The third is **a banner that says a disagreement exists without saying what it is**. FACT-04 requires
both values printed; the banner renders them from `verdict.succession` and `verdict.tax` under their
own testids so a test can assert the literal dates rather than the presence of an alert.

The route reads a case row the user already fetched under RLS and writes nothing new, so this plan
widens no access and adds no network call.
</threat_model>
