<objective>
Remove the second scenario classifier from the succession wizard, so that the screenshot gate plan
12-03 adds certifies a correct legal answer rather than a wrong one.

ROADMAP Phase 12 criterion 1 requires the succession-wizard gates to run "only after the
single-classifier fix from Phase 9 is in place". It is not in place: Phase 9's `09-04` is BLOCKED and
`ReviewStep.tsx:34` still defines and calls its own `predictScenario`.

`12-RESEARCH.md` §2 records what that costs, measured with two runs of the committed release binary:

```
./target/release/inheritance-engine < examples/cases/02-married-3lc.json   →  I2
./target/release/inheritance-engine < examples/cases/01-single-lc.json     →  I1
```

`predictScenario` returns `I1` for the first and `I2` for the second. The codes are swapped on the
two most common Philippine family shapes, and the first of those two files is — per
`frontend/supabase/seed.sql:15` — a verbatim copy of the seeded fixture case that every Phase 12
wizard gate will drive. Approving a reference image of that badge would freeze `I1` as the expected
result for a case the engine calls `I2`, and a green gate would then reassert it on every run.

`12-RESEARCH.md` §3 records why this is cheap here and is not what blocked Phase 9. The badge renders
`scenario_code` and nothing else; `scenario_code` already crosses the WASM boundary through the
existing `compute_json` export and the existing `compute()` bridge; and `ReviewStep` already holds a
complete `EngineInput` at line 215. No Rust file is edited, no new WASM export is added, and no claim
about `succession_type` is made anywhere — those three are exactly what `09-01` and `09-04` were
blocked on.

Output: a review screen whose badge is engine-backed, a stable `predicted-scenario` test hook, and
three badge tests strengthened from prefix regexes to exact measured codes.
</objective>
