### The six step records — `frontend/journey/steps/wizard.json`

The file has the same two-key shape as `steps/account.json`: a `$comment` string and a `steps`
array. Every record carries all eleven fields `run.mjs`'s `STEP_FIELDS` requires; an extra or a
missing field is rejected as `STEP FIELD INVALID`.

Common to all six: `"requirement": "JRNY-05"`, `"session": "alpha"`, `"localStorage": {}`,
`"sessionStorage": {}`, `"reset": "case-alpha-no-output"`, `"settleMs": 1200`,
`"allowConsoleErrors": false`. `<ALPHA_CASE>` below is `orgs.alpha.case_id` from
`frontend/supabase/fixtures.json`, written literally in the url because
`scripts/check-journey-registry.mjs`'s `UNKNOWN URL TOKEN` rule checks a url uuid against that file.

| `id` | `url` | single action: `waitForSelector` on | `rubric` |
|---|---|---|---|
| `wizard-estate` | `/cases/<ALPHA_CASE>?step=0` | `[data-testid="estate-step"]` | `wizard-estate.json` |
| `wizard-decedent` | `/cases/<ALPHA_CASE>?step=1` | `[data-testid="decedent-step"]` | `wizard-decedent.json` |
| `wizard-family-tree` | `/cases/<ALPHA_CASE>?step=2` | `[data-testid="family-tree-step"]` | `wizard-family-tree.json` |
| `wizard-will` | `/cases/<ALPHA_CASE>?step=3&hasWill=1` | `[data-testid="will-step"]` | `wizard-will.json` |
| `wizard-donations` | `/cases/<ALPHA_CASE>?step=3` | `[data-testid="donations-step"]` | `wizard-donations.json` |
| `wizard-review` | `/cases/<ALPHA_CASE>?step=4` | `[data-testid="review-step"]` | `wizard-review.json` |

The index arithmetic is transcribed from `readInitialWizardState()`: `WIZARD_STEPS` holds six
entries of which `will` is `conditional`, so without `hasWill` the visible order is
estate, decedent, family-tree, donations, review at indices 0-4, and with `hasWill=1` the will
screen occupies index 3.

### The six rubrics

Each is `{ "rubricId": "<the step id>", "assertions": [ … ] }` and each assertion has a unique `id`
and a `kind` drawn from the eight in `journey/rubric.mjs`. `rubricId` must equal the step id or the
static gate reports `RUBRIC ID MISMATCH`.

Every rubric carries these three, which are the same shape across all six:

| assertion `id` | `kind` | fields |
|---|---|---|
| `step-root-visible` | `element_visible` | the step's root selector from the table above |
| `wrong-step-absent` | `element_absent` | one root selector belonging to a different step, naming a screen that must not be on the page |
| `no-console-error` | `no_console_error` | none |

Each rubric then adds screen-specific assertions, all drawn from text that already exists in the
component and none of which is a peso figure:

- `wizard-estate` — `text_contains` on `[data-testid="estate-step"]` for the heading text
  `EstateStep.tsx` renders.
- `wizard-decedent` — `text_contains` on `[data-testid="decedent-step"]` for the heading text, plus
  `element_visible` on the decedent name input.
- `wizard-family-tree` — `element_count` on the person-card selector, with `expect` equal to `4`,
  the number of `family_tree` entries in the seeded case (one spouse and three legitimate children).
- `wizard-will` — `text_contains` on `[data-testid="will-step"]` for its heading text.
- `wizard-donations` — `text_contains` on `[data-testid="donations-step"]` for its heading text.
- `wizard-review` — `text_equals` on `[data-testid="predicted-scenario"]` with `expect` `"I2"`, plus
  `element_visible` on `[data-testid="compute-distribution"]`, plus `text_contains` on
  `[data-testid="review-step"]` for the literal `Predicted`.

Task 2 reads each component to copy its exact heading string and its exact person-card selector.
No assertion string is composed from memory.
