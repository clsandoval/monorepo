<objective>
Create every runtime-required storage bucket from a migration, and make a hand-made bucket detectable.

Purpose: GATE-07 requires the `firm-logos` bucket and every other runtime-required bucket to be created by a migration file rather than by a manual dashboard action. Today no migration creates any bucket: `grep -l "storage.buckets" frontend/supabase/migrations/*.sql` matches none of the nine migrations, while `frontend/src/lib/firm-profile.ts` calls `supabase.storage.from('firm-logos')` at two call sites. A fresh database therefore has no bucket, and logo upload fails for an environmental reason that looks like a product bug.

The set of runtime-required buckets was measured, not estimated. `grep -rn "storage\.from(" frontend/src` returns exactly the two `firm-logos` call sites and nothing else, and `grep -rn "createBucket" frontend/src` returns zero, so no code path creates a bucket at runtime. `012_pdf_storage.sql` defines a `case_pdfs` table with a `storage_key` column, but `grep -rn "case_pdfs\|storage_key" frontend/src` returns zero hits, so it implies no second bucket. The set has exactly one member. See `03-RESEARCH.md` section 1.3.

Because a count that is right today can be wrong next month, this plan also adds `scripts/check-storage-buckets.mjs`: a static parity check between buckets referenced in code and buckets created by migration. It reads only repo files, so it runs where GitHub Actions runs.

Scope note: this plan does not register the check as a gate. Plan 03-04 owns the next manifest edit and appends its own gate; adding two gates from two plans in two waves to the same two files invites a merge conflict for no benefit. This plan also does not fix the `logo_url`-holds-a-path defect recorded in `03-RESEARCH.md` section 4.3; that is product behavior owned by a later phase.

Output: migration `013_storage_buckets.sql`, `scripts/check-storage-buckets.mjs`, three fixture trees proving the check's verdicts, and a `_MIGRATION_NOTES.md` entry.
</objective>

Resolve default paths relative to the script's own location.

**The referenced set.** Walk `frontend/src` recursively for files ending `.ts` or `.tsx`, skipping any path containing a `__tests__` directory segment. From each file collect bucket names from two patterns:

- `supabase.storage.from('<name>')` and `.storage.from("<name>")` — a literal string argument.
- `.storage.from(<IDENT>)` — an identifier argument. Resolve it by looking for a top-level `const <IDENT> = '<name>'` or `const <IDENT> = "<name>"` assignment in the same file. If the identifier cannot be resolved in that file, that is a violation with marker `UNRESOLVED BUCKET REFERENCE`, naming the file, the line and the identifier. Silently ignoring an unresolved reference would let a bucket escape the check, which is the failure mode this script exists to remove.

**The migrated set.** Read every `.sql` file in `frontend/supabase/migrations` and collect the first single-quoted string following each occurrence of `INSERT INTO storage.buckets`, treating that as the bucket id.

**Comparisons**, collecting all violations:

1. `UNMIGRATED BUCKET` — a referenced name absent from the migrated set. Print the name and the referencing file and line.
2. `ORPHAN BUCKET` — a migrated id absent from the referenced set. Print the id and the migration file. This is a failure rather than a note: in a repo where the runtime set has exactly one member, an unreferenced bucket means the two halves have drifted, and the legitimate way to add a bucket is to add its code reference in the same commit.
3. `UNRESOLVED BUCKET REFERENCE` — as described above.
4. `RUNTIME BUCKET CREATION` — any occurrence of `createBucket(` under `frontend/src` outside a `__tests__` directory. A bucket created at runtime by application code is exactly the hand-made bucket GATE-07 prohibits. The measured count today is 0.

If `frontend/src` or `frontend/supabase/migrations` is missing or unreadable, print a message containing `BUCKET SCAN UNREADABLE` and exit 1. Never exit 0 on an internal error.

Two flags, and no others:
- `--src <dir>` — scan `<dir>` instead of `frontend/src`. Exists so fixtures can drive the failure paths.
- `--migrations <dir>` — scan `<dir>` instead of `frontend/supabase/migrations`.

Exit codes: `0` only when there are zero violations, `1` otherwise. No other exit code.

Success output: a line containing the literal string `BUCKETS OK` plus both counts, in the shape `BUCKETS OK — 1 referenced, 1 migrated`.

This script needs no database, which is the point: it can run wherever the other seven gates run.
