<objective>
Publish machine-readable per-gate results a status page can consume, and document the whole bring-up sequence in one place.

Purpose: GATE-08 requires a gate run to publish machine-readable per-gate results. Today `.gate-runs/latest.json` exists but is gitignored and runner-internal: it carries no gate name, no `proves` text, and no requirement mapping. `scripts/loop-status.mjs` line 170 already records the absence of a gate name as a known limitation. Phase 2's own STATE.md carries the note that Phase 3 extends this precursor into the published format.

GATE-05 requires one documented sequence from a clean checkout to a working environment. Plan 03-01 built the sequence as `scripts/setup-env.sh`; this plan writes it down in `README.md` alongside the local Supabase, the seed fixture and the storage bucket that plans 03-02 and 03-03 added, so a returning developer reads one section rather than four plan summaries.

The design point that matters most: the four run-record statuses — `pass`, `fail`, `cannot-run`, `not-run` — survive into the published file unchanged. Collapsing `not-run` or `cannot-run` into anything resembling a pass is the exact failure GATE-09 exists to prevent, and a published format is where that collapse would otherwise happen unnoticed.

Scope note: this plan does not build a status page. GATE-08's wording is that a gate run publishes results *a status page can consume*; the consumer is out of scope and no phase in the roadmap builds one. This plan does not change any pre-existing locked gate command.

Output: `scripts/publish-gate-results.mjs`, `scripts/check-gate-results.mjs`, a committed `gate-results.json`, gate G9 in the manifest and the lock, publisher calls in the runner, `GATES.md` section 6, a rewritten README setup section, and two fixtures proving the check fires.
</objective>

Create `scripts/check-gate-results.mjs`, a Node ESM script importing only `node:fs` and `node:path`. Follow `scripts/check-gate-manifest.mjs`'s shape: collect every violation, print all of them, exit once.

Checks, in this order, collecting all violations:

1. `RESULTS MISSING` — `gate-results.json` does not exist.
2. `RESULTS UNREADABLE` — it exists but is not parseable JSON, or its `schema` is not the integer `1`.
3. `RESULTS STALE` — its `run.started_at` differs from `.gate-runs/latest.json`'s `started_at`. A results file describing an earlier run is worse than none, because it looks current.
4. `RESULTS INCOMPLETE` — a gate present in `gates.manifest.json` is absent from `gates`; or a gate entry is missing any of the thirteen required keys; or a gate other than `G9` has status `not-run`. `G9` is exempt from that last condition and only that one, because this check *is* gate G9 and its own log entry is still being written while it runs.
5. `RESULTS STATUS INVALID` — a gate `status` outside the four legal values `pass`, `fail`, `cannot-run`, `not-run`, or a requirement `status` outside `pass`, `fail`, `incomplete`.
6. `RESULTS REQUIREMENT DRIFT` — a requirement id appearing in a manifest gate's `requirements` that has no entry in the results `requirements` array, or the reverse.

Exit codes: `0` only when there are zero violations, `1` otherwise. No other exit code.

Success output: a line containing the literal string `RESULTS OK` plus the gate count and the requirement count, in the shape `RESULTS OK — 9 gates, 8 requirements`. Then a `GATE-SKIPS total=<n> skipped=0` line, so this gate is accounted for by the same mechanism plan 03-04 established for every other gate.

Two flags, and no others:
- `--results <path>` — read the results from `<path>`.
- `--run <path>` — read the run record from `<path>`.

This script never writes `gate-results.json`. Constraint 7 forbids it, for the same reason no other check in this project can rewrite its own input.
