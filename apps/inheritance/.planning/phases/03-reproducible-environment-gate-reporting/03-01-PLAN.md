<objective>
Make one command bring up a complete local environment on a machine where another app's Supabase is already running.

Purpose: GATE-05 requires that following one documented sequence from a clean checkout yields a working local environment. Today that is false for a measured reason, not a vague one: `frontend/supabase/config.toml` requests ports 54321, 54322, 54323 and 54324, and all four are currently bound by a sibling monorepo app's Supabase stack. `supabase start` fails to bind, and `frontend/.env.local.example` points `VITE_SUPABASE_URL` at `http://localhost:54321`, which is a different product's database. See `03-RESEARCH.md` sections 1.1 and 1.2 for the full measurement.

This plan moves this app onto the measured-free 55320-55329 block, renames `project_id` from `app` to `inheritance` so its containers are identifiable, and adds two artifacts: `scripts/setup-env.sh`, which performs the bring-up, and `scripts/check-env-ready.mjs`, which only judges it. They are separate files because a script that both performs an action and judges it can always report success for work it did not do.

Scope note: this plan does not create `seed.sql` (plan 03-03), does not create the storage-bucket migration (plan 03-02), and does not register `check-env-ready.mjs` as a gate. That registration needs Docker and a running stack, which GitHub Actions does not have, and it belongs to Phase 11 where the DB-touching journey gates live. This plan does not modify `scripts/ci-gates.sh`, `gates.manifest.json`, or `gates.manifest.lock`.

Output: a de-conflicted `config.toml`, a corrected env template, an ignored `.env.local`, `scripts/setup-env.sh`, and `scripts/check-env-ready.mjs`.
</objective>

  <action>
Create `scripts/setup-env.sh`, an executable Bash script with `set -euo pipefail`. Read `engine/build-wasm.sh` first and follow its shape: a header comment stating the one command it is, preflight checks that fail loudly with an install hint, then the work, then verification of the work.

Header comment must state that this is the single documented bring-up command, that it is invoked as `bash apps/inheritance/scripts/setup-env.sh`, and that it is idempotent — running it twice is safe and the second run is fast.

Resolve `APP_DIR` from the script's own location the same way `scripts/ci-gates.sh` does, so the script works from any working directory.

Steps, in this exact order:

1. **Docker preflight.** If `docker` is absent from `PATH`, or `docker info` exits nonzero, print `SETUP CANNOT RUN: docker daemon unreachable` to stderr and exit 2. Do not attempt to install or start Docker; installing a container runtime is outside this script's authority. Exit code 2 matches the cannot-run meaning already established by `scripts/ci-gates.sh`.

2. **Rust WASM target.** If `rustup target list --installed` does not list `wasm32-unknown-unknown`, run `rustup target add wasm32-unknown-unknown`. If `rustup` itself is absent, print `SETUP CANNOT RUN: rustup not found — install from https://rustup.rs` and exit 2.

3. **wasm-pack.** If `wasm-pack` is absent from `PATH`, run `cargo install wasm-pack`. If `cargo` is absent, print `SETUP CANNOT RUN: cargo not found — install from https://rustup.rs` and exit 2.

4. **Frontend dependencies.** If `frontend/node_modules` does not exist, run `npm ci` from `frontend/`.

5. **Supabase CLI, pinned to 2.110.0.** If `supabase` is absent from `PATH`, or `supabase --version` does not print exactly `2.110.0`, download `https://github.com/supabase/cli/releases/download/v2.110.0/supabase_linux_amd64.tar.gz` with `curl -fsSL` into a temporary directory, extract it with `tar -xzf`, move the extracted `supabase` binary to `$HOME/.local/bin/supabase`, and `chmod +x` it. Create `$HOME/.local/bin` first if it does not exist. After installing, if `$HOME/.local/bin` is not on `PATH`, print a line telling the operator to add it and continue by invoking the binary through its absolute path for the rest of this script. Pinning is deliberate: the CLI version determines the Postgres, GoTrue and storage-service images, so an unpinned CLI silently changes what the local environment means between two runs of this same script.

6. **Start the stack.** Run `supabase start` from `frontend/`. If it exits nonzero, print the captured output, then print `SETUP CANNOT RUN: supabase start failed` and exit 2. Before starting, check whether a container named `supabase_db_inheritance` is already running with `docker ps --filter name=supabase_db_inheritance --format '{{.Names}}'`; if it is, skip the start and print `Supabase already running for project inheritance` — this is what makes the script idempotent.

7. **Write `frontend/.env.local`.** Run `supabase status -o env` from `frontend/` and capture its output. It emits shell-style assignments including `API_URL` and `ANON_KEY`. Write `frontend/.env.local` containing exactly four lines: `VITE_SUPABASE_URL=` set to the captured `API_URL`, `VITE_SUPABASE_ANON_KEY=` set to the captured `ANON_KEY`, `VITE_APP_URL=http://localhost:5173`, and a leading comment line stating that this file is generated by `scripts/setup-env.sh` and is gitignored. Overwrite the file if it already exists. Do not write `SERVICE_ROLE_KEY` into it — nothing in `frontend/src` reads a service-role key, and a service-role key in a Vite env file is shipped to the browser.

8. **Build the WASM artifact.** Run `bash engine/build-wasm.sh`.

9. **Verify.** Run `node scripts/check-env-ready.mjs` and propagate its exit code. Print `SETUP COMPLETE` on success.

The script must not run `supabase db reset`. Plans 03-02 and 03-03 own the database contents, and a bring-up script that silently drops the developer's local data is a hazard rather than a convenience.

`chmod +x scripts/setup-env.sh` after writing it.

Create `scripts/check-env-ready.mjs`, a Node ESM script importing only `node:fs`, `node:path`, `node:net` and `node:child_process`. Read `scripts/check-gate-manifest.mjs` first and follow its shape exactly: collect every violation rather than returning on the first, print all of them, then exit once.

Resolve every path relative to the script's own location so it works from any working directory.

**Do not hardcode ports.** Read `frontend/supabase/config.toml` and extract the `[api]` port and the `[db]` port with a line-oriented parse: track the current section header, and read the first `port` key inside each target section. Hardcoding would let the config and the check drift apart, which is the exact failure this phase exists to remove.

Checks, in this order, collecting all failures:

1. `DOCKER UNREACHABLE` — `docker info` exits nonzero, or `docker` is not on `PATH`.
2. `CLI MISSING` — `supabase --version` does not exit 0.
3. `CLI VERSION` — `supabase --version` exits 0 but does not print exactly `2.110.0`. Print both the expected and the observed version.
4. `STACK DOWN` — no running container is named `supabase_db_inheritance`, checked with `docker ps --filter name=supabase_db_inheritance --format {{.Names}}`.
5. `PORT CLOSED` — a TCP connect to `127.0.0.1` on the api port from the config, or on the db port from the config, does not succeed within 2000 milliseconds. Report each closed port separately, naming the port number and which service it belongs to.
6. `ENV FILE MISSING` — `frontend/.env.local` does not exist.
7. `ENV FILE INCOMPLETE` — `frontend/.env.local` exists but lacks a `VITE_SUPABASE_URL=` line, lacks a `VITE_SUPABASE_ANON_KEY=` line, or its anon-key value is shorter than 20 characters. A placeholder left in place is not a configured environment.
8. `ENV URL MISMATCH` — the `VITE_SUPABASE_URL` value's port differs from the `[api]` port read from the config.
9. `DEPS MISSING` — `frontend/node_modules` does not exist.
10. `WASM MISSING` — `frontend/src/wasm/pkg/inheritance_engine_bg.wasm` does not exist.

Two flags, and no others:
- `--api-port <n>` — override the api port read from the config. Exists so the `PORT CLOSED` path can be driven without stopping the stack.
- `--config <path>` — read the config from `<path>` instead of `frontend/supabase/config.toml`.

Exit codes: `0` only when there are zero failures, `1` otherwise. No other exit code.

Success output: a single line containing the literal string `ENV READY` plus the api port, the db port and the container name, in the shape `ENV READY — api 55321, db 55322, container supabase_db_inheritance`.

Failure output: one line per failure, each beginning with `ENV NOT READY: ` followed by the marker and the detail, then a final line naming the fix: `Run: bash scripts/setup-env.sh`.

This script must never install, start, reset, or write. It has no `--fix`, `--install`, `--start`, `--repair`, or `--update` flag, and it calls no `writeFileSync`. Constraint 7 forbids all of it. The reason is the same one that keeps an update flag off `scripts/check-gate-manifest.mjs`: a check that can repair what it inspects will eventually report success for work it performed rather than work that was there.
