<objective>
Write the procedure that turns a lawyer's "this is wrong" into a named test vector, a failing gate,
and a fix — and close the dangling reference Phase 2 deliberately left behind.

Purpose: ROADMAP Phase 4 criterion 4 requires a written workflow for exactly that path. Without it,
the first correction that arrives becomes an ad-hoc code change by whichever agent is holding the
context at the time, with no vector, no gate, and no record of which reading now governs — which is
the silent-wrongness failure this whole project exists to prevent.

There is also a dangling reference to close. `.planning/PLAN-STANDARD.md:180-183` tells an executor
hitting a point of law to append to `.planning/LAWYER-AGENDA.md`, "create it with the single heading
line `# Lawyer Review Agenda` if it does not exist", and notes that Phase 4 owns the file's full
structure. As of plan 04-04 that structure exists and is gate-enforced, so the instruction is
updated to describe appending into a structured file that a gate now checks.

The step order matters and is fixed rather than discovered: naming the vector comes **before** the
fix. A fix without a vector is a silent change to a legal number, which this project ranks as worse
than a loud failure.

Output: `.planning/LEGAL-CORRECTION-WORKFLOW.md`, an updated `PLAN-STANDARD.md` section 3, and a
`README.md` pointer.

Create `.planning/LEGAL-CORRECTION-WORKFLOW.md`, opening with the level-one heading
`# Legal Correction Workflow` and a one-paragraph statement of what it is for: the single procedure
by which a lawyer's correction, or an answer to one of the eight recorded decisions, becomes a change
in this codebase. State that no other path exists, and that a legal change made outside this
procedure is a silent change to a peso figure.

**Section `## When this workflow applies`.** Three triggers, listed:
1. The lawyer answers one of the eight entries in `.planning/LAWYER-AGENDA.md`.
2. The lawyer says an output is wrong, whether or not it maps to an existing entry.
3. An executor reports BLOCKED on a point of law per `.planning/PLAN-STANDARD.md` section 3, and the
   owner obtains an answer.

**Section `## The five steps`.** Each step is a level-three heading with a fixed name, and each
states the exact artifact it produces.

`### Step 1 — Record the claim, change no code`
Append the lawyer's words to `.planning/LAWYER-AGENDA.md`, quoted rather than paraphrased. If the
claim matches one of the eight existing entries, it goes into that entry's `Notes:` field. If it does
not, a new entry is appended using the same eight-heading structure with the next free id
`LAWYER-09`, `LAWYER-10`, and so on, and a matching object is added to
`.planning/lawyer-decisions.json`. State plainly: no source file is edited in this step. Paraphrasing
is prohibited, because a paraphrase of a legal correction is already an interpretation.

`### Step 2 — Name a test vector`
Every correction gets exactly one test vector id, formatted `TV-L<NN>` with `NN` zero-padded from
`01`, allocated in order and never reused. `TV-L` distinguishes a lawyer-driven vector from the
spec's existing `TV-01` … `TV-23` series in `engine/tests/integration.rs`. The vector is written as a
test function whose name contains both the vector id and the governing article, following the
existing convention in `engine/tests/integration.rs` where integration tests are one function per
spec vector. Record the vector id in the decision's `vectors` array in
`.planning/lawyer-decisions.json`. State the rule: a correction with no vector is an opinion; a
correction with a vector is a regression test.

`### Step 3 — Watch it fail`
Run the vector and confirm it fails **before** any fix. For an engine vector the command is
`cd engine && cargo test <vector id>`; for a frontend vector it is
`cd frontend && npx vitest run -t <vector id>`. Record the failure output in the plan or the summary
that carries the fix. A vector that passes before the fix is testing something other than the
correction, and the correct response is to rewrite the vector rather than to proceed.

`### Step 4 — Fix in exactly one place`
`EXT-02` forbids a legal rule from being implemented in more than one place, so the fix lands at one
site. Name the two places to look before editing: the decision's `anchors` in
`.planning/lawyer-decisions.json`, and its `LAWYER-DECISION` marker comment in the source. State that
the fix must not weaken or delete an existing test to accommodate itself, and that if the fix cannot
be made without doing so, the correct output is a BLOCKED report.

`### Step 5 — Close the loop`
Set the decision's `status` to `confirmed` or `changed`, and fill `answered_by`, `answered_on` and
`answer` with the lawyer's name, the date, and the answer in the lawyer's own words. Update the
matching agenda entry's `**Status:**` line and tick the box the lawyer chose. Then run
`node scripts/check-lawyer-agenda.mjs` and `bash scripts/ci-gates.sh`, and confirm both exit 0.
State the enforcement plainly: `DECISION STATUS INVALID` fails the build when a status other than
`awaiting-answer` carries no answer fields, so this step cannot be skipped by an agent in a hurry.

**Section `## What an agent may never do`.** Four prohibitions, each one line:
- Advance a decision's `status` without an answer recorded from the lawyer.
- Change a rule anchored by a decision whose `status` is `awaiting-answer` — that is the situation
  `LAW-06`, `LAW-07` and `LAW-12` are blocked on, and the correct output is BLOCKED.
- Delete, skip or weaken a test or an assertion to accommodate a legal fix.
- Paraphrase the lawyer's words into the record.

**Section `## Worked example`.** Walk `LAWYER-04` through all five steps end to end, using the
already-recorded facts and no invented ones: the lawyer confirms Reading A; the vector is `TV-L01`
citing Art. 992; it fails because no barrier exists today; the fix lands at
`engine/src/step1_classify.rs` where `LAWYER-DECISION: LAWYER-04` already sits; the status becomes
`confirmed` and `LAW-07` unblocks. Label the example as illustrative and state that no answer to
`LAWYER-04` has been received.

**Section `## Where this fits`.** One short table mapping this document to its neighbours:
`.planning/LAWYER-AGENDA.md` is what the lawyer answers, `.planning/lawyer-decisions.json` is what
gate `G10` checks, `GATES.md` section 8 explains the gate, `.planning/PLAN-STANDARD.md` section 3 is
where an executor is told to stop, and `EXT-06` in Phase 15 covers adding a brand-new legal rule
rather than correcting an existing one.
