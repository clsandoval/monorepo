<objective>
Turn the recorded decisions into an enforced control: a gate that fails the build when the agenda and
the registry disagree, when a decision's link to its code rots, or when a status advances without an
answer attached.

Purpose: ROADMAP Phase 4 criterion 2 requires the recorded decisions to be machine-readable and
linked from the rule they govern "so no agent re-decides it later." Plan 04-03 built both links. A
link with nothing checking it decays on the first refactor, and decays silently. This plan is what
makes the decay loud.

The single most important verdict is `DECISION STATUS INVALID`. Three requirements — `LAW-06`,
`LAW-07`, `LAW-12` in Phase 14 — are hard-blocked on a lawyer's answer, and the cheapest way for a
future agent to unblock itself is to edit one word of JSON. Requiring `answered_by`, `answered_on`
and `answer` alongside any status other than `awaiting-answer` means an agent cannot advance a
status without writing down a person, a date and a sentence that a human reading the diff sees.

One structural finding from `04-RESEARCH.md` section 1.5 shapes the registration:
`scripts/check-gate-results.mjs` fails with `RESULTS INCOMPLETE` when any gate other than itself is
`not-run`, and `scripts/ci-gates.sh` republishes after every gate — so a gate placed after `G9` would
fail `G9` on every run. `G9` must stay last. `G10` therefore takes `order: 8`, `G8` moves to
`order: 9`, and `G9` moves to `order: 10`. `order` is deliberately not locked, and placing `G10`
before the skip-accounting gate is strictly stronger: its own `GATE-SKIPS` line gets checked.

Output: `scripts/check-lawyer-agenda.mjs`, seven fixtures, gate `G10`, `GATES.md` section 8, and an
updated `README.md`.
</objective>

**Defaults.** `--registry` defaults to `.planning/lawyer-decisions.json`; `--agenda` defaults to
`.planning/LAWYER-AGENDA.md`. Anchor `file` values always resolve against the app directory and are
never overridable, which is what lets a fixture registry point an anchor at a fixture source file.

**The eight required ids** are `LAWYER-01` through `LAWYER-08`, hardcoded as a top-level `const`
array so the expected set is auditable in one place rather than inferred from whichever file is
being checked.

**The fourteen required keys** per decision, also a top-level `const` array: `id`, `question`,
`title`, `articles`, `authority`, `reading_implemented`, `status`, `blocks`, `agenda_section`,
`anchors`, `vectors`, `answered_by`, `answered_on`, `answer`.

**The three valid statuses**, a third top-level `const` array: `awaiting-answer`, `confirmed`,
`changed`.

**Seven verdicts, each with its own literal marker, all collected before exiting once:**

1. `AGENDA ENTRY MISSING` — one of the eight ids has no entry in the registry, or no `## <id>`
   heading in the agenda. Report the id and which of the two files lacks it.
2. `DECISION FIELD MISSING` — a registry entry lacks one of the fourteen keys, or carries a key not
   in the list. Report the id and the key names.
3. `DECISION STATUS INVALID` — `status` is outside the three valid values, or `status` is not
   `awaiting-answer` while any of `answered_by`, `answered_on`, `answer` is `null` or an empty
   string. Report the id, the status, and which answer fields are absent.
4. `DECISION ANCHOR BROKEN` — an anchor's `file` does not exist, or its `pattern` occurs in that file
   a number of times other than exactly one. Report the id, the file, the pattern and the observed
   count. A count of zero means the rule moved or was renamed; a count above one means the anchor no
   longer identifies a single location. Both are failures.
5. `DECISION MARKER MISSING` — an anchor's file does not contain the literal string
   `LAWYER-DECISION: <id>`. Report the id and the file.
6. `AGENDA DRIFT` — the agenda and the registry disagree. Three comparisons, each reported
   separately: the id sets differ; the agenda entry's `**Engine implements:**` value differs from the
   registry's `reading_implemented`; the agenda entry's `**Status:**` value differs from the
   registry's `status`. Parse the agenda by locating each `## <id>` heading and reading the bold
   metadata lines that follow it, up to the next `## ` heading.
7. `AGENDA SCAN UNREADABLE` — an input file is missing or unparseable, an anchor entry lacks `file`
   or `pattern`, or `decisions` is not an array. Print the message and exit 1 immediately. Never exit
   0 on an internal error.

**Pattern matching is literal, never regular-expression.** Use `String.prototype.split` on the
pattern and count the resulting segments, or an equivalent literal scan. Anchor patterns contain
parentheses, `+`, `*` and `.`, all of which are regex metacharacters, and treating them as a regex
would silently change what is being matched.

**Output on success:** a line containing the literal string `AGENDA OK` plus three counts, in the
shape `AGENDA OK — 8 decisions, 10 anchors, 8 awaiting-answer`. Then a second line
`GATE-SKIPS total=<n> skipped=0`, where `<n>` is the number of decisions checked. This line is
printed on **every** exit path, success and failure alike, immediately before the script exits —
gate `G8` fails with `SKIP REPORT MISSING` on a log that lacks it, and with `SKIP COUNT MISMATCH` on
any value other than `skipped=0`.

**Exit codes:** `0` only when there are zero violations, `1` otherwise. No other exit code.

The script must never write to `.planning/lawyer-decisions.json`, `.planning/LAWYER-AGENDA.md`, or
any other file. Constraint 6 forbids an update flag for the reason already established for
`scripts/check-gate-manifest.mjs`: a check that can rewrite its own baseline is not a check.
