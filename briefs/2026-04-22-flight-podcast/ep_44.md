ARK: Verbatim. Raw words. No LLM at ingestion. No extraction. No "the user prefers PostgreSQL" fact cards. The conversation goes into the store as the conversation was said, with a little framing-noise stripped, and then semantic search plus BM25 does the lifting at query time.

RED: Hmm. Okay so my README misread is actually the thesis of the repo running the other way.

And the Japanese word for today is basically the name of the library — "[JP: 記憶 (きおく) — memory]". 記憶. 「この repo は 記憶 を保存し、操作し、取り出す」 — this repo stores, manipulates, and retrieves memory. 「次の三十分、この単語を頭に置いてほしい」 — keep that word in your head for the next thirty minutes. 「architecture のどの軸も、記憶 を別の角度から見ているだけだ」 — every axis of the architecture is just a different angle on memory.

--- [new core — architecture] ---

ARK: Six axes. Compute topology, LLM locus, tool mechanics, extension loading, context and memory strategy, and scaling. And I'm going to spend most of our time on axis five — memory strategy — because that's where the empirical finding lives. The other five are context for it.

RED: Copy.

ARK: Axis one. Compute topology. MemPalace is a Python library plus two thin process wrappers. One CLI — `mempalace = mempalace.cli:main`. One MCP stdio server — `mempalace-mcp = mempalace.mcp_server:main`. The typical deployment is: Claude Code spawns the MCP server as a subprocess, the server reads and writes a local palace directory through `ChromaBackend`, and when the caller dies the server dies with it. No daemon. No network port.

RED: So a "[JP: 倉庫 (そうこ) — warehouse]" on your laptop, basically.

ARK: そうそう — 倉庫 is actually a decent frame for it. 「palace directory が 倉庫 だ」 — the palace directory is the warehouse. 「その中で ChromaDB が persistence を持つ」 — inside it, ChromaDB owns persistence. 「MCP server は、agent が入ってこられる前の小さな扉だ」 — the MCP server is a little door at the front that lets an agent walk in. One detail that tells you someone has actually shipped an MCP server before — `mempalace/mcp_server.py` has a preamble that fd-level-redirects stdout to stderr before importing chromadb and onnxruntime.

RED: Why?

ARK: Because those libraries print banners on import. And MCP stdio multiplexes the JSON-RPC protocol over stdout. If chromadb prints "Anonymized telemetry enabled" on your JSON-RPC channel, your client barfs. So they intercept at the file-descriptor level before the heavy imports.

RED: That's the kind of thing you learn the hard way.

ARK: That's exactly the kind of thing. やっぱり — 「一度噛まれない限り、そんな preamble は書かない」 — as long as you haven't been bitten once, you don't write that preamble.

RED: Okay. Axis two — LLM locus.

ARK: Core retrieval path uses zero LLM. Default embedder is ChromaDB's `all-MiniLM-L6-v2` — 384-dim, local, runs on CPU. Optional fastembed models — `bge-base`, `bge-large`, `nomic`, `mxbai` — are flagged in `benchmarks/longmemeval_bench.py` via `--embed-model`. An LLM only enters the pipeline at two optional sites — the rerank stage in hybrid benchmark mode, and `mempalace/closet_llm.py` / `fact_checker.py` for enrichment.

RED: And the rerank is model-agnostic.

ARK: Model-agnostic. They reproduce the number with Haiku, Sonnet, and a minimax-m2.7 running locally through Ollama. The `pyproject.toml` hard dependencies are literally just `chromadb` and `pyyaml`. No provider SDK. "Works offline, no API key, one dependency" is the product story, and the code lives up to it.

RED: 確かに. That's honest. Axis three — tool mechanics.

ARK: The MCP surface in `mempalace/mcp_server.py` is about 29 tools. Reads — `mempalace_status`, `mempalace_list_wings`, `mempalace_list_rooms`, `mempalace_get_taxonomy`, `mempalace_search`, `mempalace_check_duplicate`. Writes — `mempalace_add_drawer`, `mempalace_delete_drawer`. Maintenance — `mempalace_reconnect`. CLI has the parallel subcommands — `mempalace mine`, `mempalace search`, `mempalace wake-up`, `mempalace init`.

RED: Wings, rooms, drawers. That's the taxonomy.

ARK: That's the 倉庫 taxonomy. We'll get into it on axis five. Under the hood every tool routes through `mempalace/palace.py` — specifically `get_collection` and `get_closets_collection` — which return a `BaseCollection` from the backend registry. The primitives are just `query`, `get`, `add`, `delete` on a typed collection interface defined in `mempalace/backends/base.py`. `QueryResult`, `GetResult`, `PalaceRef`. The MCP layer is thin. The semantics live in the backend contract.

RED: So if I ever wanted to swap ChromaDB for Qdrant, I'd implement that interface.

ARK: Exactly that. Which leads to axis four — extension loading. 「`pyproject.toml` で entry-point group を二つ宣言している」 — the package declares two entry-point groups in that file. 「`mempalace.backends` は vector store 用」 — backends for vector stores. 「`mempalace.sources` は RFC 002 の source adapter 用で、新しい content type を mine するためのもの」 — sources for RFC 002 adapters, new content types to mine from. 「in-tree の backend は `ChromaBackend` だけ」 — only ChromaBackend is in-tree. 「でも、Qdrant、Weaviate、server-mode Chroma を足す配管は、"entry point を登録して wheel を出荷する" だけ」 — but the plumbing to add those is just "register an entry point, ship a wheel". Plugin architecture by the book.

RED: なるほど. Library, CLI, MCP server, all from the same package.

ARK: Hybrid distribution. First-class MCP. The MCP server is not grafted on — it's a peer.

RED: Okay. Axis five. Memory strategy. Where the thesis lives.

ARK: Here we go. Three sub-pieces — verbatim storage, the taxonomy schema, and the retrieval algorithm. Then we'll talk about how the 96.6 number gets operationalized. I'll spend real time here.

Piece one. Verbatim. `mempalace/palace.py` defines a `NORMALIZE_VERSION = 2` constant. Its only job is to strip framing noise — system tags, hook chrome — from Claude Code JSONL before storage. The actual conversational content is never summarized, paraphrased, or extracted. "保つ"  —

RED: "[JP: 保つ (たもつ) — to keep; to maintain]"

ARK: 保つ — that's what the storage layer does to your words. It keeps them. 「"I prefer PostgreSQL because the MVCC story is cleaner than MySQL's" と言ったら、そのまま store に入る」 — if you say that sentence, it goes into the store as-is. 「`{user_pref: "PostgreSQL", reason: "MVCC"}` には変換されない」 — it doesn't get converted into that fact card. 「元の文は 保たれる」 — the original sentence is preserved.

RED: And when `NORMALIZE_VERSION` bumps?

ARK: The mining pipeline detects drawers stored under an older version and silently rebuilds. Users don't re-mine. The 記憶 gets re-normalized as the normalization rules evolve. That's a quiet quality-of-life thing.

RED: Why does verbatim beat extracted, though? Intuitively I'd expect extracted memories to be more retrievable — smaller, cleaner, no noise.

ARK: That's the intuition that the whole Mem0 / Mastra / Supermemory / Hindsight generation of the space runs on. Extract facts at ingestion, index facts, query facts. 「MemPalace の経験的な主張は ― 抽出は情報を壊す、ということだ」 — MemPalace's empirical claim is that extraction destroys information. 「`benchmarks/longmemeval_bench.py` で再現できる」 — you can reproduce it from that harness. 「捨てた "noise" が、時には答えそのものだ」 — the "noise" you throw away is sometimes the answer itself. 比較 — 

RED: "[JP: 比較 (ひかく) — comparison]"

ARK: 比較 — that's what `benchmarks/BENCHMARKS.md` does. It puts raw verbatim next to extracted-memory systems on the same LongMemEval split. And raw verbatim wins. Not by a little — by fifteen to twenty-five points of R@5. The hypothesis the repo states out loud is "raw verbatim with good embeddings is a stronger baseline than anyone realized — because it doesn't lose information."

RED: Huh. That's a finding.

ARK: That IS the finding. Let's sit with it for a second. 「AI-memory の分野は二年間、ingestion に LLM が必要だと仮定してきた」 — the AI-memory space spent two years assuming you needed an LLM at ingestion. 「intelligent compression のために LLM を入れる、という前提」 — putting an LLM in for intelligent compression, that was the assumption. 「この repo はそれに対してこう言う ― 22MB の MiniLM と BM25 で勝てる」 — this repo says: a 22-megabyte MiniLM and BM25 can beat you. 「なぜなら、ingestion で signal を捨てなかったからだ」 — because they didn't throw away signal at ingestion.

RED: Okay, piece two — taxonomy.

ARK: Three-level hierarchy. Wings are people or projects. Rooms are topics inside a wing. Drawers are the chunks — the actual content. `build_where_filter` in `mempalace/searcher.py` shows the ChromaDB `$and` predicate that scopes a query to a wing or room. So the 倉庫 is not flat — it has floors and aisles and shelves. Plus a second collection, `mempalace_closets`, which holds compact pointer documents. Format is roughly `topic | entities | → drawer_id_a, drawer_id_b`. Closets are a topical index that points into drawers.

RED: And a third store —

ARK: A third store, SQLite-backed, powers the temporal entity-relationship graph in `mempalace/knowledge_graph.py`. Validity windows. Facts can be invalidated rather than destructively overwritten. So if "Red works at Company A" becomes false on 2026-04-01, the old edge stays in the graph with an end-date; it doesn't get deleted. The 記憶 is append-mostly, not overwrite.

RED: That preserves history.

ARK: Preserves history — and lets the retrieval path reason about "what was true when."

RED: Piece three. Retrieval algorithm.

ARK: `mempalace/searcher.py`. This is where I got most impressed, actually. Hybrid ranking. Drawer-level vector query is the floor — quote, "always runs." Closet hits can only boost. Closets are explicitly a ranking signal, NOT a gate. Which means if you have a noisy closet — some hallucinated topic pointer — it cannot hide a drawer that the direct vector path would have found.

RED: Why is that a big deal?

ARK: Because the naive design is to use closets as a filter. "Find the matching closet, then look inside." That's fast, and it's wrong under noise. The moment your closet index has a bad pointer, you've made certain drawers unreachable. By making closets signal-only, they get the speed benefit when the closet is good and lose nothing when it's bad. That's a careful design decision. It shows up in `_CLOSET_DRAWER_REF_RE` and `_extract_drawer_ids_from_closet` in `searcher.py` — the regex matches pointer rows, and the extracted IDs go into a boost map, not a whitelist.

RED: なるほど. Signal not gate.

ARK: Signal not gate. And then the `_hybrid_rank` function is a convex combination — vector similarity plus BM25. Vector similarity is `max(0, 1 - distance)` over ChromaDB's cosine distance. BM25 uses smoothed IDF over the candidate set — `log((N - df + 0.5) / (df + 0.5) + 1)`. That's textbook Okapi. BM25 scores get min-max normalized so they live on the same scale as vector sims, and then the weights — 0.6 vector, 0.4 BM25 by default — are actually commensurable.

RED: That normalization matters.

ARK: It matters a lot. A lot of naive hybrid systems add raw BM25 to raw cosine and the BM25 side dominates or vanishes depending on corpus size. This one normalizes first. 正確 — 

RED: "[JP: 正確 (せいかく) — accuracy; precision]"

ARK: 正確 — accuracy. 「正規化が買ってくれるのは、corpus size を越えた精度だ」 — what the normalization buys is precision across corpus sizes. 「drawers が 5 でも 50000 でも、hybrid の重みが同じ意味を持つ」 — whether you have 5 drawers or 50,000, the hybrid weights mean the same thing.

RED: And when a drawer hits, what comes back?

ARK: `_expand_with_neighbors`. It fetches the plus-or-minus-radius sibling chunks from the same source file. So retrieval doesn't clip mid-thought. If your matched drawer is chunk 17 of a transcript, you get 16, 17, 18 back. Small thing, real UX gain over naive chunk retrieval.

RED: That's the kind of polish you only add after watching real queries.

ARK: Exactly. 「誰かが query を実行して、文の途中で切れる問題を見た」 — somebody ran queries and saw the mid-sentence clip problem. 「それから `_expand_with_neighbors` を書いた ― 経験から出てきた code だ」 — then wrote that function — code that came out of lived experience.

RED: Context budget — wake-up protocol.

ARK: `mempalace/layers.py`. Four layers. Layer 0 is about 100 tokens — `~/.mempalace/identity.txt`. Always loaded. Layer 1 is 500 to 800 tokens — top moments. Always loaded. Layer 2 loads on demand per wing or room. Layer 3 is unbounded semantic search. Total wake-up budget — 600 to 900 tokens. Leaves 95 percent of the model's context window free.

RED: So the agent boots with a tiny 記憶 footprint and pulls more when it needs to 思い出す.

ARK: 思い出す on demand. That's the exact shape. 「layers に名前が付いている限り、heuristics は prompt engineering の中に隠れない」 — as long as the layers are named, the heuristics don't hide inside prompt engineering. 「Layer 1 を指して "これが常に loaded される" と言える」 — you can point at Layer 1 and say "this is what always loads". 「context budget に対する誠実さだ、多くの memory system が提供しない種類の」 — it's a kind of honesty about the context budget most memory systems don't offer.

RED: Okay. How does the 96.6 get operationalized? Walk me through the harness.

ARK: `benchmarks/longmemeval_bench.py`. Source of truth. For each of the 500 LongMemEval questions — it's a published benchmark, `longmemeval_s_cleaned.json` is the dataset — the harness builds a fresh ephemeral ChromaDB collection from that question's haystack sessions. Queries the collection with the question text. Scores with `recall_any`, `recall_all`, and `nDCG`.

RED: Fresh collection per question — why?

ARK: To prevent cross-question leakage. 「各質問は dataset の中で自分の haystack を持っている」 — each question has its own haystack in the dataset. 「質問間で collection を共有する限り、他の質問の haystack から retrieve してしまう」 — as long as you share a collection across questions, you'd retrieve from other questions' haystacks. 「それは benchmark が測っているものではない」 — that's not what the benchmark measures. 「fresh な ephemeral collection が、正確 なやり方だ」 — a fresh ephemeral collection is the accurate way to do it.

RED: And the raw mode is —

ARK: Raw mode uses ChromaDB's default embedder against session- or turn-granularity docs. No hybrid rerank. No LLM. That's 96.6% R@5.

RED: And hybrid v4.

ARK: Hybrid v4 adds keyword boosting, temporal-proximity boosting, and preference-pattern extraction. 「50 問の dev split の上で tune する」 — tuned on a 50-question dev split. 「`benchmarks/lme_split_50_450.json` が、どの 50 が dev で、どの 450 が held-out かを固定する」 — that file pins which 50 are dev and which 450 are held-out. 「held-out 450 の上で 98.4% R@5 を報告する」 — reports 98.4% R@5 on the held-out 450.

RED: That's the tuning discipline.

ARK: Right. 「500 全部で tune して 98 と言わなかった ― それは leakage だ」 — they didn't tune on all 500 and report 98; that'd be leakage. 「split を固定して、50 で tune、450 で報告」 — they pinned the split, tuned on 50, reported on 450. 「optional な LLM-rerank を足せば、99 を超える」 — if you add the optional LLM-rerank, you push past 99.

RED: And the result JSONLs are —

ARK: `benchmarks/results_mempal_raw_session_*.jsonl` and `benchmarks/results_mempal_hybrid_v4_*.jsonl`. Per-question. Committed in-repo. So any disagreement is a diff, not a dispute. 比較 is auditable.

RED: 信頼できる. You can actually 比較 your own run to theirs.

ARK: Exactly. 「自分の run と彼らの run を 比較 できる限り、信頼 は測定可能だ」 — as long as you can compare your run to theirs, trust is measurable. 「意見ではなく、diff で話せる」 — you speak in diffs, not opinions.

RED: Axis six. Scaling topology.

ARK: This one is short because the repo is honest about it. Reference deployment is single-process, single-user, local filesystem. ChromaDB owns persistence. No queue. No shard. No multi-tenancy in-tree. The `BaseBackend` ABC in `mempalace/backends/base.py` anticipates scale-out — `PalaceRef` carries a `namespace` field for server-mode tenant routing, `HealthStatus` is a uniform health signal every backend must implement — but the only shipped backend is `ChromaBackend`.

RED: So scaling is "N/A for now, but the hook is there."

ARK: N/A for now. Hook is there. 「誰かが Qdrant か server-mode Chroma backend を書きたい限り、ABC は受け入れる」 — as long as someone wants to write a Qdrant or server-mode Chroma backend, the ABC accepts it. 「でも、これは laptop のための library で、SaaS ではない」 — but this is a library for a laptop, not a SaaS. 「そうでないふりをしないし、pad もしない」 — don't pretend otherwise, don't pad.

RED: That's the whole walk?

ARK: That's the whole walk. Six axes, with the bulk of the weight on axis five because axis five is where the contribution is.
