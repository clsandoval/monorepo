# 3.5 — Data Display

## Design Direction

**Numbers are the product.** Every Angkin tool exists to produce a number — a peso amount, a percentage, a date, a count. Data display is where Angkin earns its keep. These components must make numbers feel authoritative, precise, and immediately scannable.

Six component types, one principle: **the data is the star, the chrome is invisible.**

1. **Large Peso Amounts** — the hero moment (IBM Plex Mono, navy, monospace)
2. **Comparison Tables** — regime/option side-by-side evaluation
3. **Progress Bars** — completion, capacity, percentage fill
4. **Badges** — status labels, category tags, counts
5. **Tooltips** — contextual help without leaving the flow
6. **Stat Blocks** — dense numeric summaries (already spec'd in 3.3, refined here)

## 2. Comparison Tables

Comparison tables are the second most critical data display in Angkin. TaxKlaro uses them for 3-regime tax comparison. Inheritance uses them for heir share distribution. The table must handle:
- 2-4 columns of numerical data
- Row highlighting for recommended options
- Mixed content: peso amounts, percentages, labels, badges

### Badge Usage Rules

1. **Badges are read-only.** They communicate status, not action. Never make a badge clickable — use a button or link.
2. **One badge per concept.** "Recommended" OR "Best" — never both on the same card.
3. **Badge text is 1-3 words.** "Recommended", "3 Warnings", "Labor" — not "This is the recommended tax regime."
4. **Dot badges for subtle status.** Use `badge__dot` when the text alone is sufficient — the dot adds a scannable color cue.
5. **Count badges for numbers.** "3 Warnings" uses the count variant: `[● 3 Warnings]`.
6. **Solid badges only on colored backgrounds.** Solid navy/success/error badges are for contexts where the tinted background variant lacks contrast (e.g., on a dark card header).

## 5. Tooltips

Tooltips provide contextual help without cluttering the interface. In a compliance platform, users often need to understand legal terms, tax codes, or calculation methodology without navigating away.

### Tooltip Usage Rules

1. **Tooltips appear on hover/focus, not click.** On touch devices, they appear on tap and dismiss on tap-outside.
2. **Maximum 2-3 sentences.** If you need more, use a modal or inline expandable section.
3. **Tooltips never contain interactive elements.** No links, no buttons inside tooltips.
4. **Use tooltips for definitions, not instructions.** "Effective tax rate: your total tax ÷ gross income" (definition) vs. "Click here to change your filing status" (instruction — use help text instead).
5. **Tooltip trigger is always the ⓘ info icon** (Lucide `info` icon, 14px). Don't use `?` or other symbols.
6. **Position: prefer top placement.** Only use bottom when top would go off-screen. Left/right placement is reserved for table column headers.

## Anti-Patterns

1. **No red peso amounts for neutral values.** Red is only for penalties, overdue amounts, and errors. A regular "Tax Due: ₱38,400" is navy, not red — owing tax is expected, not an error.

2. **No animated counters on peso amounts.** "Counting up" animations destroy precision. The number appears immediately and completely. Users need to read it, not watch it animate.

3. **No pie charts for comparison.** Regime comparisons use tables, not pie charts. Pie charts obscure the absolute differences that matter for tax decisions.

4. **No color as the only differentiator.** Every semantic color also has text, icon, or position context. "Recommended" is green text + green badge + green border, not just a green number. This ensures colorblind accessibility.

5. **No truncated peso amounts.** Never abbreviate `₱1,234,567.89` to `₱1.2M` in result displays. Abbreviation is acceptable only in dashboard stat cards where space is constrained — and always with a tooltip showing the full amount.

6. **No percent signs without the number.** Always `3.2%`, never just the bar. Progress bars are supplementary visual aids — the number is always visible.

7. **No table rows without alternating cues.** For tables longer than 8 rows, use subtle alternating row backgrounds (`--neutral-50` on even rows) to aid scanning.

8. **No badges as navigation.** Badges display status. They never link somewhere. Use tags or pills with `cursor: pointer` if you need clickable category filters.

## Summary

| Component | Purpose | Key Visual | States |
|-----------|---------|------------|--------|
| Peso Display | Hero amounts | IBM Plex Mono, navy, 40/28/16/13px | savings, due, penalty, overpayment |
| Comparison Table | Regime evaluation | Sticky labels, recommended column, scroll | hover rows, recommended highlight |
| Progress Bar | Completion/capacity | 8px track, navy fill, pill shape | default, segmented, threshold, indeterminate |
| Badge | Status labels | Pill shape, tinted bg, 12px | 8 colors × 3 fill styles × 3 sizes |
| Tooltip | Contextual help | Dark popover, 280px max, arrow | visible/hidden, rich/simple, light/dark |
| Stat Block | Inline summaries | Mono values, label-above, row/grid | savings, due, neutral, total |

**Total new CSS custom properties: ~20**

**Key design decisions:**
- Peso amounts ALWAYS use IBM Plex Mono with `tabular-nums` — no exceptions
- Comparison tables are horizontally scrollable on mobile with sticky first column
- Progress bars have a segmented variant for wizard steps (gap between segments)
- Badges are pill-shaped (border-radius: full) — they never have square corners
- Tooltips are dark by default, max 280px, positioned top — they use the light variant only on dark surfaces
- Stat blocks come in two orientations: vertical (label → value) and inline (label ··· value)
- Anti-pattern #1: red is never neutral — it always means penalty/error
