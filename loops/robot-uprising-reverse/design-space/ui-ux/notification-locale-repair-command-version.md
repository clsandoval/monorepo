# `repair_command_version` Field for Schema Compatibility

**Aspect:** 4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-i-A — Versioning the repair command format so cached audit outputs can be detected as stale after a `repair-suppression-ref` argument schema change; semantic versioning of CLI argument schemas as a general pattern

**Parent:** 4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-i — `repair_command` field in audit JSON output (established: three-field pattern `repair_command`/`repair_confidence`/`repair_confidence_reason`, six confidence cases, shell-safe quoting rules, flag inclusion policy, `repair_candidates` array for ambiguous cases)

**The gap this closes:** The parent's Weakness #1 identifies the core problem: "The `repair_command` string encodes the repair command's argument schema. If `make repair-suppression-ref` changes its argument format, all cached audit outputs contain invalid commands." Without versioning, Aarav's CI pipeline (Journey 2 in parent) silently passes invalid commands to `eval`, producing cryptic make errors. The fix: a `repair_command_version` field that consuming scripts can compare against the currently-installed tool version.

---

## The Design Decision

When the audit tool generates a `repair_command` string like `make repair-suppression-ref KEY=shared.error.bufferFull.toast SURFACE=notification.toast`, that string embeds assumptions about the repair tool's argument schema:
- That the tool accepts `KEY=` and `SURFACE=` as positional-looking keyword arguments
- That the tool is invoked via `make` (not a direct binary call)
- That no mandatory flags have been added since the audit was generated

If the repair tool's schema changes — say, `SURFACE` is renamed to `TARGET_SURFACE`, or a new `--strategy` flag becomes mandatory — every cached audit JSON contains commands that will fail at runtime. The `repair_command_version` field is a staleness detector: a version stamp that lets consumers check "was this command generated by a tool version I understand?"

### The Field in Context

```json
{
  "audit_metadata": {
    "generated_at": "2026-03-14T10:42:00Z",
    "tool_version": "1.4.2",
    "repair_command_schema_version": "2"
  },
  "suppressions": [
    {
      "key": "shared.error.bufferFull.toast",
      "status": "unevaluable",
      "repair_command": "make repair-suppression-ref KEY=shared.error.bufferFull.toast SURFACE=notification.toast",
      "repair_command_version": "2",
      "repair_confidence": "high",
      "repair_confidence_reason": "Rename log entry matches stale surface exactly (PR #412, 2025-11-18)"
    }
  ]
}
```

Two version fields, different scopes:
- `audit_metadata.repair_command_schema_version`: the schema version used to generate ALL commands in this audit output
- Per-entry `repair_command_version`: redundant but useful when entries are extracted individually (e.g., `jq '.suppressions[] | select(.key == "...")'` strips the metadata)

## The Five Design Options

### Option A: Integer Schema Version ("The Counter")

A monotonically increasing integer. Starts at `1`. Incremented whenever the argument schema changes in a way that would invalidate previously-generated commands.

```json
{
  "repair_command_version": "2",
  "repair_command": "make repair-suppression-ref KEY=... SURFACE=..."
}
```

The consuming script checks:

```bash
EXPECTED_VERSION=$(make repair-suppression-ref --schema-version)
COMMAND_VERSION=$(echo "$ENTRY" | jq -r '.repair_command_version')
if [ "$COMMAND_VERSION" != "$EXPECTED_VERSION" ]; then
  echo "STALE: repair command generated with schema v$COMMAND_VERSION, current is v$EXPECTED_VERSION"
  echo "Re-run 'make l10n-suppression-audit' to regenerate."
  exit 1
fi
```

**Strengths:**
- Dead simple. No parsing, no range logic, no compatibility matrices.
- Easy to compare: `!=` is the only check needed.
- Easy to increment: change one line in the repair tool's source.
- Matches the ESLint/Prettier pattern where config versions are integers.

**Weaknesses:**
- No backward compatibility signaling. Schema v3 might be a minor additive change (new optional flag) that doesn't invalidate v2 commands, but the integer check rejects them anyway.
- No machine-readable information about WHAT changed. The script knows the version is wrong but not how to fix the command.
- Overly conservative: ANY schema change increments the version, even non-breaking ones. This forces unnecessary re-audits.

**When to use:** When the repair tool changes rarely (≤2 times per year) and re-running the audit is cheap (< 30 seconds).

### Option B: Semantic Version ("The SemVer")

A MAJOR.MINOR.PATCH version string. MAJOR = breaking argument changes, MINOR = additive non-breaking changes, PATCH = bug fixes in command generation.

```json
{
  "repair_command_version": "2.1.0",
  "repair_command": "make repair-suppression-ref KEY=... SURFACE=..."
}
```

Consuming script:

```bash
EXPECTED_MAJOR=$(make repair-suppression-ref --schema-version | cut -d. -f1)
COMMAND_MAJOR=$(echo "$ENTRY" | jq -r '.repair_command_version' | cut -d. -f1)
if [ "$COMMAND_MAJOR" != "$EXPECTED_MAJOR" ]; then
  echo "BREAKING CHANGE: repair command schema v$COMMAND_VERSION incompatible with current v$EXPECTED_VERSION"
  exit 1
fi
```

**Strengths:**
- Backward compatibility is expressible: a v2.0 command works with a v2.3 tool (same major).
- MINOR bumps (new optional flag added) don't invalidate cached commands.
- Industry standard — developers immediately understand the semantics.

**Weaknesses:**
- Overkill for a single CLI tool's argument schema. SemVer shines for libraries and APIs with many consumers; a single `make` target consumed by 1-2 scripts doesn't need this granularity.
- Parsing is more complex (split on dots, compare numerically).
- The distinction between MINOR and PATCH is ambiguous for argument schemas. Is fixing a quoting bug MINOR or PATCH?

**When to use:** When the repair tool is a shared utility consumed by multiple teams or open-source consumers who need compatibility promises.

### Option C: Capability Set ("The Feature Flags")

Instead of a version number, the audit output declares which capabilities the `repair_command` assumes the tool supports:

```json
{
  "repair_command_capabilities": ["key_surface_args", "confirm_surface_flag"],
  "repair_command": "make repair-suppression-ref KEY=... SURFACE=... --confirm-surface=..."
}
```

The consuming script checks:

```bash
SUPPORTED=$(make repair-suppression-ref --capabilities)
# Returns: ["key_surface_args", "confirm_surface_flag", "dry_run_flag", "strategy_flag"]

REQUIRED=$(echo "$ENTRY" | jq -r '.repair_command_capabilities[]')
for CAP in $REQUIRED; do
  if ! echo "$SUPPORTED" | grep -q "$CAP"; then
    echo "MISSING CAPABILITY: command requires '$CAP' which current tool doesn't support"
    exit 1
  fi
done
```

**Strengths:**
- Precise staleness detection. The script knows EXACTLY what's missing — not just "version mismatch" but "this command uses `--confirm-surface` which the installed tool doesn't support."
- Additive changes never invalidate old commands: adding a new capability to the tool doesn't remove old capabilities.
- Debugging-friendly: when a command fails, the missing capability name tells you what to look for.

**Weaknesses:**
- Capability names must be carefully designed — they're a mini-schema language that itself needs versioning (meta-problem).
- More complex to implement on both sides (audit must declare capabilities per-command, tool must expose its capability set).
- Doesn't handle capability removal cleanly: if `key_surface_args` is replaced by `key_arg` + `surface_arg` (split), old capabilities don't map to new ones.

**When to use:** When the repair tool's argument schema evolves frequently with additive changes, and consumers need to know exactly which features are required.

### Option D: Hash of Schema Definition ("The Content-Addressed Version")

The repair tool exposes its argument schema as a JSON Schema or similar structure, and the version is a content hash of that schema:

```json
{
  "repair_command_version": "sha256:a1b2c3d4e5f6...",
  "repair_command": "make repair-suppression-ref KEY=... SURFACE=..."
}
```

Consuming script:

```bash
CURRENT_HASH=$(make repair-suppression-ref --schema-hash)
COMMAND_HASH=$(echo "$ENTRY" | jq -r '.repair_command_version')
if [ "$COMMAND_HASH" != "$CURRENT_HASH" ]; then
  echo "SCHEMA CHANGED: command generated against schema $COMMAND_HASH, current is $CURRENT_HASH"
  exit 1
fi
```

**Strengths:**
- Automatically detects ANY change — no human needs to remember to bump a version.
- Content-addressed = unforgeable. If the schema hasn't changed, the hash matches. If it has, it doesn't. No human error in version management.
- Works with any schema language (JSON Schema, custom, informal).

**Weaknesses:**
- Maximally conservative — even adding a comment to the schema changes the hash. Non-breaking changes invalidate cached commands.
- No backward compatibility signaling. A different hash = incompatible, always.
- Hashes are opaque: when the hash mismatches, the developer has no idea what changed without running a diff.
- Requires the repair tool to have a formal, hashable schema definition — which it might not have.

**When to use:** When correctness is paramount and re-auditing is always cheap. Appropriate for safety-critical systems, not for developer-facing game tooling.

### Option E: No Version Field ("Trust the Timestamp")

Don't version the command at all. Instead, rely on the `generated_at` timestamp in the audit metadata. If the audit is older than the last schema change, regenerate.

```json
{
  "audit_metadata": {
    "generated_at": "2026-03-14T10:42:00Z"
  },
  "suppressions": [
    {
      "repair_command": "make repair-suppression-ref KEY=... SURFACE=...",
      "repair_confidence": "high"
    }
  ]
}
```

Consuming script:

```bash
SCHEMA_CHANGED=$(make repair-suppression-ref --schema-changed-date)
# Returns: "2026-02-20"
AUDIT_DATE=$(echo "$AUDIT_JSON" | jq -r '.audit_metadata.generated_at')
if [ "$(date -d "$SCHEMA_CHANGED")" -gt "$(date -d "$AUDIT_DATE")" ]; then
  echo "STALE: audit predates schema change on $SCHEMA_CHANGED"
  exit 1
fi
```

**Strengths:**
- No new field in the per-entry JSON. Lean.
- Works for any kind of staleness, not just schema changes (also catches surface additions, budget changes, etc.).

**Weaknesses:**
- Requires the repair tool to track its own "last schema change" date, which is a manual process prone to being forgotten.
- Timestamp comparison is fragile (timezone issues, clock skew in CI).
- Doesn't tell you what changed — just that something did.
- Can't distinguish between breaking and non-breaking changes.

**When to use:** When the primary staleness concern is audit freshness, not schema compatibility specifically.

## Recommendation: Option A (Integer Counter) with Option B (SemVer) Migration Path

Start with Option A. The repair tool is consumed by at most 3 scripts (Aarav's batch pipeline, Priya's manual workflow, the IDE extension). The schema changes maybe once a year. An integer counter is:
- Trivially implementable (one constant in the repair tool source, one field in audit output)
- Trivially checkable (`!=` comparison)
- Trivially debuggable ("expected 2, got 1" is a complete error message)

**Migration to Option B if:**
- The tool gains more consumers (open-source, multi-team)
- The schema starts changing more frequently (quarterly+)
- Non-breaking changes become common and re-auditing becomes expensive

**Why not Option C:** The capability set is elegant but over-engineered for a CLI tool with 6 arguments. The abstraction cost (defining capability names, maintaining the capability registry) exceeds the value.

**Why not Option D:** Content-addressed hashing is appropriate for package lockfiles and build artifacts, not for a CLI argument schema that changes at human cadence. The opacity of hash mismatches is unacceptable for developer-facing tooling.

**Why not Option E:** Timestamps are a proxy for version, and proxies introduce false positives (a re-deploy without schema changes bumps the date) and false negatives (clock skew).

### The Version Constant

In the repair tool source:

```makefile
# repair-suppression-ref.mk
REPAIR_SCHEMA_VERSION := 2

# Expose for consumers
.PHONY: repair-suppression-ref-schema-version
repair-suppression-ref-schema-version:
	@echo $(REPAIR_SCHEMA_VERSION)
```

Or, if implemented in a script:

```bash
# repair-suppression-ref.sh
SCHEMA_VERSION=2

if [ "$1" = "--schema-version" ]; then
  echo "$SCHEMA_VERSION"
  exit 0
fi
```

The audit tool reads this at generation time and embeds it in every `repair_command_version` field.

### Version Bump Protocol

When the repair tool's argument schema changes:

1. Increment `SCHEMA_VERSION` in the repair tool source
2. Update the CHANGELOG (optional but recommended)
3. CI scripts that check version will start failing on stale audit JSON — this is the desired behavior
4. The developer re-runs `make l10n-suppression-audit` to regenerate
5. New audit output has the new version, CI scripts pass

**What constitutes a schema change:**
- New mandatory argument → BUMP
- Renamed argument (KEY → KEYNAME) → BUMP
- Removed argument → BUMP
- New optional flag → NO BUMP (old commands remain valid)
- Changed default value of optional flag → NO BUMP (old commands remain valid — they never included the flag)
- Changed the `make` target name → BUMP

This matches the SemVer "breaking change" definition, applied to a single integer. Non-breaking changes don't bump. This gives Option A most of Option B's benefits without the parsing complexity.

## The Stale-Command Error Path

When a consuming script detects a version mismatch, the error message must be actionable:

```
ERROR: Stale repair command detected.

  Entry:    shared.error.bufferFull.toast
  Command:  make repair-suppression-ref KEY=shared.error.bufferFull.toast SURFACE=notification.toast
  Version:  1 (generated 2026-01-15)
  Current:  2 (schema updated 2026-03-10)

  The repair command's argument format has changed since this audit was generated.
  Re-run:   make l10n-suppression-audit --output-format=json > l10n/audit-cache.json

  What changed in schema v2:
    - SURFACE argument renamed to TARGET_SURFACE
    - New mandatory flag: --validate-budget
```

The "what changed" section is optional — it requires the repair tool to maintain a changelog per schema version. If present, it transforms a cryptic "version mismatch" into a comprehensible upgrade path.

### Changelog Per Schema Version

```json
{
  "repair_schema_changelog": {
    "2": {
      "date": "2026-03-10",
      "breaking_changes": [
        "SURFACE argument renamed to TARGET_SURFACE",
        "New mandatory flag: --validate-budget"
      ],
      "migration": "Replace SURFACE= with TARGET_SURFACE= and append --validate-budget"
    },
    "1": {
      "date": "2025-09-01",
      "breaking_changes": ["Initial schema"],
      "migration": null
    }
  }
}
```

This changelog could live:
- In the repair tool itself (exposed via `--schema-changelog`)
- In a separate `l10n/repair-schema-changelog.json` file
- Inline in the audit output's metadata section

**Recommendation:** In the repair tool itself, exposed via `--schema-changelog --from=1 --to=2`. This keeps the changelog co-located with the schema it describes, and the `--from/--to` flags let scripts extract only the relevant migration path.

## Interaction with Cached Audit Outputs

### The Caching Pattern

Several workflows cache audit JSON:
1. **Nightly CI:** Generates audit JSON, stores as artifact, downstream jobs consume it
2. **PR comments:** Audit JSON cached in the PR comment body (base64-encoded in a hidden `<!-- -->` block)
3. **Slack summaries:** Audit JSON cached in a Slack message's metadata (for the 👍-to-approve flow)

All three caches can become stale if the repair tool is updated between the audit generation and the command execution.

### Cache Invalidation Strategy

The version field enables a simple cache invalidation rule: **before executing any `repair_command` from a cached audit, compare `repair_command_version` against the tool's current `--schema-version`. If mismatched, discard the cached audit and regenerate.**

This is the same pattern as browser cache `ETag` validation: the cached resource (audit JSON) includes a version tag, the consumer checks the tag against the server (tool), and revalidates if stale.

### PR Comment Staleness

The 👍-to-approve flow (from the parent's Aarav journey) posts a PR comment with a ready-to-run command. If the repair tool is updated between the comment posting and the 👍 reaction, the command is stale. The GitHub Actions workflow that processes the reaction must:

1. Extract the `repair_command_version` from the comment's hidden metadata
2. Compare against the current tool version
3. If stale: edit the comment to say "⚠ This command is outdated. Re-running audit..." and regenerate
4. If fresh: execute the command

```yaml
# .github/workflows/approve-repair.yml
- name: Check command freshness
  run: |
    CURRENT=$(make repair-suppression-ref --schema-version)
    CACHED=$(echo "$COMMENT_METADATA" | jq -r '.repair_command_version')
    if [ "$CURRENT" != "$CACHED" ]; then
      gh pr comment $PR --edit $COMMENT_ID --body "⚠ Repair command outdated (schema v$CACHED → v$CURRENT). Regenerating..."
      make l10n-suppression-audit --output-format=json > /tmp/new-audit.json
      # Re-post with updated commands
    fi
```

## The General Pattern: CLI Argument Schema Versioning

This design generalizes beyond `repair-suppression-ref`. Any CLI tool that embeds its commands in structured output (audit reports, diagnostic JSON, CI artifacts) faces the same staleness problem. The pattern:

1. **Version constant** in the tool source (integer, bumped on breaking changes)
2. **`--schema-version` flag** that prints the current version
3. **Version field** in every structured output that contains executable commands
4. **Consumer check** before executing: compare embedded version against current version
5. **Actionable error** on mismatch: what changed, how to regenerate

This is the CLI equivalent of API versioning (REST `Accept` headers, GraphQL schema versioning, gRPC service version). The same principles apply: version the contract, not the implementation; bump only on breaking changes; provide migration paths.

### Where Else This Applies in Robot Uprising's Toolchain

- `make fork-string` output JSON could include a `fork_command_version` for downstream automation
- `make rename-surface` output could include a `rename_command_version` for undo scripts
- The nightly Playwright audit could include a `screenshot_schema_version` for visual regression CI that caches baseline screenshots
- Any tool that generates "run this command next" suggestions benefits from versioning those suggestions

### Journey: Aarav, 28, CI Automation Engineer — The Schema Update That Broke Nightly

**Context:** Three months after deploying the batch repair pipeline (parent Journey 2). The team has upgraded the repair tool to add a `--validate-budget` mandatory flag (schema v1 → v2). Aarav's nightly CI pipeline starts failing.

**Minute 0:00 — Nightly Pipeline Failure Alert**

Slack notification at 6:47 AM: "🔴 l10n-nightly: repair pipeline failed." Aarav checks the CI log on his phone during breakfast.

The log shows:

```
AUTO-REPAIRING: shared.error.bufferFull.toast (confidence: high)
make: *** No rule to make target 'repair-suppression-ref'. Stop.

Wait — that's wrong. The target exists. He scrolls up:

STALE COMMAND DETECTED
  Entry:    shared.error.bufferFull.toast
  Command:  make repair-suppression-ref KEY=shared.error.bufferFull.toast SURFACE=notification.toast
  Version:  1 (cached audit from 2026-03-12)
  Current:  2 (schema updated 2026-03-14)

  Re-run:   make l10n-suppression-audit --output-format=json > l10n/audit-cache.json
```

Aarav's script caught the version mismatch before calling `eval`. The error message tells him exactly what happened and exactly what to do.

**Minute 0:30 — Understanding the Change**

He checks the schema changelog (exposed via `make repair-suppression-ref --schema-changelog --from=1 --to=2`):

```
Schema v1 → v2 (2026-03-14):
  Breaking changes:
    - New mandatory flag: --validate-budget
      Every repair command now requires --validate-budget to confirm
      the repaired condition doesn't immediately trigger.

  Migration:
    Append '--validate-budget' to all cached repair commands.
    Or: regenerate audit output (recommended).
```

Aarav understands: Priya added a safety check that prevents repairs from silently creating conditions that fire immediately. Good change. But his cached audit JSON from two days ago doesn't include the flag.

**Minute 1:00 — The Fix**

Two options:
1. Regenerate the audit cache (recommended)
2. Update his script to append `--validate-budget` to all cached commands (hacky, temporary)

He picks option 1. He updates the CI workflow to regenerate the audit at the start of each nightly run rather than caching it across runs:

```yaml
- name: Generate fresh audit
  run: make l10n-suppression-audit --output-format=json > /tmp/audit.json

- name: Run batch repair
  run: ./scripts/batch-repair-stale-refs.sh /tmp/audit.json
```

No more caching the audit JSON as a CI artifact. The audit takes 8 seconds — not worth caching.

**Minute 2:00 — Adding the Version Check**

But Aarav realizes: what if the audit tool and the repair tool are out of sync? (The audit generates commands, the repair tool executes them.) He adds a pre-flight check to his script:

```bash
# Pre-flight: ensure audit and repair tool agree on schema version
AUDIT_VERSION=$(jq -r '.audit_metadata.repair_command_schema_version' "$AUDIT_FILE")
TOOL_VERSION=$(make repair-suppression-ref --schema-version)

if [ "$AUDIT_VERSION" != "$TOOL_VERSION" ]; then
  echo "FATAL: Audit generated with schema v$AUDIT_VERSION but repair tool is at v$TOOL_VERSION"
  echo "This should not happen if both tools are from the same commit."
  echo "Check that 'make l10n-suppression-audit' and 'make repair-suppression-ref' are in sync."
  exit 1
fi
```

This catches a subtler failure mode: the audit tool is updated but the repair tool isn't (or vice versa). In a monorepo where both tools are in the same directory, this shouldn't happen — but in a multi-repo setup, or if someone cherry-picks one tool's update without the other, it could.

**Minute 3:00 — Verifying the Fix**

Re-runs the pipeline manually. Fresh audit generates commands with `repair_command_version: "2"`. Repair tool is at schema v2. Version check passes. Commands include `--validate-budget`. All repairs succeed. No immediate triggers.

The pipeline is green by 7:15 AM. Aarav finishes breakfast.

**UI Annotations:**
- The `STALE COMMAND DETECTED` error is printed in bright yellow with a `⚠` prefix — yellow (not red) because it's a staleness issue, not a repair failure. The distinction matters: yellow = regenerate, red = investigate.
- The `Re-run:` line is printed in bold white, indented, with the full command ready to copy. Same pattern as the `repair_command` field itself — actionable text is visually distinct from diagnostic text.
- The schema changelog output (`--schema-changelog`) uses a simple text format: version header, bulleted breaking changes, migration note. No JSON — this output is for humans debugging a CI failure at 6:47 AM.

When Aarav's CI script detects a stale command, the terminal output has a distinctive visual rhythm:


The `⚠` is bright yellow — the only colored character on the line. `STALE COMMAND DETECTED` is white, bold, all-caps. It sits on its own line with a blank line above and below, creating visual breathing room that says "stop and read this."

## Strengths

1. **Prevents silent failures.** Without versioning, a stale `repair_command` passed to `eval` produces a cryptic Make error ("missing argument", "unknown flag"). With versioning, the failure is caught before execution with a clear message.

2. **Cheap to implement.** One integer constant, one `--schema-version` flag, one field in JSON output. Under 20 lines of code across both tools.

3. **Self-documenting with changelog.** The `--schema-changelog` flag means the version number isn't just a number — it has an explanation. Developers can always answer "what changed in v2?" without reading git log.

4. **Generalizable pattern.** Every CLI tool that embeds commands in structured output benefits from this. The pattern is reusable across the entire toolchain.

5. **Non-breaking additive changes don't bump.** By defining "breaking" as "invalidates previously-generated commands," the version stays stable through most tool updates. Only true schema changes trigger version bumps.

## Weaknesses

1. **Human-maintained version.** The developer must remember to bump the version when making a breaking change. If they forget, the version field is wrong and consumers execute stale commands without warning. Mitigation: PR template checkbox, or a CI check that compares the argument parser's accepted arguments against a recorded manifest.

2. **Over-simplification of compatibility.** An integer version can't express "v1 commands work with v2 tool if you ignore the new flag's absence." In practice this means the version is bumped for changes that aren't truly breaking (e.g., a new mandatory flag with a sensible default). Mitigation: only bump for changes that make old commands produce wrong results, not changes that make old commands produce less-validated results.

3. **Dual-location redundancy.** The version appears in both `audit_metadata` and each entry. If the audit tool has a bug where the metadata version and entry version disagree, consumers get confused. Mitigation: the audit tool writes both from the same constant; a test asserts they match.

4. **No automated detection of schema changes.** The developer must manually identify "this change is breaking." A renamed argument is obviously breaking, but a changed default value might or might not be. The gray area creates inconsistency in version bump decisions. Mitigation: document the "what constitutes a schema change" rules (as done above) and reference them in PR reviews.

## Interaction Effects

- **4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-i-B (Eval injection hardening):** If the field becomes a structured object instead of a string, the version field versioning the STRUCTURE of that object (which keys exist, what types they have). Structured objects are more version-sensitive than strings because field additions/removals are breaking by default.

- **4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-i-C (PR comment rendering):** The version field must be included in the PR comment's hidden metadata so the approval workflow can check freshness before executing. The markdown rendering should NOT show the version to the developer (visual noise) — it's a machine-readable field.

- **4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-i-D (Confidence calibration):** Historical accuracy tracking must be scoped to a schema version. A confidence level's accuracy under schema v1 doesn't predict its accuracy under schema v2 (the confidence algorithm may have changed along with the schema). When the schema version bumps, accuracy counters should reset or be version-tagged.

- **4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-i-E (Auto-repair governance):** The governance model should define who can bump the schema version. If bumping the version invalidates all cached audits and breaks CI pipelines, it's a team-affecting action — analogous to a database migration. Should it require review from the CI maintainer (Aarav)?

- **4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-ii (`--auto-lookup`):** When `--auto-lookup` is added, does it constitute a schema change? If old commands didn't include `--auto-lookup` and the flag becomes mandatory, yes. If it's optional with backward-compatible defaults, no. The version bump protocol (defined above) answers this clearly: new optional flag = NO BUMP.

- **4.69e-i-a-i-f-i-α-i-A-α-i-1-I-a-iv (Batch repair rollback):** Rollback scripts that replay old commands in reverse must check the version of each replayed command. If the tool has been upgraded since the original repair, the inverse command might use the wrong schema. The version field enables the rollback script to detect this and refuse to roll back stale repairs.

## Comparable Systems

### REST API Versioning

The closest analog is REST API versioning (`/api/v2/resource`). The API version is embedded in the URL, not the response body — but the principle is identical: the consumer declares which contract it expects, and the server either honors it or rejects it. Robot Uprising's `repair_command_version` is the response-body equivalent: the server (audit tool) declares which contract the embedded commands follow, and the consumer (batch script) checks it.

**Key difference:** API versioning typically supports multiple versions simultaneously (v1 and v2 both work). The repair tool only supports the current schema version. Old commands are invalid, period. This is acceptable because regenerating the audit (the fix for stale commands) is cheap (8 seconds).

### Docker Image Tags vs. Digests

Docker images have mutable tags (`latest`, `v2`) and immutable digests (`sha256:abc123`). Option A (integer) is like a tag — human-friendly, manually maintained, could in theory point to different content. Option D (hash) is like a digest — immutable, content-addressed, unforgeable. The industry uses both, for different purposes: tags for convenience, digests for reproducibility. Robot Uprising uses the tag equivalent because convenience matters more than reproducibility for this use case.

### Terraform State File Versioning

Terraform's state file includes a `"version"` field (integer) and a `"terraform_version"` field (semver). When the state format changes, the integer bumps. When the Terraform binary version changes, the semver bumps. Both are present, serving different consumers. This is the exact same dual-version pattern as `repair_command_schema_version` (format) vs. `tool_version` (software).

### Protocol Buffers Wire Format Version

Protobuf messages include a wire format version that tells the deserializer how to parse the bytes. If the wire format changes (proto2 → proto3), the version tells the consumer "you can't read this." Same principle: the version is about the FORMAT of the data, not the CONTENT.
