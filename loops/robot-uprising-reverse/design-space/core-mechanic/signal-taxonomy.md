# 2.10 — Signal Taxonomy: What Kinds of Information Exist in the Game World

**Aspect:** 2.10 — Signal taxonomy
**Wave:** 2 (Core Mechanic Variations)
**Category:** core-mechanic

---

## The Design Question

Every tick, agents' context windows fill with *data*. But what IS that data? The signal taxonomy — the classification of information types that exist in the game world — is a foundational design decision that shapes every other system. It determines what rules can test for, what hooks can transmit, what the buffer visualization shows, what the Inspector reveals, and ultimately what the player's design vocabulary looks like.

The core tension: **richness vs. legibility**. A rich taxonomy (12+ signal types with metadata fields) creates deep combinatorial design space but risks overwhelming players with type-management busywork. A minimal taxonomy (3-4 broad categories) keeps the game focused on *architecture* rather than *data modeling* but may feel shallow for veterans.

This analysis explores the full spectrum from "signals are opaque blobs" to "signals are structured records with typed fields."

---

## The Information Sources

Before classifying signals, we must enumerate where data comes from. In Robot Uprising, information enters the system through exactly three gates:

### 1. Perception (Self-Generated Observations)
Units with perception radius > 0 (Scout: 5, Striker: 2, Specialist: 3) generate observations each tick about what they see within range. This is the primary raw data source — the game world translated into context window entries.

### 2. Hook Transmissions (Received Signals)
Signals arriving on channels the unit listens to. These are *processed* data — another unit decided this was worth sending. The signal passed through at least one other agent's decision-making before arriving.

### 3. Internal State (Self-Knowledge)
Data the unit generates about itself — current position, remaining skills, active rules, buffer occupancy. This is the only "free" data source (no latency, no buffer cost for basic state).

---

## Six Taxonomy Models

### Model A: "The Blob" — Untyped Signals

**Mechanical specification:** All data is the same type. A perception observation, a hook message, and a self-state datum occupy identical slots and are indistinguishable to rules. The only metadata is `tick_created` (age) and `source` (which unit generated it).

**What rules can test:** `IF buffer contains entry from SCOUT-A → ...` or `IF buffer contains entry newer than 3 ticks → ...`. Rules cannot distinguish "enemy sighting" from "all clear" from "orders received." The CONTENT is opaque.

**How the player differentiates:** By CHANNEL. If SCOUT-A sends on channel `threats`, the Striker's rule becomes `IF buffer contains entry from channel threats → engage`. The channel name IS the type system. The player creates the taxonomy through naming conventions.

**Strengths:**
- Maximum simplicity. Zero new vocabulary to learn. The only types are the ones the player invents through channel names.
- Forces the player to think about information architecture from tick 1 — "what should this channel be called?" IS the design work.
- Channel naming conventions become the emergent community vocabulary — players develop their own signal taxonomies and share them.
- Maps directly to real-world event-driven systems where message types are defined by the producer, not the infrastructure.

**Weaknesses:**
- Rules can't distinguish between two different signals on the same channel. If `threats` carries both "enemy spotted" and "area clear," the Striker can't tell them apart without a second channel.
- Channel proliferation. To differentiate signal types, players create more channels — `threats-spotted`, `threats-clear`, `threats-high-priority` — and the channel map becomes unmanageable.
- No built-in vocabulary for the tutorial to teach. "What types of signals exist?" Answer: "Whatever you name them." This is powerful for experts, frustrating for beginners.
- Inspector debugging is harder — every entry looks the same, differentiated only by source and channel.

**Sensory description:** Buffer visualization shows uniform amber pips. No color variation. The only visual distinction is a tiny source icon (👁/📡/⚔) in the corner of each pip. In the Inspector, each entry shows `[T12] SCOUT-A → threats: {opaque blob}` — the content is a grey box until clicked, revealing raw observation text.

**Comparable:** Unix pipes (untyped byte streams, meaning imposed by convention), early message queues (ActiveMQ — all messages are strings, type lives in headers), Screeps (Memory is untyped JSON, players define their own data structures).

### Model B: "The Envelope" — Source-Typed Signals

**Mechanical specification:** Signals carry a mandatory `origin_type` field that classifies them by HOW they were generated, not what they contain:

| Origin Type | Generated By | Visual | Buffer Cost |
|-------------|-------------|--------|-------------|
| `OBSERVATION` | Perception system (seeing the world) | 🟢 Green pip | 1 slot |
| `MESSAGE` | Hook transmission (another unit sent it) | 🔵 Blue pip | 1 slot |
| `PROCESSED` | Compress/filter/amplify skill output | 🟡 Yellow pip | 1 slot |
| `ALERT` | System-generated (overload warning, stun recovery) | 🔴 Red pip | 1 slot |
| `SELF` | Internal state query | ⚪ White pip | 0 slots (free) |

**What rules can test:** `IF buffer contains OBSERVATION → ...` or `IF buffer contains MESSAGE from channel orders → ...` or `IF count(ALERT) > 2 → enter defensive mode`. Rules can now distinguish "I saw something" from "someone told me something" from "the system is warning me."

**How the player designs:** The origin type creates a natural priority hierarchy. Observations are ground truth (but stale by 1+ ticks). Messages are processed intelligence (filtered by another agent's judgment). Processed signals are compressed (high-value but lossy). Alerts are urgent system state.

**Strengths:**
- Small vocabulary (5 types) that maps to intuitive categories — seeing, hearing, thinking, alarming, self-awareness.
- Color-coded buffer visualization is instantly legible during sealed watch. A buffer full of red pips means the unit is in crisis. A buffer full of green means it's perceiving but not hearing from the network.
- Rules can implement "trust hierarchy" — prefer observations over messages, prefer messages over processed summaries. This teaches a transferable AI engineering concept (data provenance).
- Origin type is AUTOMATIC — the player doesn't have to label anything. The system tags every datum at creation.

**Weaknesses:**
- Doesn't distinguish between different observations. "Enemy at C3" and "empty tile at D4" are both green OBSERVATION pips. The player still needs channels to differentiate.
- Five types is arbitrary — why not three? Why not eight? The taxonomy feels imposed rather than emergent.
- The PROCESSED type conflates compress output with filter output with amplify output. Are these the same? A compressed signal and an amplified signal serve very different purposes.

**Sensory description:** Buffer bars show colored pips — a glanceable health readout. A healthy buffer is a mix of green and blue with occasional yellow. A stressed buffer is solid blue (flooded with messages). A blind buffer is all green (perceiving but disconnected). An overloaded buffer pulses red. In the Inspector, each entry header is color-coded: `🟢 [T12] OBSERVATION: Enemy scout detected at C3 (SCOUT-A, perception)` vs. `🔵 [T15] MESSAGE: threat-east channel (RELAY-B, hook)`.

**Comparable:** Email (FROM header is automatic metadata, content is separate), HTTP requests (GET/POST/PUT/DELETE as origin types, body is content), Into the Breach (damage types — physical vs. pushing vs. environmental — as automatic categorization of effects).

### Model C: "The Field Report" — Content-Typed Signals

**Mechanical specification:** Every signal carries a mandatory `content_type` field classifying WHAT information it contains:

| Content Type | What It Describes | Icon | Buffer Cost | Example |
|--------------|-------------------|------|-------------|---------|
| `THREAT` | Enemy unit detected | ⚠️ | 1 slot | "Enemy striker at D5, heading west" |
| `TERRAIN` | Map feature observed | 🗺️ | 1 slot | "Jungle tile at C3, signal attenuation zone" |
| `POSITION` | Friendly unit location | 📍 | 1 slot | "SCOUT-A currently at B2" |
| `ORDER` | Behavioral directive | 📋 | 1 slot | "Converge on D5" |
| `STATUS` | Unit state report | 📊 | 1 slot | "RELAY-B buffer 80% full" |
| `RESOURCE` | Economy information | 💎 | 1 slot | "Node at F4 untagged" |
| `NOISE` | Detected EM emission | 📡 | 1 slot | "Strong emission from G6" |
| `UNKNOWN` | Unclassifiable data | ❓ | 1 slot | Degraded signal, enemy injection |

**What rules can test:** `IF buffer contains THREAT within 3 tiles → engage` or `IF count(ORDER) > 0 → follow most recent ORDER` or `IF no THREAT in buffer for 5 ticks → resume patrol`. Rules now operate on semantic meaning, not just provenance.

**How the player designs:** Content types create a VOCABULARY for agent behavior. A scout's hook can be configured to send only `THREAT` signals — filtering out terrain and position data. A Command agent's rules can prioritize `STATUS` signals from overwhelmed relays over `THREAT` signals from scouts. The type system becomes the language of attention.

**Strengths:**
- Rules become readable as English: "IF THREAT detected AND no ORDER received → patrol toward THREAT." This is the most accessible rule-writing experience.
- Natural filtering vocabulary. Context config can say "listen to THREAT and ORDER, ignore TERRAIN and POSITION." This is EXACTLY how attention systems work in real AI — you configure what the agent attends to by content category.
- Inspector debugging is semantic: "The striker missed the flanking enemy because its context config was set to ignore NOISE signals, and the enemy's EM emission was classified as NOISE, not THREAT."
- Creates information warfare depth. Enemy DECEPTION signals (2.12) can inject false `THREAT` entries. The `UNKNOWN` type creates a natural category for suspicious data that a Specialist's intrusion detection can reclassify.
- Content types are AUTOMATIC for observations (the perception system classifies what it sees) but PLAYER-CHOSEN for hook transmissions (the hook config includes a content type selector). This hybrid gives the player agency over their signal vocabulary.

**Weaknesses:**
- Eight types is a lot of vocabulary for Mission 1. Need careful pacing — introduce THREAT and POSITION only, add ORDER in Mission 4, STATUS in Mission 5, RESOURCE in Mission 5, NOISE and UNKNOWN in Mission 7+.
- Classification ambiguity. Is "enemy relay at G6 emitting signals" a THREAT (it's an enemy) or NOISE (it's an emission) or POSITION (it's a location)? The game must make these calls deterministically, and the player must learn the classification rules.
- Rigidity. What if a player wants a custom type — "retreat signal" or "VIP escort path"? The fixed taxonomy can feel constraining for advanced players who think in terms of their own abstractions.
- Buffer visualization with 8 colors/icons is noisy. During sealed watch, 8 pip types on a 6-slot buffer is a lot of visual information competing with the battle.

**Sensory description:** Buffer bars become information rainbows. Each pip shows its content type icon at pixel scale — barely readable at sealed watch zoom, but the COLOR pattern tells a story. A buffer dominated by red ⚠️ pips means the unit is surrounded by threats. A buffer full of blue 📋 pips means it's drowning in orders. In the Inspector, each entry unfolds into a structured card: `⚠️ THREAT | Enemy striker | D5 | Heading W | Tick 12 | Fidelity: HIGH | Source: SCOUT-A perception`. The card layout has consistent fields, making cross-entry comparison trivial.

**Comparable:** Military intelligence (SALUTE reports: Size, Activity, Location, Unit, Time, Equipment — a fixed content taxonomy for field observations), typed events in event-driven architectures (CloudEvents spec: `type`, `source`, `subject`, `data`), Dwarf Fortress thoughts (happy thoughts, unhappy thoughts, needs — typed psychological signals).

### Model D: "The Spectrum" — Continuous Signal Attributes

**Mechanical specification:** Instead of discrete types, every signal has continuous ATTRIBUTES that rules can test:

| Attribute | Range | What It Measures |
|-----------|-------|-----------------|
| `urgency` | 0.0–1.0 | How time-sensitive (enemy in combat range = 1.0, distant terrain = 0.1) |
| `confidence` | 0.0–1.0 | How reliable (direct observation = 1.0, 3-hop relay = 0.4, degraded = 0.1) |
| `specificity` | 0.0–1.0 | How detailed (exact position + type = 1.0, "something nearby" = 0.2) |
| `relevance` | 0.0–1.0 | How applicable to this unit's role (threat for striker = 1.0, threat for relay = 0.3) |

**What rules can test:** `IF any signal with urgency > 0.7 AND confidence > 0.5 → engage` or `IF average(confidence) < 0.3 → broadcast REQUEST_UPDATE on intel`. Rules become threshold-based filters on continuous dimensions.

**How the player designs:** Instead of categorizing signals (threat vs. terrain vs. order), the player configures SENSITIVITY. "My striker should react to anything above urgency 0.7" vs. "My relay should only forward signals with confidence above 0.5." This is a fundamentally different cognitive model — not "what type of information" but "how important/reliable/detailed is it."

**Strengths:**
- Maps directly to real attention systems. Human attention is threshold-based, not category-based — we notice URGENT things regardless of type. AI attention (similarity scores, relevance ranking) is also continuous.
- Creates elegant difficulty progression. Early missions: one threshold (urgency). Later: two thresholds. Expert: all four as interacting constraints. The slider-per-attribute model scales smoothly.
- Eviction policies become intuitive: "evict lowest urgency × confidence" naturally keeps the most important, reliable data.
- Information warfare is sophisticated: enemies can craft HIGH-urgency LOW-confidence signals (panic-inducing noise) or LOW-urgency HIGH-confidence signals (slow-burning disinformation that persists in buffers because it's "reliable").

**Weaknesses:**
- Sliders are hard to reason about. "Set urgency threshold to 0.65" is less intuitive than "listen to THREAT signals." The abstraction is powerful but cognitively expensive.
- Debugging is non-obvious. "Why did my striker ignore the flanking enemy?" Because the signal arrived at urgency 0.68 and the threshold was 0.70. Finding this requires Inspector deep-dive into attribute values — not immediately legible.
- The four attributes are not orthogonal — urgency and relevance are highly correlated for combat units. This creates redundancy that feels like false complexity.
- Sealed watch visualization is abstract. What does "urgency 0.7" look like as a pip? Color gradients are less glanceable than discrete icons.

**Sensory description:** Buffer pips are rendered as gradient fills — hotter colors for high urgency, brighter saturation for high confidence, larger pips for high specificity, white-outlined for high relevance. In practice, most pips are orange-yellow blurs. In the Inspector, each entry shows four tiny bar charts (like a miniature equalizer): `|████░| |███░░| |██░░░| |████░|` for urgency/confidence/specificity/relevance. Hovering shows exact values. The visual language is "signal processing console" — oscilloscope aesthetic.

**Comparable:** Radar systems (return signals have strength, confidence, bearing — continuous attributes), machine learning attention scores (continuous 0-1 relevance weights), Factorio circuit signals (integer values on typed channels — typed + valued hybrid).

### Model E: "The Packet" — Structured Records with Typed Fields

**Mechanical specification:** Every signal is a structured record with mandatory and optional fields:

```
SIGNAL {
  // Mandatory (auto-generated)
  source_unit: UNIT_ID        // Who created this
  source_type: OBSERVATION | MESSAGE | PROCESSED | ALERT
  tick_created: INT           // When
  tick_received: INT          // When it arrived here
  channel: STRING | null      // Which channel (null for observations)

  // Content (auto-classified for observations, player-set for hooks)
  content_type: THREAT | TERRAIN | POSITION | ORDER | STATUS | RESOURCE | NOISE | UNKNOWN

  // Attributes (auto-computed)
  urgency: FLOAT 0.0-1.0
  confidence: FLOAT 0.0-1.0

  // Payload (variable)
  location: GRID_COORD | null
  target_unit: UNIT_ID | null
  data: STRING               // Human-readable description
}
```

**What rules can test:** Everything. `IF THREAT from SCOUT-A with urgency > 0.7 at location within 3 tiles AND confidence > 0.5 → engage target_unit`. This is the most expressive model — rules are database queries against the buffer.

**How the player designs:** Like writing SQL WHERE clauses against a log database. Each rule's condition is a filter across multiple signal fields. The workbench UI provides a query builder with dropdowns for each field.

**Strengths:**
- Maximum expressiveness. Any conceivable agent behavior can be specified by the right combination of field tests.
- Natural SQL/API-query parallel. Players who know databases or REST APIs will feel instantly at home.
- Inspector is maximally informative — every field of every signal is visible, searchable, filterable.
- Future-proof. Adding new fields doesn't break existing rules (they just don't test the new field).

**Weaknesses:**
- Overwhelming. This is a database schema, not a game mechanic. The UI must hide most fields most of the time.
- Violates the "not writing code" ethos. Building a rule by selecting `content_type = THREAT AND source_type = OBSERVATION AND urgency > 0.7 AND location.distance(self) < 3` IS programming, even with a visual query builder.
- Tutorial pacing nightmare. How do you introduce 10+ fields across 10 missions without each mission feeling like a database tutorial?
- Sealed watch is impossible to read at pip level. A 10-field record can't be summarized in a 4-pixel pip.

**Sensory description:** Buffer visualization shows condensed "micro-cards" instead of pips — each slot is a tiny card with a colored header (content type), a dim icon (source type), and a brightness level (urgency). At sealed watch zoom, these are 8×4 pixel rectangles with colored tops. In the Inspector, entries expand into full database records with every field labeled. The aesthetic is "IDE debug panel" — structured, dense, powerful, but not playful.

**Comparable:** Protocol Buffers / JSON schemas (structured typed records), database rows (queryable fields), CloudEvents specification (typed, extensible event schema for distributed systems), Factorio blueprint JSON (structured records with typed fields — but players don't read them directly).

### Model F: "The Living Language" — Emergent Taxonomy with Progressive Disclosure

**Mechanical specification:** The taxonomy GROWS with the player. The system starts with Model A (untyped blobs) and progressively reveals structure:

| Campaign Phase | Visible Fields | New Vocabulary |
|---------------|---------------|----------------|
| Missions 1-2 | Source only (who sent it) | `from SCOUT-A` |
| Mission 3 | + Origin type (observation vs. message) | `OBSERVATION`, `MESSAGE` |
| Mission 4 | + Content type (threat, position, order) | `THREAT`, `POSITION`, `ORDER` |
| Mission 5 | + Status, Resource types | `STATUS`, `RESOURCE` |
| Mission 6-7 | + Urgency attribute (continuous 0-1) | `urgency > 0.7` |
| Mission 8 | + Confidence attribute | `confidence > 0.5` |
| Mission 9 | + Noise, Unknown types | `NOISE`, `UNKNOWN` |
| Mission 10 | Full schema available | All fields |

**What rules can test:** Only the fields that have been "unlocked" so far. A Mission 2 rule can only test `source`. A Mission 5 rule can test `source + origin + content_type + channel`. A Mission 10 rule can test everything.

**How the player designs:** Each mission introduces 1-2 new signal properties through gameplay necessity. Mission 3's challenge requires distinguishing observations from messages → origin type unlocks. Mission 6's challenge requires prioritizing urgent data → urgency slider unlocks. The taxonomy feels DISCOVERED, not imposed.

**Strengths:**
- Perfect pacing. Each new field is introduced when the player needs it, not before.
- The "subsystem online" boot log beat: `[SIGNAL CLASSIFIER v2.0 ONLINE: CONTENT_TYPE field now available in CONTEXT WINDOW]` — diegetic unlock that teaches vocabulary.
- Veterans can access the full schema immediately via a "technical mode" toggle (interaction with 5.00c veteran fast-path).
- Combines the best of all models: starts as simple as Model A, ends as expressive as Model E.
- Each unlock is a gameplay moment — the first time the player sees a colored pip instead of an amber blob, the first time a rule can test `content_type`, the first time urgency appears as a slider.

**Weaknesses:**
- Replay complexity. On a second playthrough, the early missions feel artificially constrained. Need a "skip taxonomy tutorial" option that unlocks the full schema from Mission 1.
- The unlock order is a design commitment. If the order is wrong (e.g., urgency should come before content type for some players), the pacing feels forced.
- Community fragmentation. Players at different campaign stages have different vocabularies. A Mission 4 player can't read a Mission 8 config shared on Discord because it uses fields they haven't unlocked.
- Testing burden. Every rule, every hook, every context config must work correctly at every taxonomy level (10 configurations to test).

**Sensory description:** The buffer visualization literally GROWS. Mission 1: plain amber pips. Mission 3: pips split into green (observation) and blue (message) — a visible "upgrade" moment. Mission 4: pips show tiny content-type icons. Mission 6: pips gain a brightness gradient (urgency). Each unlock is accompanied by a brief crystallization animation — the pip shimmers, splits into more detailed rendering, and settles into its new form. The boot log announces: `PERCEPTION SUBSYSTEM: Signal classification module installed. Your context window now distinguishes THREAT signals from TERRAIN signals. Engage CONTEXT CONFIG to configure attention priorities.`

**Comparable:** Baba Is You (new rule words introduced per world — the vocabulary IS the progression), Factorio (tech tree unlocks new signal wire colors and combinators), Slay the Spire (new cards appear in higher ascensions — vocabulary expands with difficulty), Metroid (environmental scanner reveals more detail as suit upgrades are acquired).

## Recommendation: Model F with Model C Core

The recommended approach is **Model F (Living Language) as the delivery mechanism wrapping Model C (Content-Typed) as the core taxonomy**, enhanced with two continuous attributes from Model D (urgency and confidence).

The full mature taxonomy at Mission 10:

| Field | Category | When Unlocked | Auto vs. Player-Set |
|-------|----------|---------------|---------------------|
| `source_unit` | Identity | Mission 1 | Auto |
| `channel` | Routing | Mission 1 | Auto |
| `origin_type` (4 values) | Provenance | Mission 3 | Auto |
| `content_type` (8 values) | Semantics | Missions 4-9 | Auto for observations, Player-set for hooks |
| `urgency` (0.0-1.0) | Priority | Mission 6 | Auto for observations, Player-adjustable for hooks |
| `confidence` (0.0-1.0) | Reliability | Mission 8 | Auto-decays with hops/age |
| `location` | Spatial | Mission 1 | Auto for observations, Optional for hooks |
| `tick_created` | Temporal | Mission 1 | Auto |

This gives the game:
- A **learnable 8-type content vocabulary** (THREAT, TERRAIN, POSITION, ORDER, STATUS, RESOURCE, NOISE, UNKNOWN) that creates readable rules and colorful buffer visualization
- **Two continuous attributes** (urgency, confidence) for advanced tuning without overwhelming beginners
- **Progressive disclosure** that paces vocabulary introduction across the campaign
- **Automatic classification** for observations (the game assigns content type based on what was perceived) with **player agency** for hook transmissions (the player chooses what content type to label their signals)

## The Eight Content Types — Deep Dive

### THREAT (⚠️ Red-Orange)
**What generates it:** Perception of an enemy unit within range. Auto-classified by the perception system.
**Payload:** Enemy type, position, heading, estimated buffer state (if within close range).
**Urgency formula:** `1.0 - (distance_to_enemy / perception_radius)`. Adjacent enemy = 1.0. Edge of perception = 0.2.
**Tactical role:** The most important signal type. The one that triggers engagement, evasion, and alarm chains. A buffer full of THREAT signals means the unit is surrounded — and probably about to be overloaded.
**Design tension:** Should a Relay that receives a THREAT message re-classify it as MESSAGE or preserve THREAT? Recommendation: preserve content type across hops (a relayed threat is still a threat), but origin type changes (OBSERVATION → MESSAGE).

### TERRAIN (🗺️ Brown-Green)
**What generates it:** Perception of map features — jungle tiles, city blocks, resource nodes, factory positions.
**Payload:** Tile type, position, traversability, signal attenuation modifier (if applicable).
**Urgency formula:** Always 0.1 (terrain doesn't change). Urgency rises to 0.5 if terrain was recently damaged (6.01a-iii).
**Tactical role:** Low-priority background data. In early missions, terrain is noise — the player learns to filter it out. In late missions with terrain-modified signal routing (2.00f-ii), terrain data becomes strategically valuable.
**Design tension:** TERRAIN is the "noise" of the perception system. A scout with wide perception sees LOTS of terrain every tick. This is the first thing players learn to filter — and filtering terrain IS the first attention design lesson.

### POSITION (📍 Cyan)
**What generates it:** Perception of friendly units, or self-position reports via hooks.
**Payload:** Unit ID, position, unit type, buffer state (visible if within close range).
**Urgency formula:** 0.2 default. Rises if the friendly unit is in STUN state (0.8) or has changed position since last report (0.4).
**Tactical role:** Enables formation awareness. A Command agent uses POSITION signals to know where its subordinates are. A Striker uses POSITION signals from other Strikers to avoid target duplication.
**Design tension:** Position data ages fast. By the time a POSITION signal reaches a Command agent via relay chain (2-4 tick latency), the unit may have moved. This is the "observation gap" (2.20) made concrete through a specific content type.

### ORDER (📋 Purple)
**What generates it:** Hook transmissions explicitly tagged as ORDER by the player. Only Command agents and player-configured Relays typically send ORDERs.
**Payload:** Directive type (converge, spread, patrol, retreat, hold), target location or unit, priority level.
**Urgency formula:** Player-set in hook config (0.1 for routine, 0.5 for tactical, 1.0 for emergency).
**Tactical role:** The downward signal — from coordinators to executors. ORDERs are what make hierarchical architectures work. A Striker that receives an ORDER overrides its default patrol behavior.
**Design tension:** ORDER is the only content type that is ALWAYS player-set (never auto-generated by perception). This makes it the player's most direct channel of influence on unit behavior during execution. The temptation is to make every hook an ORDER — but ORDER signals from multiple sources create the "Committee Problem" (2.00e-i).

### STATUS (📊 Amber)
**What generates it:** Self-diagnostic hooks ("my buffer is 80% full," "I just entered stun," "compress skill completed").
**Payload:** Unit ID, metric name, value, trend (rising/falling/stable).
**Urgency formula:** Scales with severity. Buffer at 50% = 0.2. Buffer at 80% = 0.6. Stun entered = 1.0.
**Tactical role:** The health monitoring signal. A Command agent watching STATUS signals from its subordinates can detect overloaded relays, stunned scouts, and starving strikers. This is the operational dashboard of the army.
**Design tension:** STATUS signals are meta-signals — data about data. They consume buffer slots to report buffer state, creating a small recursive overhead. A relay that sends STATUS every tick uses 1 hook slot and generates 1 buffer entry in every listener, forever. This is the "monitoring cost" problem — identical to real observability overhead.

### RESOURCE (💎 Gold)
**What generates it:** Perception of untagged resource nodes, or hook reports about economy state.
**Payload:** Node position, current tag state, estimated yield.
**Urgency formula:** Low default (0.2). Rises if the node is being contested (enemy nearby = 0.6).
**Tactical role:** Economy awareness. In factory-phase missions (5+), resource signals guide production decisions. A scout that finds an untagged node sends RESOURCE signal → Relay forwards → Command adjusts production queue priority.
**Design tension:** RESOURCE signals are only relevant after Mission 5 (factory introduction). Before that, resource nodes don't exist. This content type exemplifies the progressive unlock — it literally doesn't appear until the game needs it.

### NOISE (📡 Grey-White)
**What generates it:** Detection of EM emissions from any unit (friendly or enemy). Passive interception of radio chatter.
**Payload:** Approximate source position, signal strength, frequency signature.
**Urgency formula:** Low for friendly emissions (0.1). High for unknown/enemy emissions (0.6-0.8).
**Tactical role:** Counter-intelligence. A Specialist with detect skill can sense enemy EM emissions even outside perception range. NOISE is how the player detects hidden enemy relays and command units. It's also how ENEMIES detect the player's architecture — deep relay chains emit lots of noise.
**Design tension:** NOISE is double-edged. Your own army generates NOISE that enemies can detect. Configuring units to LISTEN for NOISE also means their buffers fill with friendly emission data unless filtered. The "EM silence" strategy (minimal hooks, minimal emissions) trades intelligence for stealth.

### UNKNOWN (❓ Flickering Grey)
**What generates it:** Degraded signals (fidelity loss from long relay chains), enemy-injected deception signals that fail authentication, or corrupted data.
**Payload:** Partial or garbled data. Location may be approximate. Source may be spoofed.
**Urgency formula:** Variable (inherits from original signal, but confidence drops to 0.1-0.3).
**Tactical role:** The "here be dragons" type. UNKNOWN entries are suspicious — they might be valuable intelligence degraded by distance, or they might be enemy disinformation. A Specialist's extract skill can attempt to reconstruct UNKNOWN entries. The decision to act on UNKNOWN data vs. ignore it is a core late-game skill.
**Design tension:** UNKNOWN signals create the "paranoia dial" in context config. High paranoia: ignore all UNKNOWN data (safe but information-poor). Low paranoia: treat UNKNOWN as potentially valid (more intelligence but vulnerable to deception). The paranoia setting IS the player's risk tolerance, expressed as a context config toggle.

## Interaction Effects

### With Buffer Models (2.01-2.05)
- **Fixed-slot:** Each content type occupies 1 slot. A 6-slot Scout buffer with 3 THREAT + 2 TERRAIN + 1 POSITION is instantly legible as "mostly about nearby enemies."
- **Weighted:** Different content types could have different weights. THREAT = 1 slot, STATUS = 1 slot, but a detailed ORDER = 2 slots (more payload). Creates type-aware buffer pressure.
- **Decay:** Different content types could decay at different rates. TERRAIN decays slowly (terrain doesn't move). THREAT decays fast (enemies move every tick). POSITION decays fastest (stale positions are dangerous). This pairs PERFECTLY with Model C content types.

### With Rules Language (3.05)
Content types become the primary VOCABULARY for conditions. `IF THREAT` is the most common rule prefix. The sentence builder (3.05 Model D) reads naturally: `WHEN [THREAT] [within 2 tiles] [urgency > 0.7] → [ENGAGE] [nearest]`. Content types are the nouns of the rules language.

### With Hook Configuration (3.08-3.11)
Hook transmissions include a content type selector. When configuring a hook, the player chooses: "ON_PERCEPTION → SEND on channel `intel` as THREAT." This choice determines how downstream listeners classify the signal. A misconfigured hook that sends TERRAIN data tagged as THREAT will cause Strikers to engage empty tiles — a debuggable error that teaches data labeling.

### With Context Config
Content types enable type-based filtering: "Listen to THREAT and ORDER, ignore TERRAIN and RESOURCE." This is the most intuitive way to configure attention — by WHAT you care about, not just WHERE it comes from. The context config panel becomes a checklist of content types with listen/ignore toggles per type.

### With Inspector
Content types make the Inspector vastly more readable. Buffer state at any tick shows a typed breakdown: "3 THREAT, 1 ORDER, 2 TERRAIN." The player can filter the event log by content type: "Show me only THREAT signals across all units." Signal genealogy traces become semantic: "This THREAT originated as an OBSERVATION from SCOUT-A, was relayed as a MESSAGE through RELAY-B, and arrived as PROCESSED via RELAY-C's compress skill."

### With Information Warfare (2.12, 2.16, 2.26)
Content types are the ATTACK SURFACE for deception. Enemy injection sends a false THREAT signal — the player's units react to a phantom enemy. The Specialist's intrusion detection skill checks signal provenance and reclassifies suspicious entries as UNKNOWN. Content type authenticity becomes a late-game mechanic: "Is this THREAT real or injected?"

### With Sealed Watch Visualization
During sealed watch, buffer bars show content-type-colored pips. A well-designed army has a rainbow of signal types flowing through it. An overloaded army shows mono-colored buffers (all THREAT = surrounded, all ORDER = micro-managed, all NOISE = being jammed). The COLOR PATTERN of the buffer tells the battle's story at a glance — even at sealed watch zoom level.

| ORDER | 87 | 17% | 0.55 | 1.00 |
| STATUS | 64 | 13% | 0.40 | 0.95 |
| TERRAIN | 52 | 10% | 0.10 | 1.00 |
| NOISE | 28 | 6% | 0.45 | 0.60 |

"Look at this. 23% of my entire signal traffic is POSITION data. Friendly units constantly reporting where they are. And the average urgency is 0.25 — almost none of it is actionable. **Minute 2:00 — The Compression Strategy**
Amara redesigns RELAY-B's compress skill configuration. Previously, compress treated all input equally — 3 signals in, 1 compressed signal out. Now she configures content-type-aware compression: "Compress POSITION signals into a single summary every 3 ticks. Forward THREAT signals uncompressed. Drop TERRAIN entirely." The compress skill's config panel shows a priority queue: `1: THREAT (pass-through) → 2: ORDER (pass-through) → 3: STATUS (compress 3:1) → 4: POSITION (compress 5:1) → 5: TERRAIN (drop)`.

"This is literally a message broker with topic-based routing and per-topic QoS policies," she says to herself, recognizing the Kafka parallel. "THREAT is a zero-loss topic. POSITION is a sampled topic. TERRAIN is /dev/null."

**Minute 4:00 — The Confidence Threshold Experiment**
Amara notices her Command agent is acting on 8 UNKNOWN signals across 80 ticks. Each UNKNOWN triggers a defensive posture — the Command sends "retreat" ORDERs that waste 2-3 ticks. She opens the Command's context config and finds the confidence threshold slider (unlocked in Mission 8). Currently set to 0.0 (accept everything). She moves it to 0.3. This will reject all UNKNOWN signals (confidence < 0.2) and degraded relay signals (confidence drops with hops).

But she hesitates. "If I set the threshold to 0.3, I'll also reject legitimate signals that traveled through 4 relay hops — by the time they arrive, confidence has decayed to 0.25. My deep scout reports will be treated as noise." She pulls up the confidence decay formula in the Blueprint Codex: `confidence_at_receiver = confidence_at_source × (0.85 ^ hops)`. A 4-hop signal from a Scout (source confidence 1.0) arrives at 0.85^4 = 0.52. Safe above 0.3. A 6-hop signal arrives at 0.85^6 = 0.38. Still above 0.3 but tight. She sets the threshold to 0.35 — aggressive enough to reject UNKNOWN but still accepting 5-hop legitimate signals.

"I just tuned a classifier's confidence threshold," she murmurs. "Accept rate vs. false positive rate. This is literally ROC curve thinking in a game."

**Minute 7:30 — The Type-Based Eviction Policy**
Amara's final optimization: the Command agent's 14-slot buffer with type-based eviction priority. She drags content types into a priority order in the context config:

```
EVICTION PRIORITY (evict first → keep longest):
1. TERRAIN (evict immediately — Command doesn't need terrain)
2. NOISE (evict after 2 ticks — recent noise is useful, old noise isn't)
3. POSITION (evict after 3 ticks — position data ages fast)
4. STATUS (keep for 5 ticks — relay health monitoring)
5. RESOURCE (keep for 5 ticks — economy decisions)
6. ORDER (keep until superseded — the Command's own orders persist)
7. THREAT (never evict manually — threats are top priority)
```

The eviction policy is now a semantic priority queue — the buffer automatically keeps the most important information categories and discards the least important. "This is exactly how I'd configure a bounded message queue in production. Topic-priority-based retention with TTL overrides."

**Minute 10:00 — The Result**
Amara runs the battle. Post-battle Inspector shows: POSITION traffic down 60% (compression working). UNKNOWN signals rejected at the Command level (zero false retreat orders). Buffer utilization on the Command: never exceeded 85% (previously peaked at 100% with stun). The efficiency score jumps from 72nd to 89th percentile. She screenshots the content-type frequency histogram and posts it to the game's Discord: "Type-aware compression + confidence thresholds + semantic eviction. This is what production message pipeline optimization looks like as a game mechanic."

- **2.10d — Enemy signal type spoofing depth:** How sophisticated can enemy type spoofing get? Level 1: wrong content type (THREAT tagged as POSITION).
